## Audit Method Notes

- Requirements were re-cross-referenced across three sources this run, not carried forward.
- **Integration is live-verified this run, not inherited.** Run 2 explicitly declared its seam
  verdicts as carried forward on an unchanged tree; this run replaces them with evidence from a
  real release, a real tap push, and a real cask install. The distinction is recorded so a reader
  can tell which runs asserted what.
- Source drift since run 2 is four files — `post-release-verify.yml`, `taskfile_shape_test.go`,
  `.release-please-manifest.json`, `CHANGELOG.md`. None is compiled into the indexer binary
  (`_test.go` files are excluded from the build), so no seam verdict rests on changed code.
- **A checked assumption that would have been an overclaim.** Phase 4's `leg3_executed` was not
  marked closed by the `post-release-verify` run: that workflow has five jobs and
  `rg -c 'brew install'` returns **0**. Gatekeeper and notarized-suite prove the published darwin
  binaries pass Gatekeeper and the real suites — valuable, but not a cask install. leg3 was closed
  only after a real `brew`-installed v0.9.0 was observed refusing.
- **Four self-inflicted false signals in this session**, all the same class — a query that does
  not match reality reports absence rather than truth: `go test -run` printing `ok` on zero
  matches; `rg -c '\b17\b'` matching `goreleaser/v2@v2.17.1` version strings; `task` echoing
  unexpanded `${VAR}` source lines so an EVIDENCE-line count doubles; and a receipt glob searching
  `<token>/<version>/.metadata/` when the Caskroom receipt lives at `<token>/.metadata/`. The
  standing discipline (rule 84d1gfpywd) is to assert resolved content with a positive count, never
  a bare match or an absence.
- Retained from run 1: the integration checker ran on `haiku`, which this repo has a recorded
  reliability finding against; its two load-bearing claims were independently re-verified by the
  orchestrator before acceptance.
