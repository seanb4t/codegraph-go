## Audit Method Notes

- Requirements were cross-referenced across three independent sources this run, not carried
  forward from the first audit.
- **Integration and flow scores were explicitly carried forward, not re-derived.** The
  justification is a measured one — zero non-`.planning` file changes since the audited commit
  — and is stated in the Cross-Phase Integration section itself so a reader cannot mistake
  inherited depth for verified depth. Same discipline the phase-level SECURITY.md files apply.
- Phase 1's closure this session refused the ASVS-L1 short-circuit (fourth consecutive phase to
  do so) and verified all 45 threats inline with executed commands, not plan-time assertions.
  Two load-bearing positive assertions: 34 jobs across 13 workflow files scanned with exactly
  one holding `id-token: write`; 111 `uses:` references resolving to 91 SHA-pinned + 20 local
  with remainder 0.
- **A finding worth carrying forward as a pattern, not debt.** Phase 1's threat T-01-38 recorded
  "exactly 3 guards, matching the 3 jobs" for `post-release-verify.yml`. Phase 2 later added two
  jobs; the file now has 5 jobs and 5 guards. The **1:1 invariant survived the change**, where a
  count-based assertion (`== 3`) would have gone red on a correct addition. This is the same
  lesson as `verify:release-assets` asserting set equality rather than a fixed 17-asset total,
  arriving from the opposite direction: assert the relationship, not the cardinal.
- One orchestrator self-error is recorded from this run, the fourth sighting of the shape:
  `rg -c '\b17\b' Taskfile.yml` returned 11, which read as Phase 1's T-01-33 (brittle fixed-total
  assertion) being live. All 11 are `goreleaser/v2@v2.17.1` version strings and `D-14`/`D-17`
  decision references. Scoping to the actual 197-line `verify:release-assets` block
  (`Taskfile.yml:2362-2558`) gives 0. **A whole-file grep is not an assertion about a target.**
- From the first run, retained: the integration checker ran on `haiku`, which this repo has a
  recorded reliability finding against. Its two load-bearing claims — the cask `sha256` match
  and the `INSTALL_RECEIPT.json` location — were independently re-verified by the orchestrator
  before being accepted. A prior sha256 comparison used an `rg` lookahead this build rejects,
  leaving variables empty and printing `✗ MISMATCH` on byte-identical hashes — a broken
  extraction can fail loudly and wrongly, which is more dangerous than failing quietly.
