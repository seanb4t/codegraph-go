    ## First: a stable origin, because `codegraph ui` has no port flag

    `web/scripts/live-push-stable-proxy.mjs` — a tiny loopback reverse proxy, started ONCE and
    kept alive for the whole run, in front of a `codegraph ui` that may be stopped and
    restarted behind it.

    This exists because the previous draft's RECONNECT scenario could not pass. `codegraph ui`
    binds an ephemeral loopback port and exposes no bind/port flag (`internal/cli/ui.go:26`,
    `:40`, `:81-82` — the only flags are `--path` and `--no-open`). Stop and restart it and
    the tabs are pointed at a dead URL forever; their reconnect loop can never reach the new
    process, so "every tab is receiving events again afterwards" is unsatisfiable. Adding a
    port flag is NOT the fix — that changes `SRV-01`/`SRV-03`'s shipped command surface and
    reopens D-08, for a test harness. The proxy changes nothing that ships.

    Requirements on the proxy, each load-bearing:
    - Bind once on loopback. The port may be ephemeral; what matters is that it never changes,
      so the tabs' ORIGIN survives the upstream restart.
    - Forward to a MUTABLE `upstreamURL`, updated when the UI is restarted. Expose that update
      to the check script (a module export, or a tiny control endpoint on the same listener).
    - REWRITE `Host` and `Origin` to the upstream's own authority before forwarding. The
      upstream's exact-match guard (`originguard.go:42-67`) requires `Host` to be in the
      allowlist for the UPSTREAM's port AND `Origin == "http://" + Host`; forwarding the
      proxy's own authority is rejected with 403, and rewriting only one of the two is
      rejected by the pairing check. Rewrite both, to the same spelling.
    - STREAM the response. `res.writeHead` from the upstream's status and headers, then pipe —
      no buffering middleware, no response accumulation. This is not merely for latency: the
      FAN-OUT scenario below runs through the proxy and would DEADLOCK on a buffering proxy at
      its "wait until every tab received generation k" step, which is exactly the desired
      failure mode. The proxy is therefore self-policing and needs no separate assertion.
    - Return a 502 and destroy the socket when the upstream is down, so the browser sees a
      genuine stream failure and the client's own backoff engages.

    Write it as an importable module (an exported `startProxy({ port })` returning a handle with
    a `setUpstream(url)` method and a `close()`), so Task 2 drives it in-process rather than
    shelling out to a second node process and parsing its stdout.
  </action>

    printed URL, point the proxy at it. Open at least THREE real tabs in one browser context
    ON THE PROXY'S URL, each on a route that subscribes to live push.

    Instrument each tab to record, per event, the generation and a client-side receipt
    timestamp. Note that each tab's FIRST event is the seeded current state (`06-02`'s
    `Subscribe` contract) and is not a triggered generation — record it separately as
    `seedGenerationPerTab` and exclude it from the triggered accounting below.

    Then run three scenarios and record evidence for each:

    FAN-OUT AND TIMING. Trigger at least three REAL re-indexes, spaced deliberately, waiting
    each time until every tab has received that generation before triggering the next. Record
    `triggeredGenerations` (the array of generation values the triggers produced) and
    `receivedGenerationsPerTab` (per tab, the array of generations received after the seed).
    Every tab's received set must be a SUPERSET of `triggeredGenerations`, and the recorded
    inter-arrival gap between consecutive TRIGGERED receipts, per tab, must be at least the
    trigger spacing. A test asserting only that N messages arrived is vacuous here — silent
    buffering delivers all N at the end and passes — and so is an inter-arrival MINIMUM
    computed over a single receipt, which is vacuously satisfied. The superset check is what
    pairs the timing bound with a real receipt floor; the blocking structure is what makes
    buffering deadlock rather than pass.

    FAN-OUT ISOLATION (this replaces the previous "BACKPRESSURE" scenario — see below). Occupy
    one tab's main thread for longer than the trigger interval, keep the other two normal, and
    trigger several re-indexes. Record: `blockedTabBlockedMs` (the measured block duration),
    `blockedTabReceiptsDuringBlock` (which MUST be 0 — the proof the tab really was blocked, not
    merely believed to be), the two healthy tabs' per-generation receipt latencies during the
    block, and the blocked tab's generation on recovery. Assert the healthy tabs received every
    triggered generation with their inter-arrival timing still bounded by the trigger spacing,
    and that the recovered tab is at the NEWEST generation.

    **This scenario deliberately does NOT claim to prove server-side backpressure, and must not
    be written as though it does.** Blocking a tab's main thread does not stop the browser and
    the kernel from draining a handful of tiny Connect envelopes into their own buffers, so the
    slow tab may well receive every intermediate generation when it resumes — meaning
    `slowTabFinalGeneration === newestGeneration` passes whether or not the publisher's
    capacity-1 coalescing channel ever engaged. Real transport pressure at re-index pacing
    (seconds apart, ~40-byte messages) cannot be manufactured in a browser: the send loop always
    wins. The coalescing claim is therefore carried where it CAN be made deterministic and
    non-vacuous — `06-04`'s `TestWatchGraphHandlerCoalescesForANonReadingClient`, which opens a
    real stream over real HTTP/1.1, stops receiving, publishes 2000 generations, and asserts
    `received < published` with the newest surviving. Record that division of labour in the
    record as `coalescingProvenBy` and repeat it in the SUMMARY, naming that test. What this
    browser scenario proves — fan-out isolation, that a stalled tab does not degrade healthy
    ones — is genuinely what T-06-34 is about and is genuinely only observable here.

    RECONNECT. Stop the `codegraph ui` process, start a NEW one against the same repository,
    and point the proxy at the new upstream — the tabs' origin never moves. Record each tab's
    reconnect attempt timestamps and the raw delay arrays. Assert every tab is receiving events
    again afterwards. Because the restarted publisher's generation counter begins again at 1,
    the post-reconnect receipts will carry LOWER generation values than the pre-restart ones;
    that is expected and is exactly what `06-03`'s connection-epoch rule exists to handle — a
    tab that applies nothing after the restart is a FAILURE of that rule, so assert each tab
    applied at least one post-reconnect event. Record `resumeCursorSentPerTab` (the
    `since_generation` each tab sent on its reconnect request) and assert it is greater than
    zero — the client resumed from what it had seen rather than restarting from scratch.

    Record the per-tab attempt-count and total-attempt figures explicitly: a reconnect storm is a
    high attempt count in a short window, so the record must carry the number, not a verdict.
    Record the raw delay arrays too — the verify command RECOMPUTES growth and cross-tab
    distinctness from them rather than reading a self-reported boolean.
  </action>
