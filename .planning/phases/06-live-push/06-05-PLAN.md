<objective>
Make the graph view update in place without throwing the developer's mental map away.

Purpose: LIV-04 is verified against the graph view specifically — list and table views do not
exhibit this failure. And the guarantee cannot come from the layout engine: ELK's own
maintainer states on the record that the layered algorithm "cannot be used to precisely fix
the positions of the nodes", only "somewhat preserve the topology." D-06 therefore relocates
the guarantee into our own authoritative write-back after layout, which is exact, rather than
into ELK's best effort, which is explicitly approximate.

Output: a two-path live-update seam on the renderer, the route wiring that feeds it, and the
guava-scale displacement measurement D-06 mandates.
</objective>

    - Given an incoming set that ADDS nodes, every surviving leaf node's position after the update equals its position before, exactly.

    - Given an incoming set that both adds and removes, the same holds.

    Implement D-03's two paths:

    FAST PATH — the node id set is unchanged (only counts, cycle membership or health moved).
    Update the affected element data in place and run no layout at all. Republish geometry
    directly, exactly as `removeByIds` already does when it changes the model without running a
    layout. Running a layout here would move nodes for no reason, which is precisely the failure
    LIV-04 names.

    STRUCTURAL PATH — nodes were added or removed. Before touching the model, capture every
    currently-rendered node's model position keyed by id. Perform the element swap through the
    existing replace bookkeeping so the symbol-survivor rule is not duplicated. Run the layout
    with the interactive strategies enabled, then — on `layoutstop`, before geometry is
    republished — authoritatively write each surviving node's captured position back.

    Enable ELK's interactive strategies by extending the existing `elk` options object (a plain
    pass-through merged into ELK's own layout options) with the interactive layering,
    cycle-breaking and semi-interactive crossing-minimisation settings, so NEW nodes are placed
    knowing where the survivors are. cytoscape-elk already sends every node's current position
    to ELK, so ELK does have that knowledge. But the interactive strategies only approximate;
    the exactness comes from the write-back. Keep `LAYOUT_OPTIONS` a single shared
    configuration — do not fork a second layout config for live updates.

    Write back positions for NON-PARENT nodes only. In cytoscape a compound's position is
    derived from its children; setting a parent's position moves its children and would undo the
    exact restoration. Restoring every leaf makes each unchanged compound follow its children
    exactly, while a compound that genuinely gained a child moves — which is correct.

    Verifying ELK option names: `elkjs` resolves to 0.9.3 and is a transitive dependency that
    pnpm does NOT hoist. It exists only under the pnpm content-addressed store path, never at
