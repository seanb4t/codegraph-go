<objective>
Build the server-side engine of live push: a store watcher that learns a re-index happened,
a change detector that decides whether that is worth telling anyone, and a bounded,
coalescing fan-out registry that hands the news to every open stream without letting a slow
reader hurt a fast one.

Purpose: this is where criterion 5 is won or lost. `pebble.Open` holds an EXCLUSIVE directory
lock for the store's whole open lifetime (`internal/graphstore/pebble_store.go:67-80`), so a
publisher that holds the store open would not merely slow a concurrent `codegraph daemon`
sync — it would deny it the store outright. Open, read, close, on every wake.

Output: `livepublish.go` and its goleak-guarded test file, with no HTTP or Connect
dependency of any kind — the handler in `06-04` consumes this, not the other way round.
</objective>

  <behavior>
    - Subscribing returns a receive-only channel and an unsubscribe function; subscribing twice yields two independent channels.
    - Publishing to a subscriber whose buffer is EMPTY delivers that event.
    - Publishing to a subscriber whose buffer is FULL REPLACES the unsent event with the newer one (D-04). The subscriber then reads the NEWER generation, never the older — asserted by generation value, not by count.
    - Publishing never blocks: with one subscriber that never reads and one that reads every event, N publishes complete and the reading subscriber observes the final generation. The reading subscriber's observed count is asserted with a non-zero floor, so "nothing blocked" cannot be satisfied by nothing having happened.
    - Unsubscribing removes the subscriber from the registry: the registry's subscriber count returns to its prior value, and a subsequent publish does not touch the removed channel.
    - Cancelling a subscriber's context removes it exactly as an explicit unsubscribe does.
    - Counter separation (the recorded verdict for criterion 3): the count of server-initiated event sends and the count of live client-initiated subscribers are two distinct values that never share storage. Subscribing and unsubscribing leave the sends count unchanged; publishing leaves the subscriber count unchanged. Both directions asserted.
    - Under `goleak`, a publisher started and stopped with N subscribers attached leaks no goroutine.
  </behavior>
  <action>
    Extend `internal/uiserver/livepublish.go` with the subscriber registry. Tests first.

    Implement D-04's backpressure exactly as decided: one small buffered channel per
    subscriber (capacity 1 is sufficient and is the clearest expression of the semantics),
    and on a full buffer, drain the stale value and enqueue the new one under the registry
    lock. These are state-change notifications, not a log — a client that never sees
    "changed at T1" loses nothing by receiving only "changed at T2", because it re-reads
    current state either way. Dropping the NEWEST would be backwards; disconnecting a slow

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem -> UI process | Untrusted, high-volume event source; another process (the daemon, a manual index) is the writer |
| UI process -> shared Pebble store | Cross-process exclusive directory lock; the UI must never deny it to a writer |
| publisher -> N subscribers | Per-subscriber state held on behalf of a client that may vanish or stall |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-05 | Denial of Service | store handle held across a stream lifetime | critical | mitigate | Task 1 opens through `openEngine`, defers `Close`, and returns — one open per debounced check, never a retained handle. Proven by an injected seam asserting `opens == closes` with a non-zero floor. `06-06` re-proves it against real concurrent processes. |
| T-06-06 | Denial of Service | fsnotify event storm from Pebble compaction | medium | mitigate | `watch.Debouncer` coalesces bursts into one flush; the last-sync comparison discards non-index churn before any subscriber is touched. |
| T-06-07 | Denial of Service | unbounded per-subscriber buffering | high | mitigate | D-04's capacity-bounded, coalescing channel: memory is O(1) per subscriber regardless of event rate. |
| T-06-08 | Denial of Service | a stalled subscriber blocking the publisher | high | mitigate | The send path never blocks; a full buffer is drained and replaced under the registry lock. Proven by the non-blocking test with a deliberately non-reading subscriber. |
| T-06-09 | Denial of Service | subscriber-registry growth from abandoned tabs | high | mitigate | Context cancellation removes the subscriber from the map; asserted by test in both the explicit-unsubscribe and cancelled-context forms, with `goleak` covering the goroutine half. |
| T-06-10 | Tampering | server-initiated sends corrupting client-initiated subscriber state | high | mitigate | Two structurally separate counters, with both directions of non-interference asserted by test — the encoded form of the verdict LIV-03 requires be recorded rather than assumed. |
| T-06-11 | Information Disclosure | an unvalidated commit SHA leaving the server | medium | mitigate | `schema.IsCommitSHA` is applied at this exit exactly as `GetStatus` applies it at its own, degrading a malformed value to the empty string. |
| T-06-12 | Denial of Service | a store-lock error escalated into a publisher crash | high | mitigate | `errors.Is(err, graphstore.ErrStoreLocked)` is a soft "retry next wake" outcome; classification is by exported sentinel, never by message text. |
</threat_model>
