multi-process use, and running `codegraph ui` alone is the dev workflow that hides it.

      each message in a length-prefixed envelope, so counting messages or reading generations
      out of a curl body requires decoding those envelopes — a curl invocation with the right
      Host and Origin headers proves a connection was accepted and nothing about what arrived.
      The generated client already handles framing, the origin/host pairing (it sends the base
      URL's own authority as both) and incremental delivery.

    `mcp --path <repo> --seconds N`
      Spawns `codegraph serve --mcp --path <repo>` with stdin and stdout PIPES held open,
      performs the MCP `initialize` handshake, then keeps the pipes open for N seconds — so
      this is genuinely one of the three concurrent processes for the whole run, not a
      process started at the end to answer one question. After N seconds it issues ONE real
      tool call, validates the response, prints a JSON verdict and exits. `serve --mcp` is
      stdio-only (`internal/cli/serve.go:179`), so there is no socket to poll and a one-shot
      invocation would neither hold the store open during the run nor prove liveness after it.

    Both subcommands print a single JSON object to stdout on exit and write nothing else there,
    so the gate script in Task 2 can parse them without scraping prose.

    **Measure the no-UI BASELINE first.** Before starting the UI and the stream probe, drive
    the same five real re-index flushes with only the daemon running, and record
    `baselineMaxFlushDurationMs`. Without it `maxFlushDurationMs` is recorded and bounded by
    nothing, and a severely degraded but eventually-completing flush scores a clean pass —
    which is precisely the "slowed, not denied" half of criterion 5 that a bare completion
    count cannot see.

    Then drive at least FIVE real re-index flushes with all three processes running. Each
    flush needs BOTH of its endpoints pinned, and the debounce excluded from the interval:

    - **Write a content-derived marker.** Modify a source file whose new content contains a
      unique per-flush token (a symbol name carrying the flush index and a nonce). This is
      what makes completion attributable: `last_sync_unix_ms` advancing proves *an* index ran,
      not that YOUR revision landed, and the daemon may be reconciling something else.
    - **START the clock after the debounce window has elapsed, not at the write.** The
      daemon's debounce is `DebounceDuration()` — 2000 ms by default. Sleep it out, then
      start timing. Including it in the interval inflates BOTH the baseline and the
      concurrent measurement by a constant ~2000 ms, which does not cancel: it makes
      `maxFlushDurationMs <= 3 * baselineMaxFlushDurationMs + 1000` enormously less sensitive,
      because a baseline dominated by a fixed sleep leaves a bound that real degradation has
      to be gigantic to breach. Set `CODEGRAPH_DEBOUNCE_MS` explicitly for the run and record
      the value, so the exclusion is exact rather than approximate.
    - **STOP the clock when the marker is queryable**, not when a timestamp moves: poll until
      the index reports the symbol carrying that flush's unique token. Record both endpoints
      and the excluded debounce for every flush.

    Apply exactly the same three rules to the baseline run, so the two remain
    apples-to-apples — and record `debounceExcludedMs` in the JSON so a reader can see the
    interval is the indexing work rather than the wait.

    **Define "starved" operationally, not as a feeling.** A flush counts as STARVED when
    either (a) the daemon's own output for that flush reports a store-lock failure — match on

    condition fired. "Whether any store-lock contention was reported" without a rule for
    reading it is not a definition.
