<objective>
Build the browser half of live push: a reconnecting stream consumer, a broadcast store the
routes subscribe to, and the change that lets one classifier serve both the unary status
answer and the live event.

Purpose: criterion 1 requires the staleness and health chrome to update "by the same
mechanism rather than staying stale itself while the data around it moves." D-07 made that
mechanically possible by giving the event `GetStatusResponse`'s own field names; this plan
cashes that in by widening one function signature rather than building a second classifier.

Output: `web/src/lib/live/`, a widened `classifyStatus` contract, and the route subscriptions
that make open views update in place.

  <behavior>
    - Starting the client calls the generated streaming method once and iterates it with `for await`, handing each event to the callback as it arrives. A test that resolves the async iterable's second value only after the first callback has already fired proves consumption is incremental; collecting the iterable first would deadlock that test.
    - Each delivered event updates the client's last-seen generation.
    - **Every successful (re)establishment of the stream increments a connection EPOCH, and each delivered event is handed to the callback with the epoch it arrived under.** This is not bookkeeping for its own sake: the server's generation counter is per-process and starts again at 1 after a restart, so a tab holding last-seen generation 4 that reconnects to a restarted server would ignore every event forever under a strict "greater than" gate. Scoping the gate to an epoch fixes that without weakening ordering within a connection, where one ordered stream plus capacity-1 coalescing means generations only ever move forward.
    - **A stream that ends cleanly is restarted after the SAME backoff delay a thrown failure gets** — not immediately. An immediately-restarted clean EOF is a tight reconnect loop against a server that is closing streams for any reason (shutdown in progress, a proxy cycling), which is the storm LIV-03 exists to prevent. Only an explicit client stop terminates without a retry. A test drives at least 5 consecutive clean EOFs and asserts the scheduled delays grow, exactly as the thrown-failure test does.
    - The delay grows exponentially across consecutive failures and includes jitter: over a run of N consecutive failures the scheduled delays are strictly non-decreasing in their base term, and two clients failing in lockstep do not schedule identical delays.
    - The delay resets to its base after any successfully received event — a long-lived stream that drops once does not inherit an hour-old backoff.
    - Every restart sends the last-seen generation as the request's resume cursor; the first ever connection sends zero.
    - Stopping the client aborts the in-flight request and schedules no further reconnect; a pending backoff timer scheduled before stop never fires a reconnect after it.
  </behavior>

    - `classifyStatus` accepts BOTH a full unary status response and a live event, and returns the identical verdict for every combination of the five shared fields. A table-driven test walks the combinations and asserts equality between the two input shapes for each.
    - The live store exposes the store contract this app already uses: `subscribe(run)` returns an unsubscribe and invokes `run` synchronously once with the current value.
    - An event delivered to the store updates every subscriber, in registration order, exactly once per event.
    - **The generation gate is scoped to the connection epoch.** An event is applied when its epoch differs from the last applied epoch, OR its generation is strictly greater than the last applied generation within the same epoch. Everything else is ignored. So: a replayed lower generation on the SAME connection is ignored (idempotence), and the FIRST event of a NEW connection is always applied even if its generation is lower — which is what a restarted server, whose counter began again at 1, actually sends. A strict `>` gate with no epoch would leave every open tab permanently deaf after a server restart.
    - The status gate gains a way to apply a live event directly, bypassing the navigation-identity guard, and applying one emits a new verdict WITHOUT issuing a status request. A stub client counts its calls and the count must not move.
    - **One shared observation counter orders live applications against unary fetches.** The exact invariant: every `fetchStatus` START and every applied live event mints the next id from the SAME monotonic counter and records it as current; an operation may emit ONLY if the id it holds is still the current one. Consequences, both asserted: a live event applied while a unary fetch is in flight invalidates that fetch, so the fetch's response is dropped when it settles; and a unary fetch started after a live application supersedes it, so a late duplicate of that live event cannot emit. "A later in-flight unary fetch and vice versa" is too loose to pin either direction — the counter rule is the whole specification.
  </behavior>

## Trust Boundaries

| Boundary | Description |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-13 | Denial of Service | reconnect storm from many tabs after a server restart | high | mitigate | Exponential backoff with jitter, with the jitter proven by test to desynchronise two lockstep clients. Base delay and cap are named constants. |
| T-06-14 | Denial of Service | request amplification from live-triggered re-fetches | high | mitigate | Per-view coalescing (no second request while one is in flight) plus the server-side coalescing publisher; the live trigger deliberately bypasses, rather than widens, `navigationIdentity`. |
| T-06-15 | Tampering | a replayed or out-of-order event reverting the displayed verdict | medium | mitigate | Strictly-increasing generation gate in the store, plus the existing monotonic supersession id in the status gate covering the live/unary interleaving. |
| T-06-16 | Denial of Service | an abandoned reconnect timer firing after teardown | medium | mitigate | Stop aborts the in-flight request and cancels the pending timer; asserted by a test that no further call occurs after stop. |
| T-06-17 | Information Disclosure | event fields rendered into chrome | low | accept | The event carries only fields already exposed by the existing status rpc over the same loopback-only, origin-guarded surface. |
| T-06-18 | Spoofing | a cross-origin page opening the stream | high | mitigate | Unchanged and inherited: the streaming rpc mounts through the same handler constructor and the same exact-match Origin/Host guard as the 13 unary rpcs; no new bypass is introduced. |
| T-06-41 | Denial of Service | a strict generation gate silently deafening every open tab after a server restart | high | mitigate | The generation gate is scoped to the connection epoch: the first event of a new connection is always applied regardless of its generation, because the server's counter is per-process and restarts at 1.
