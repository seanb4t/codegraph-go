  <name>Task 1: Version-forcing decision (D-06, one-way once published)</name>
  <decision>Force the first automated cut to exactly `1.0.0` with a one-shot `Release-As: 1.0.0` footer, or let release-please compute the version naturally from the accumulated commits.</decision>
  <context>
    This is one-way once published. `v1.0.0` becomes what `codegraph upgrade` resolves as "latest" for every existing user the moment it publishes; a wrong version number can only be superseded, never withdrawn. A stable tag that users have already verified must never be moved.

    The mechanics are confirmed from release-please's own source: `buildNewVersion` checks a config-level version-forcing key first, then the `Release-As:` commit footer, then the normal versioning strategy. So the footer deterministically overrides whatever the accumulated commits would produce — which, from the `0.1.0` baseline, is the natural next minor rather than `1.0.0`.

    D-06 rejects two alternatives for stated reasons: a config-level version-forcing key is sticky and would pin every subsequent release until removed; and relying on a breaking-change marker yields `1.0.0` only as an accident of the pre-major rules and misrepresents a milestone as a breaking change.

    Before deciding, confirm what release-please currently proposes on the open release PR left by plan 09-07's teardown, and confirm plan 09-07's live proof passed — in particular that the cosign identity verification succeeded. If it did not, this plan must not run.
  </context>

      <cons>Adds one empty commit to `main`; the footer remains in history and must not be duplicated later.</cons>
    </option>
