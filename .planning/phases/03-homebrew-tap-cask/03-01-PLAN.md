<objective>
Prove the entire Homebrew path end-to-end on one thin slice before anything is built
on top of it: a Go subcommand that does not exist yet, a `homebrew_casks:` block that
does not exist yet, GoReleaser's cask renderer, Homebrew's own Ruby installer, and a
post-install hook that executes the installed binary — wired together and observed
working, in one task.

Purpose: three of this phase's load-bearing facts are currently assumptions.
RESEARCH.md A1 assumes the binary sits at the root of the `zip` so `binaries:` needs
no rename handling. A3 assumes `#{HOMEBREW_PREFIX}/bin/codegraph` is already a live
symlink by the time the post-install hook runs, rather than the hook needing
`#{staged_path}`. And D-10's entire claim — that the install *is* the gate — depends
on a raising hook genuinely failing `brew install`. All three are cheap to settle now
against a real `brew install` and expensive to discover after four more plans are
stacked on them.

a maintainer-invocable rehearsal target that renders the cask GoReleaser would ship
and installs it for real.

**The rehearsal target — `release:rehearse-cask`.** Maintainer-only and local, in the
shape `release:rehearse-notarize` established: never invoked by any workflow, never
added to `inScopeJobs`, guarded by named `preconditions:` so it halts by name rather
than failing halfway. Preconditions: host is darwin; `brew` is on PATH; no
brew-managed `codegraph` is currently installed (this target installs and uninstalls
a real cask into the real Homebrew prefix, and it must refuse rather than disturb an
existing install); and an explicit opt-in environment variable is set, so nobody runs
it by accident from a `task --list` browse. Use `if`/`fi` conditionals throughout —
never a trailing `&&`-chained list as the last statement inside a loop, which aborts
silently on the success branch under go-task's `set -e` while behaving normally under
plain `sh`.

The target's algorithm:

1. Run a snapshot release that renders but publishes nothing, following the flags
   `release:dry-run` already uses. Set `HOMEBREW_TAP_TOKEN` to an obvious
   non-credential placeholder for the duration, so a template referencing it cannot
   fail the run and cannot be mistaken for a real secret in the log.
2. Assert `dist/homebrew/Casks/codegraph.rb` exists and is non-empty. This is the
   positive assertion that the render actually happened; a target that proceeds to
   install a file it never confirmed was written is the vacuous-guard shape this
   repository has rule `84d1gfpywd` for.

   tag. Primary mechanism: a `file://` URL naming the local `zip` in `dist/`. If
   Homebrew's downloader rejects that scheme, fall back to serving `dist/` over a

<assumption_delta_decision>
The `assumption-delta` detector fired on this phase (`detected: true`, kind
`pluralization`). Two genuine singular-to-plural transitions are in scope, and both
are recorded here rather than left implicit.

**1. Install channel.** Before this phase there is one way codegraph arrives on a
machine: a raw binary downloaded directly, which `internal/upgrade` also swaps in
place. This phase adds a second: a Homebrew cask. The generalized noun is
**"install channel"**, and the identity question is whether `codegraph upgrade` still
names the right thing when it assumes it owns the binary it is replacing.

- **Decision: `add-alongside`, with the promotion explicitly scheduled.** The raw
  archive entry is byte-frozen by D-02/Finding 1 and `codegraph upgrade` continues to
  consume exactly it; nothing about the direct-download channel changes here.
- **Accepted debt, named:** between this phase's first release and Phase 4 landing,
  a brew-installed user who runs `codegraph upgrade` gets the direct-download
  behavior — it will try to replace a Cellar-managed binary behind brew's back. That
  window is real and is bounded by Phase 4, whose UPGR-01/02/03 are precisely the
  promotion: teaching `upgrade` to ask which channel it is on before acting. This
  phase's contribution to that promotion is D-08's sentinel, written by the
  post-install hook in plan 03-02.
- **What would force an earlier promote:** a third channel (linuxbrew, or any
  non-macOS package manager) arriving before Phase 4. At that point a per-channel
  sentinel written by one installer stops being sufficient and the channel identity
  has to move into the binary's own resolution logic.

**2. Release write credential.** Before this phase, one credential writes on the
release's behalf: `GITHUB_TOKEN`, scoped to `seanb4t/codegraph-go`. This phase adds a
second: a GitHub App installation token scoped to `seanb4t/homebrew-tap` alone.

- **Decision: `add-alongside`, and deliberately NOT `promote`.** The generalization is
  the trap here. Unifying the two behind one "release credential" would produce a
  single token able to write both repositories — which is exactly what ROADMAP
  criterion 5 forbids and what D-16 rejected a classic PAT for. The two credentials
  are different *because* their scopes differ; that difference is the feature.
- **The invariant test that encodes it** (the companion this checkpoint suggests, and
  accepted): plan 03-03's workflow-scoping shape test, which asserts each credential
  appears only in the job entitled to it and independently re-checks that
  `id-token: write` is still held by exactly one job. That test goes red the instant
  a future change collapses the two credentials or widens either one's reach.
</assumption_delta_decision>
