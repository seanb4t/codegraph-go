<objective>
Publish, twice, and then find out whether any of it is true.

Purpose: three of this phase's five criteria are statements about a published release
and cannot be observed anywhere else. Criterion 1 is stricter than that — it asks for a
cold install verified "at least one release later, against a cask GoReleaser
regenerated rather than the one hand-checked at first publish", because a cask that
works on the day someone watched it being made proves the maker's attention, not the
mechanism. D-13 satisfies that by cutting two releases inside this phase rather than
waiting on external cadence, which makes the second release's releasable commit a
planning problem, not a discovery to be made at the tail. It is named below.

Criterion 4 is the one that has to be handled honestly. Its release-integrity half is
executed evidence and always was — the existing post-release verification re-downloads
published assets and re-verifies every supply-chain claim on every release. Its
failure-and-recovery half is not. D-18's original mechanism was falsified against the
pinned module's own source before any plan was drawn over it, and the maintainer chose
a structural argument with no executed evidence rather than a rehearsal harness. That
decision is accepted and its cost is named: it leaves a check that has never been
observed to fire, which is this repository's own recurring failure mode. This plan
records it as an argument and says so in the words it uses.

Two rules govern behaviour when something goes wrong here, both inherited: release
automation is the sole tag authority, so no version tag is ever created by hand; and a
published release or tag is never deleted or re-pushed — recovery is patch-forward, a
new version.

Output: two published releases, a cold install verified against the second, and an
evidence record in which an argument and an observation are distinguishable at a glance.
</objective>

1. **BREW-01 / unclassified / unresolved** — probe text: "unclassified — review
   manually." Manual review: the probe engine has no category for "a package manager on
   a machine nobody controls resolves a tap and installs a binary." The substantive
   assumption is that one cold install, on one macOS version, on one architecture,
   generalises to "works on a clean machine" — which is what BREW-01 claims. It does
   not automatically: the verification available to this phase runs on Apple Silicon
   with a `/opt/homebrew` prefix, and the Intel `/usr/local` prefix, a custom prefix and
   any linuxbrew case are unexercised. Consequence if wrong: an install path that works
   for the maintainer and fails for a class of users, with nothing red. Carried, not
   resolved. The compensating controls are that the post-install hook's own assertions
   run on every user's machine and fail loudly there rather than silently, and that the
