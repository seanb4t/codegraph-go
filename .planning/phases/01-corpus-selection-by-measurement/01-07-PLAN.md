<objective>
Turn the measurement record into a guard that keeps holding, and wire the corpora into CI with
a per-corpus cache whose miss path falls through to a real fetch.

Purpose: D-07 makes the record re-runnable rather than frozen once, and D-08 splits the cost by
trigger — a cheap check on every run against the committed record, and a re-index-and-diff leg
only when the pin manifest changes. FIXT-02 criterion 5 requires a CI run to restore the
corpora from cache with a miss falling through to a fetch rather than to a skip. This is also
the repository's FIRST use of a caching action anywhere, so there is no in-repo precedent for
the mechanic — only for the pinning style.

Output: the coverage guard, three Taskfile targets, one new step in the existing CI test job,
and a new path-filtered sibling workflow modelled on `linux-cross-canary.yml`.

The guard is written so that bumping a pinned SHA in a way that kills `type_of` coverage fails
loudly instead of passing silently. That is the whole point of D-07, and it is the reason the
positive-count assertions below are not optional decoration.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions cache → CI workspace | A restored cache entry becomes a corpus tree the indexer reads and the drift guard measures |
| Manifest matrix output → workflow step environment | Manifest-derived repository and SHA values cross into a job's environment and then into the fetch target's shell |
| Third-party caching action → this repository's CI | The first use of a caching action anywhere in this repository |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-07-01 | Tampering | GitHub Actions cache poisoning | medium | mitigate | Cache keys are content-addressed by repository slug and pinned commit, and no prefix-fallback key list exists, so a restored entry can only ever be the tree for the exact pinned commit. The unconditional assertion step independently re-verifies the restored tree's checked-out HEAD against the pinned SHA, so a poisoned or stale entry fails the job rather than being indexed. This repository's CI triggers on pull request and push to the default branch, never on the fork-writable trigger variant, so no cross-trust-boundary cache write path is introduced.
