<objective>

Purpose: D-07 makes the record re-runnable rather than frozen once, and D-08 splits the cost by

## The guard derives the claim; it does not validate a summary

An earlier draft had `CheckCoverage(rec)` read a stored `coverage[kind]` map and compare each
entry against a threshold. **Nothing in that design required the claimed supplier to be locked,
to have actually been measured, or to match its own raw measurement.** A summary naming a
repository that was never locked, or citing a count higher than that repository's observation,
would have passed — the central claim of the whole phase could drift internally while the guard
stayed green. That is rule `84d1gfpywd` again in its subtler form: not a guard that checks
nothing, but a guard that checks the wrong artifact.

`CheckCoverage` now takes all three documents and reconstructs the claim from first principles:

1. load and validate `corpora/manifest.json`;
2. derive the locked `repo@sha` identities from it;
3. require EXACT set equality with `corpora/selection.json`'s locked set;
4. require every locked identity to have an observation in `corpora/observations.json`;
5. compute, per kind, the best count across those observations and which repository supplied it;
6. apply the selection's thresholds to the DERIVED counts;
7. require `syntheticKinds` to be empty.

There is no stored supplier field to trust, so step 5 cannot disagree with the evidence — it *is*
the evidence. Plan 01-05's prose renderer derives its supplier column the same way for the same
reason.

## Cache mechanism — a corrected premise, and the decision it forces

**CONTEXT.md D-13, RESEARCH.md and PATTERNS.md all state that this phase introduces the
repository's first CI caching. That is false, and the plan corrects it rather than inheriting
it.** All three reached that conclusion by grepping for the literal vendor string `actions/cache`,
which genuinely has zero hits. Enumerating every `uses:` line instead shows the repository
already caches in **nine** places:
`namespacelabs/nscloud-cache-action@c5f8dab7560444c4bf8dbc64f1b203431873c547 # v1.6.1`, with
`cache: go`, at `ci.yml` lines 60, 203, 232, 356, 386, 415 and `bench.yml` lines 112, 374, 473 —
always paired with `actions/setup-go` carrying `cache: false`. This is a **locked maintainer
decision** (v1.0 Phase 10 D-06), not an open field.

**Decision: use the established mechanism — option (a).** Verified against its actual interface:
the Namespace action takes `cache`, `detect`, `path`, `fail-on-cache-miss`, `github-token` and
the spacectl inputs, and emits a `cache-hit` output. **It has no `key` input at all** — it mounts
a persistent NVMe volume with no upload or download phase. That looks disqualifying for D-13's
"one entry per corpus keyed `repo@sha`", and is not: **the corpus destination path already embeds
the pinned SHA** (`Entry.Dir`, Plan 01-04), so each corpus occupies its own content-addressed
subdirectory and a pin bump produces a *new path*, absent by construction and therefore fetched.
There is no prefix-matching feature to disable because there are no keys.

**D-13's stated premises do not survive and are not carried forward as fact.** Its "GitHub gives
a repo 10 GB of total cache with LRU eviction" justification describes **GitHub's** cache service;
this workflow runs on `namespace-profile-linux-amd64-4x8`, the same runner class as `ci.yml`'s
`test` job, where the cache is a provisioned volume. What survives is D-13's real intent —
content-addressing, and a miss that fetches rather than skips — and both hold.

**What this avoids:** a second, differently-shaped caching mechanism beside nine instances of an
established one, on runners where its behaviour is an open question, silently overriding a locked
decision. It also means this phase adds **no new supply-chain surface**: the action and its pin
are already trusted in nine places.

**But a persistent volume is MUTABLE**, which makes the integrity check below load-bearing rather
than belt-and-braces — see `T-01-07-01`.
</objective>
