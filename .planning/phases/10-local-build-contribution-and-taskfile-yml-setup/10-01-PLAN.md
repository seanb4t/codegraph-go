<assumption_delta_decision>
**Noun that is now primary:** the *command definition*. Before this phase there were N definition sites (one `run:` body per CI step) and no local one; after it there is exactly one (`Taskfile.yml`) and the workflow steps are demoted to invocation sites.

**Decision: `promote`.** `Taskfile.yml` becomes the primary definition site and the workflow `run:` bodies become detail of one caller. This is not `add-alongside` — a Taskfile that mirrors the workflows while the workflows keep their own bodies is exactly the drift-guard design D-01 rejected.

A second, smaller pluralization also occurs: the *tool module* goes from zero/one to two (`go.tool.mod`, `go.tool-lint.mod`). That one IS `add-alongside`, and deliberately so — D-03 measured that merging them does not compile. The accepted debt is that a future third tool needs a placement decision; the header comment in each modfile is what forces that decision to be made consciously.

**Invariant test suggested and taken:** `TestWorkflowRunBodiesInvokeTask` (plan 10-07) encodes the generalized intent — it goes red the instant a workflow step reintroduces its own command body.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Go module proxy -> CI runner | Tool binaries (`task`, `goreleaser`, `actionlint`) are fetched and compiled from an external registry into the environment that gates this repo |
| Third-party GitHub Action -> workflow job | `namespacelabs/nscloud-cache-action` executes with the job's token and can read/write the cache volume |
| Namespace runner infrastructure -> repo secrets/token | Job execution moves off GitHub-hosted infrastructure to a third-party runner provider |
| Cache volume -> build | Restored Go module/build cache contents are consumed by later build steps |
