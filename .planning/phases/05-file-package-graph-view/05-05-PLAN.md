<objective>
Make the two things GRF-04 and GRF-02 actually promise true in the rendered view:
dependency cycles a developer does not have to hunt for, and aggregated edges whose
per-kind counts can be read.

The tracer proved the composition and 05-04 proved it holds at scale. What it does
not yet do is answer the two questions the requirements are written around. A cycle
that is technically present in the element data but indistinguishable on screen is
not "visually distinguished"; and edges that carry per-kind counts nobody can read
are not "aggregated with per-kind counts" in any sense a developer benefits from.

The cycle answer has two halves and both are required. Styling makes a cycle legible
once you are looking at it; a stated count and a control that brings the next cycle
into view is what removes the hunting. On a 3,233-node graph, styling alone leaves
the developer scanning — which is precisely the failure GRF-04's wording rules out.

Everything a cycle class expresses came from the server (D-06). This plan copies wire
fields onto element data and styles them. It computes nothing.

Purpose: turn two requirements from data present to information legible.
Output: cycle styling and cycle discoverability, an edge detail view built on the one
shared table, and a rebuilt committed bundle.
</objective>
