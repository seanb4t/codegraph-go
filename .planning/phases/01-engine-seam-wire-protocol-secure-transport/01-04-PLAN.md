<objective>
Extract the structured `NodeDetail` and `ExploreResult` seams from `internal/query`,
leaving `Node()` and `Explore()` byte-identical.

Purpose: the UI must be a third consumer of `internal/query.Engine`, never a second
implementation of it. Eight of the Engine's ten read methods already return structured
results; `Node` and `Explore` are the two that return rendered markdown. Both already
compute structured intermediate data before rendering —
`fetchCalls`/`fetchCalledBy` for Node, and the `groups`/`symbolCount`/`blasts`/`sources`/
`skeletonFiles` assembly for Explore. This plan exposes those pieces as new methods that
stop BEFORE the existing render call. It is an extraction, not a rewrite: a rewrite that
re-derives the same data is how a second implementation of the query engine gets born,
and the extraction is only cheap while it stays an extraction.

Almost every browse and inspect requirement in Phases 3-6 depends on these two methods,
and the ROADMAP forbids planning any UI view work before they land and are independently
proven golden-clean.

Output: `NodeDetail`, `ExploreResult`, one gather path per shape, and a recorded
mutation-proof that the goldens can actually detect a break.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied file path → `readSourceFile` | `Node`'s file mode, the multi-definition path and `Explore`'s group sources all take a path that ultimately originates from a CLI argument, an MCP tool call, or (from Phase 3) a browser. `resolveSourcePath` is the single confinement gate. |
| indexed graph → rendered output | Node and edge content originates from third-party source trees and is rendered into markdown consumed by agents and humans. |
