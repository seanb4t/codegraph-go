<objective>
Give the graph a commit identity, and give that identity a real path out of
`internal/query` to the wire.

Purpose: `schema.Meta` records no commit SHA today. A GitHub permalink that matches what
the UI just showed must point at the *indexed* commit, not at whatever HEAD happens to be
when the link is clicked — so `BRW-09` in Phase 3 is gated on this field existing. It is
sequenced here, with the protobuf work, so it inherits the same additive-only discipline
(D-02a) rather than being invented alongside a UI feature.

The field alone is not enough, and the first review of this phase caught why. `Engine.Status`
returns a `StatusResult` projection that has no commit field; `Engine.reader` is unexported;
`graphstore.Reader.GetMeta()` is unreachable from `internal/uiserver`; and a second
in-process `graphstore.Open` on the same directory is lock-refused. Adding the field
without adding an accessor would leave plan 01-09's "the Status response carries the commit
SHA" unachievable. So this plan ships both halves: the field, and
`(*Engine).IndexMeta` — an accessor that reads the metadata the Engine already reads,
placed deliberately outside `status.go` so D-06's "the CLI stays untouched" stays true and
visibly so.

Output: `Meta` field 8, one HEAD resolution per operation threaded to all three write
sites, an exported metadata accessor, and a recorded proof that `codegraph status`'s bytes
did not move.
</objective>

  <context>
    **Autonomy note, recorded because the cross-AI review flagged it.** 01-CONTEXT.md's
    D-05 already locks the number, the type, the name and the precedent. This checkpoint
    therefore adds no new information and costs one blocking pause. It is kept anyway for
    one reason and one only: the field number is permanently unrecoverable once a build
    stamps it into a real store, and `REVERSIBILITY_GATES` is enabled precisely so that
    class of decision gets a human eye before it ships. If you have no change to make,
    reply "proceed" — that is the expected answer.

    What is being locked:

    - **Field number 8 is spent permanently.** Once a build stamps it into a real store,
      no future schema change may reuse 8 for anything else, and no future change may
      renumber it. If this turns out to be the wrong field, the only correction is
      `reserved 8;` plus a new number.
    - **Type is `string`, not `bytes`.** A lowercase hex object ID — 40 characters under
      Git's SHA-1 object format, 64 under SHA-256. Both lengths are accepted, because a
      40-only check would silently record an ABSENT commit on a SHA-256 repository and the
      permalink would just quietly stop working with no error anywhere. Chosen for
      legibility in decoded output and direct use in a GitHub permalink without
      re-encoding. A `bytes` field would be half the size but would need encoding at every
      read site, and would have to carry the object format out of band to be decodable.
    - **Absent means a pre-upgrade graph**, matching `has_file_index`'s precedent exactly.
      An empty string is indistinguishable from absent in proto3, and that is deliberate:
      both cases degrade the same way.
    - **No `SchemaVersion` bump.** `internal/schema/meta.go` states that a well-formed
      additive change never requires one.

    Alternatives considered and rejected: a separate `meta/commit` key outside the `Meta`
    record (invents a second staleness mechanism and a second read path); storing the full
    `git describe` output (not stable, not permalinkable); deferring the field until Phase
    3 needs it (would land it beside a UI feature instead of inside the schema discipline,
    which is the sequencing the ROADMAP explicitly chose against).
