<objective>
Bound every response and make the degraded states legible.

Purpose: `connect-go` defaults to unlimited on both send and receive, so RPC-05 is
satisfied by no default and must be built. But the transport limit rejects rather than
truncates — it returns `CodeResourceExhausted` — which prevents an unbounded response
without delivering a bounded one. So RPC-05 needs two independent layers: application
truncation that still hands the client usable content it can render as "showing first N of
M", and a transport backstop strictly above it that catches the case where application
truncation was missed.

And SRV-04's degrade path does not exist today. `Engine.Status()` runs only after a
successful `Engine` construction, and `query.OpenAt` fails outright when the store is
locked past `graphstore.Open`'s retry budget — so `Status()` never even runs in the exact
case the requirement describes. This is new plumbing at the RPC layer, not a reuse of an
existing fallback.

Output: rune-safe two-tier truncation with explicit totals, a typed `IndexingInProgress`
degrade, and a `Status` that answers precisely when things are wrong.
</objective>

  <reversibility rating="one-way">Under D-02a's additive-only discipline, `SourceBlob`'s field numbers can never be renumbered or reused once shipped.   <decision>Lock `SourceBlob`'s six-field shape and its field numbers 1 through 6: truncation is signalled by explicit response fields carrying both totals and both returned counts, never by an error (D-11, D-12, RPC-05).</decision>
  <context>
    Confirm before writing: truncation is signalled by explicit fields on a `SourceBlob`
    message, never by an error, and the field set is locked now.

    What is being locked:

    - **`SourceBlob` carries six fields**: `bytes content = 1`, `bool truncated = 2`,
      `int64 total_lines = 3`, `int64 total_bytes = 4`, `int64 returned_lines = 5`,
      `int64 returned_bytes = 6`. Both totals AND both returned counts, in both units, so
      the client can render "showing first N of M lines" without recomputing anything and
      without having to guess which unit the cap fired on.
    - **Field numbers 1 through 6 are spent permanently** in this message. No future change
      may renumber or reuse them.
    - **Truncation is never an error.** `CodeResourceExhausted` was considered and rejected:
      it prevents an unbounded response but does not deliver a bounded one, and RPC-05
      literally asks for a response that "comes back bounded and explicitly marked
      truncated". The client still gets usable content.
    - **Two units, both reported.** The line cap is primary because it matches how a human
      reads a file; the byte cap is secondary because a minified single-line file blows any
      byte budget at one line. Reporting only one unit would make the other cap's firing
      invisible.
    - **Every Phase 3 through 6 source view reads these fields**, which is what makes the
      semantics costly to change later even though the field numbers are the strictly
      one-way part.

    Alternatives considered and rejected: byte-range paging (rejected for RPC-05 in favour
    of line-capped truncation; it would change what Phase 3's viewer must build); a single
    combined `truncated_reason` enum instead of two unit pairs (loses the totals the client
    needs to render the count); returning `CodeResourceExhausted` (above).
  </context>
