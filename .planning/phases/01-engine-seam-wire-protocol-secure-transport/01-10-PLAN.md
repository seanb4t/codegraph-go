<objective>
Bound every source blob leaving the process, in two units, on a rune boundary, explicitly
marked — and put a transport backstop above it that never fires on correct output.

Purpose: `connect-go` defaults to unlimited on both send and receive, so RPC-05 is
satisfied by no default and must be built. But the transport limit rejects rather than
truncates — it returns `CodeResourceExhausted` — which prevents an unbounded response
without delivering a bounded one. So RPC-05 needs two independent layers: application
truncation that still hands the client usable content it can render as "showing first N of
M", and a transport backstop strictly above it that catches the case where application
truncation was missed.

The details that look cosmetic are the ones that become permanent. `SourceBlob`'s field
numbers can never be reused; where the blob attaches to `ExploreResponse` decides whether
the group-to-source association survives; whether the content field is `bytes` or `string`
decides what happens to a source file that is not valid UTF-8; and what "line count" means
for an unterminated final line is a number every Phase 3 through 6 view will render. All
four are settled in the checkpoint below, before anything is written, because after it they
are contract.

Output: a shared rune-boundary helper, two-tier truncation with explicit totals in both
units, and a transport backstop asserted to sit above the application cap.
</objective>

  <name>Checkpoint: `SourceBlob`'s shape, its attachment points, and its counting semantics are one-way</name>
  <reversibility rating="one-way">Under D-02a's additive-only discipline, `SourceBlob`'s field numbers and its attachment field numbers on three messages can never be renumbered or reused once shipped. The semantics are additionally costly to reverse: every Phase 3 through 6 source view reads these fields, so changing what they mean later means touching every view.</reversibility>
  <decision>Lock `SourceBlob`'s six-field shape and numbers, its three attachment points, the `bytes` content type with its scoped UTF-8 guarantee, and the exact line-counting rule (D-11, D-12, RPC-05).</decision>
  <context>
    **Why this checkpoint is substantive, unlike plan 01-06's.** 01-CONTEXT.md's D-11 and
    D-12 lock the PRINCIPLE — a line cap primary, a byte cap underneath, truncation
    signalled by an explicit field and never by an error. They do not lock the field set,
    the numbers, the attachment points, the content type, or the counting rule. All five of
    those are new decisions being made here, and four of them are permanent. This is not a
    reconfirmation.

    What is being locked:

    1. **`SourceBlob` carries six fields**: the content, a truncated flag, the true total in
       lines, the true total in bytes, the returned count in lines, and the returned count
       in bytes — numbered 1 through 6 in that order. Both totals AND both returned counts,
       in both units, so the client can render "showing first N of M lines" without
       recomputing anything and without having to guess which unit the cap fired on.
       Numbers 1 through 6 are spent permanently in this message.

    2. **Three attachment points, at the numbers plan 01-09 already reserved**:
       `GetNodeDetailResponse` (the single-definition shape's source),
       `NodeDefinition` (each gathered candidate's own source), and `ExploreGroup` (each
       group's own source). The `ExploreGroup` placement is the load-bearing one:
       `ExploreResult.Sources` is a `map[string][]byte` keyed by group path, so a single
       response-level blob would lose which file each blob belongs to and a parallel
       unkeyed list would make the association positional. Plan 01-09 already reserved and
       commented all three numbers, and plan 01-09's known-number fixture already pins
       them, so approving this locks numbers that are already visible in the tree rather
       than numbers that do not exist yet.

    3. **Content is `bytes`, and the UTF-8 guarantee is SCOPED, not universal.** A proto3
       `string` field requires valid UTF-8 and fails to marshal otherwise, so a single
       oddly-encoded file anywhere in an indexed repository would turn an ordinary source
       view into a server error. Indexed source is not guaranteed valid UTF-8. So the field
       is `bytes`, and the guarantee the contract makes is the one it can keep: *if the
       input was valid UTF-8, the output is valid UTF-8, because the byte cut never splits
       a rune.* A universal "this is always UTF-8" guarantee alongside a `bytes` field
       would be a contract the server cannot honor.

    4. **Line counting is defined exactly**: the count is the number of newline characters
       in the input, plus one when the input is non-empty and does not end in a newline. So
       empty input is 0 lines; a lone newline is 1; `a\nb\n` is 2; `a\nb` is 2. This rule
       is applied identically to the total and to the returned count, and it lives in one
       named helper referenced from both. Leaving this undefined would mean every Phase 3
       view renders a subtly different "of M".

    5. **Truncation is never an error.** `CodeResourceExhausted` was considered and
       rejected: it prevents an unbounded response but does not deliver a bounded one, and
       RPC-05 literally asks for a response that "comes back bounded and explicitly marked
       truncated". The client still gets usable content.

    Alternatives considered and rejected: byte-range paging (rejected for RPC-05 in favour
    of line-capped truncation; it would change what Phase 3's viewer must build); a single
    combined truncation-reason enum instead of two unit pairs (loses the totals the client
    needs to render the count); a `string` content field (above); counting an unterminated
    final line as zero (would make `a\nb` report 1 line while returning 2, which no client
    could reconcile).
  </context>
