<objective>
Turn the tracer's single file view into the phase's actual browsing motion: open a symbol,
see its source with its callers, callees and blast radius, click any of them, and keep
going — with every state you reach addressable and every step walkable by back and
forward.

The history rule is the design. Navigation pushes; refinement replaces. Opening a node,
clicking a neighbour and picking a search result are places a developer wants to come
back to. Typing in search and dragging a depth control are not — but the URL must still be
correct and shareable at every instant of them. That is what "walk that history correctly"
actually asks for.

The mechanism matters as much as the rule. SvelteKit exports two different things that
both touch history, and only one of them updates the reactive URL the view reads. This
plan uses `goto` with its own `replaceState` option; a plan built on the other pair would
produce history entries whose URLs never change, passing a naive "an entry was created"
check while failing NAV-01 outright.

Purpose: BRW-03's click-through is the phase goal's own wording — keep clicking outward
without losing their place — and NAV-01's parameter shape is what Phase 4's workbench
deep-links against, so it is settled here.

Output: a navigation module, a neighbours panel, and the extension of the load seam to
symbol targets and blast radius.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shared URL -> `depth` / `limit` reaching traversal RPCs | A link authored by someone else controls how much graph traversal the server performs |
| shared URL -> `symbol` / `file` reaching `GetNodeDetail` | The same attacker-influenceable target path as the tracer's, now reachable from more call sites |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-27 | Denial of Service | a crafted link with an extreme `depth` or `limit` | high | mitigate | The values are passed through unchanged to the server, whose existing `validateDepth`/`clampDepth`/`validateLimit`/`MaxLimit` refuse or bound them for every caller; the client adds no second copy of the bound, so there is no path where a client-side clamp lets a value through that the server would have refused |
| T-03-17b | Tampering / Information Disclosure | `file` target reaching `GetNodeDetail` from neighbour clicks | high | accept | Same server-side confinement gate, already proven at this boundary by plan 03-02; neighbour targets originate from the server's own `Location` results and are re-validated by the same gate on the way back in |
| T-03-28 | Spoofing | a shared link reconstructing a different view than its author saw | medium | mitigate | One serializer and one parser, round-trip asserted; no client-side clamping or defaulting, so the receiver's request is byte-identical to the sender's |
</threat_model>
