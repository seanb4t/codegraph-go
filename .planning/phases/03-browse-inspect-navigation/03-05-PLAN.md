<objective>
Add the one new RPC this phase introduces: `GetPermalink`, which turns a repository path
and a line (or line range) into a GitHub permalink pinned to the commit the index was
built at.

The server owns all of it — remote-URL derivation, `url.<base>.insteadOf` expansion,
GitHub detection, and the pushed-commit hint — because the browser cannot read
`.git/config` and because only the server can say "this commit is in no remote-tracking
branch, so this link may 404", which is BRW-09's actual failure mode. A static template
string is a pure formatter; it can say where a file WOULD live but cannot express that.

This is also where SRV-05 meets the new endpoint. `GetPermalinkRequest.path` is a
client-steerable filesystem path, so it goes through the same confinement gate
`GetNodeDetail` uses — reused, never reimplemented — and that reuse is proven at the RPC
boundary with a passing control alongside the refusals.

Purpose: BRW-09 is what makes a truncated local view usable (D-20) and what makes a
shared observation checkable by someone else. Getting the uncertainty honest is the whole
design: for a local dev tool, the indexed commit is very frequently an unpushed local
commit, so the expected failure is ordinary daily use, not an edge case.

Output: an additive proto method and its messages, a `internal/gitmeta` remote/pushed
derivation layer following that package's existing degrade-to-empty contract, a
`internal/uiserver` handler, and tests covering every branch.
</objective>

**Cycle-1 review raised this decision to HIGH and it is now the first thing to settle
here.** The cycle-1 plan was internally contradictory about git failures in three places
at once: the artifact table declared `CommitOnRemoteTrackingBranch(...) (bool, error)`;
Task 2 said "every function degrades to its zero value on any failure — never to an

cannot execute. Those three cannot all be true. If the error is swallowed into a bare
`false`, the handler cannot distinguish "I checked and the commit is on no remote-tracking
branch" from "I could not check at all" — and D-07 requires exactly that distinction,
because the first is ordinary daily use for a local dev tool and the second is not a
statement about the link at all.

This revision resolves it by construction, and the resolution is presented below as the
recommended option rather than left open: the git layer returns a TRI-STATE
(`RemotePresenceUnknown` / `Observed` / `NotObserved`) and a STRUCTURED remote
(`GitHubRemote{Owner, Repo, Host, Reason}`), so "could not check" and "checked, not there"
are different values that survive all the way to `availability` and `reason`. Errors are
still not returned to the caller — the degrade-to-a-value contract this package already
keeps is preserved — but the VALUE degraded to now carries which degrade happened. That
is the difference between swallowing an error and recording it.

The maintainer may still overrule this. What they may NOT do is leave it unresolved: this
is a permanently published RPC shape, and `availability`/`reason` are the fields that
either can or cannot express the distinction, forever.

`RemoteURL(ctx, dir)` reads the remote URL via git's own URL-expansion subcommand — the
one that applies `url.<base>.insteadOf` rewrites and, per git's own documentation, exits
WITHOUT talking to the remote. Do not use the plain remote-config read: it returns the
unexpanded value, so a developer with an `insteadOf` rewrite configured would get a
different answer from this function than git itself uses.

`RemoteGitHubRepo(ctx, dir)` parses that URL and returns a `GitHubRemote` struct, not a
bare `(owner, repo)` pair. Handle the three transport shapes real repositories use: a URL
with a scheme, the scp-like `user@host:path` form, and a bare path form. Compare the host
to the literal `github.com` by exact equality. Do not use substring, prefix or suffix
matching: this project already closed a DNS-rebinding class by exact-match allowlisting,
and a host-suffix match here accepts an attacker-controlled lookalike host as if it were
the real forge.
