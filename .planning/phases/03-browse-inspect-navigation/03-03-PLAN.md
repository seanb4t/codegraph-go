<objective>
Resolve the `TestFrozenTranscriptsMatch/toolslist-repeat` ordering flake folded into
this phase from `.planning/todos/pending/2026-08-07-wire-oracle-toolslist-repeat-response-ordering-flake.md`.

This is unrelated work riding along. It touches neither `web/` nor `internal/uiserver`,
depends on no Browse-view task, and **must not gate this phase's five browse success
criteria**. Its verdict is reported separately.

The observed failure: line 2 of the normalized transcript held the id-3 response where
the id-2 response belonged. Tool payloads matched exactly. The scenario's own comment
(`test/wireoracle/scenarios.go:559-563`) asserts this cannot happen because both calls
are `tools/list` and therefore handled synchronously in request order. The evidence
contradicts that comment. Either the claim is wrong about the server, or it is true of
the server but not of the transcript reader — and the current evidence does not
distinguish them.

Purpose: this gate is a required PR leg that was never relaxed. An intermittent failure
there blocks merges at random AND trains people to treat a red blocking gate as a
re-run prompt.

Output: a recorded root cause, a reproduction that goes RED before the fix, and a fix
that leaves the oracle's discriminating power intact.
</objective>
