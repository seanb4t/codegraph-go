<objective>
Complete the source pane: jump from a reference to its definition, disambiguate a bare
name without guessing, copy an identifier in one action, and reach the rest of a truncated
file on the remote.

Click-to-definition has exactly one viable shape this phase, and that was checked rather
than assumed. `SourceBlob`'s reserved band anticipates syntax-highlight spans, but the
store cannot enumerate call sites at all: the Pebble edge key omits line and column, so
two call sites between the same source, kind and target collapse into one stored edge.
Server-side resolved reference spans would need a storage key-shape change, far outside
this phase. So resolution is text-driven — an identifier is clickable only when its text
matches a name already on the wire in the opened node's call list — and BRW-05's picker
exists in the same phase precisely because text-driven resolution is inherently ambiguous.

The truncation and permalink halves complete each other. The local view is bounded by
design (there is no pagination RPC and this phase does not add one, because a ranged
source fetch would be a second bounded-read path). The remote view is the unbounded one.
Two requirements specified separately turn out to be one feature.

Purpose: this is criterion 2 of the phase in full, plus the client half of criterion 3.

Output: a pure identifier-matching module, the completed source pane, the disambiguation
picker, and the copy affordance.
</objective>

  <action>
Create `web/src/lib/call-targets.ts`.

Build the index keyed by the node name string exactly as the wire supplied it, with the
value a list so a name matching several call targets is representable rather than
silently collapsed — that ambiguity is real and the picker is what handles it.

Matching is exact string equality. Do not lowercase, do not apply Unicode normalization,
do not strip anything, and do not fall back to a prefix or fuzzy comparison. The wire's
name and the source text either agree or they do not; anything looser produces click
targets that jump somewhere the developer did not point at, which is worse than an
identifier that is simply not clickable.

Export the identifier tokenizer as a named pattern using Unicode property escapes so a
non-ASCII identifier is one token. An ASCII-only pattern would split such an identifier at
its first non-ASCII code point and then match a fragment of it, producing a click target
on part of a name.

`decorateCallTargets(root, index, onSelect)` walks the rendered fragment's TEXT NODES with
a tree walker, tokenizes each, and replaces a matched token by constructing elements and
text nodes through DOM APIs. It must never assemble a markup string and never assign one
to any HTML-string property or method. The input here is verbatim, occasionally
adversarial repository content; the client has exactly one escaping path and this must not
become a second markup producer. Constructing nodes through the DOM makes the escaping
question not arise at all.

Give each produced element an accessible activatable role and a keyboard activation path,
not a bare click handler on a span — a jump-to-definition affordance that only responds to
a mouse fails NAV-03's spirit inside the very pane the phase is about.

**Lifecycle, which cycle-1 left unspecified (Codex, MEDIUM).** `decorateCallTargets`
returns a TEARDOWN function that removes every listener it attached and restores the
subtree to its pre-decoration text content. Wrap it in a Svelte action, `callTargets`,
exported from this same module, with `update` (re-decorate when the index or the rendered
source changes) and `destroy` (run the teardown). The source pane applies the action to
the element it renders highlighted markup into, rather than calling the decorator from an
effect. A Svelte rerender destroys and recreates the decorated nodes; a decorator with no
teardown leaks a listener per rerender, and re-running it without cleanup nests one
wrapper element inside the last one until a token is buried several levels deep.

Make the decorator IDEMPOTENT independently of the action, not only in practice through
it: mark decorated elements (a data attribute is enough) and skip anything already marked.
The action makes double-application unlikely; idempotence makes it harmless. Both are
tested.

**The split-identifier bound, stated rather than discovered (Codex, MEDIUM).**
highlight.js can place parts of one qualified identifier in separate sibling elements —
a package qualifier styled differently from the member it qualifies. A TreeWalker
tokenizing each text node independently cannot see across that boundary, so such a name
produces no click target. Do NOT try to reassemble text across element boundaries to fix
it: reassembly means deciding where a "logical" token begins across arbitrary markup, and
getting that wrong produces a click target spanning DOM the user did not point at —
worse than an identifier that is simply not clickable, which is the failure this design
already accepts everywhere else. Document the bound in the module's doc comment and pin
it with the `<behavior>` test above, so the next person meets it as a decision.

Write `web/tests/call-targets.test.ts` first covering every case in `<behavior>`. For each
NEGATIVE matching case, assert in the same block that the exact-match case DOES hit, so
the non-match assertions are proven to be running against a populated index rather than an

## Deferred with reason: client-side performance validation

Cycle-1 review (Codex, cross-plan MEDIUM; uncontradicted by the other lane) observed that
this phase plans no measurement for three client-side costs: rendering and highlighting a
source blob at the server's truncation cap, rendering hundreds of callers/callees, and the
DOM cost of a large search result list. This plan is where two of those three land, so the
disposition is recorded here.

**Deferred to a follow-up todo, not incorporated.** The reasons, in order of weight:

1. **No requirement in scope asks for it.** This phase's fourteen requirement IDs are all
   behavioural. Adding a performance budget now would mean inventing the threshold as well
   as the measurement, and a budget nobody agreed to is a gate that gets relaxed the first
   time it is inconvenient — the failure mode this phase's own prohibitions are written
   against.
2. **The dominant cost is already bounded server-side, and that bound is tested.**
   `internal/uiserver/truncate.go`'s line-then-byte cap (RPC-05) bounds every `SourceBlob`
   before it leaves the server, and `validateLimit`/`MaxLimit` bound result counts. The
   client renders what it is given. The unbounded-input version of this risk does not
   exist on this wire.
3. **The remaining risk is real but is a Phase 4 concern.** Highlighting a capped blob and
   decorating it is O(source length) on the main thread; hundreds of neighbour entries is
   a list-virtualization question. Both are worth measuring against the workbench's denser
   views rather than against this phase's single-pane one.
