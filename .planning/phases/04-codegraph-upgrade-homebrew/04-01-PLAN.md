<objective>
Teach `codegraph upgrade` to recognize a Homebrew-managed install from the resolved
location of its own binary, refuse the mutation with an actionable pointer, and step
aside under `--check` — all before any network call.

Purpose: neither install path may lie about what is installed. A brew-managed binary
that self-replaces leaves Homebrew's own receipt describing a version that is no longer
on disk (UPGR-01). Detection must be structural and prefix-agnostic so it is correct on
every Homebrew prefix rather than only the one this machine happens to use (UPGR-02),
and the read-only path must stay read-only (UPGR-03).

Output: `internal/upgrade/brew.go` (detection + the shared pointer message),
`internal/upgrade/brew_test.go` (the constructed-tree table including the executing
false-positive rows), one new early branch in `Run()`, and three seam-based `Run()`
tests alongside the existing ones.

Placement is fixed by D-12: the new file pair lives in `internal/upgrade`, not a new
`internal/brew` package and not `internal/cli/upgrade.go`. `internal/upgrade` already owns
install-shape knowledge (`checkWritable`, `atomicSwap`, `releaseAssetName`), and putting the
guard anywhere above `Run()` would leave `upgrade.Run()` willing to download and swap over a
Caskroom when called directly — outside the seam that enforces everything else, and out of
reach of D-08's proof.
</objective>

<assumption_delta_decision>
**Detected signal:** `chosen` — "a custom prefix" in the phase scope (assumption-delta
scan, 2026-08-11).

**Noun now primary:** the **Homebrew prefix**. The generalized identity is "any prefix",
not `/opt/homebrew`.

**Decision: promote.** The general representation (an arbitrary, unnamed prefix derived
from the resolved path itself) is the primary and only representation the detector
carries. `/opt/homebrew`, `/usr/local`, a custom prefix and linuxbrew are demoted to
*rows in a test table*, never branches in the detector. There is deliberately no
prefix list, prefix constant, or prefix default anywhere in `brew.go` — the detector
locates the `Caskroom`/`Cellar` segment inside the resolved path and treats everything
to its left as the prefix, whatever it is.

**Rationale:** this is exactly what D-03 locks and what UPGR-02 requires; a
prefix-carrying representation alongside a prefix-agnostic one would be a second source
of truth that can disagree with the first. No accepted debt.
</assumption_delta_decision>

Implement `detectBrewManaged(targetPath string) (brewInstall, bool)`:
  1. Resolve with `filepath.EvalSymlinks(targetPath)`. **On error, return
     `brewInstall{}, false` immediately** — do NOT fall back to `targetPath` and do NOT
     continue scanning. An unresolvable path is "not detected", never an error that blocks
     a legitimate non-brew upgrade (RESEARCH Pattern 3, V5 in the security domain), and
     never a shape scan of a path we could not resolve. This is the single contract; it is
     the same statement threat T-04-03 makes, and Task 2 asserts it with a dangling-symlink
     row and a symlink-loop row. (Review cycle 1, MEDIUM: the earlier "fall back and
     continue" wording contradicted T-04-03 — the two differ observably when the
     *unresolved* path happens to contain a tree segment and a receipt exists beside it,
     which is exactly the attacker-shaped case. One contract, and it is the safe one.)
  2. Walk the ancestry ROOT-PRESERVINGLY. Do NOT split the path into segments and rebuild
     it with `filepath.Join`: for an absolute POSIX path like
     `/opt/homebrew/Caskroom/codegraph/0.8.0/codegraph`, splitting on `os.PathSeparator`
     yields a leading empty segment that `filepath.Join` discards, producing the RELATIVE
     path `opt/homebrew/...` — the receipt `os.Stat` would then resolve against the process
     working directory and detection would fail on every real install. (Review cycle 1,
     HIGH: this defect was in the prescribed algorithm.)

     Instead, start at `dir := filepath.Dir(resolved)` and walk upward with
     `parent := filepath.Dir(dir)`, stopping when `parent == dir` (the filesystem root —
     this termination condition is correct for `/`, for a Windows volume root, and for a
     UNC root alike). At each step, examine the CHAIN OF BASENAMES rather than indices:
     a candidate exists when, for some ancestor `treeDir`, `filepath.Base(treeDir)` is
     exactly `Caskroom` or `Cellar` AND `treeDir` has at least two descendant components on
     the path back down to `resolved` (`<token>` then `<version>`). Every path you build
     from here is derived by `filepath.Join(treeDir, ...)` or by retaining an ancestor value
     you already hold — never by re-joining split segments — so volume and root semantics
     are preserved by construction and no prefix string is ever materialised. Never compare
     the prefix against anything, never carry a prefix list, never special-case an operating
     system.
  3. For each candidate, build the receipt path the tree implies, joining onto the
     already-rooted ancestor paths held from step 2:
     Caskroom -> `<tokenDir>/.metadata/INSTALL_RECEIPT.json`;
     Cellar   -> `<versionDir>/INSTALL_RECEIPT.json`.
     Both locations were measured on a real Homebrew 6.0.16 install and confirmed against
     Homebrew's own `tab.rb`/`cask/metadata.rb` (RESEARCH § Summary).
  4. `os.Stat` the receipt. Existence is the whole check — do not import `encoding/json`
     and do not read any field out of it; the file's contents are a Homebrew-internal
     format with no third-party stability contract (RESEARCH Pitfall 2). If the stat
     fails, continue to the next candidate; if no candidate has a receipt, return
     `brewInstall{}, false`.
  5. On success return the populated struct with `InstallDir` set to the `<version>`
     directory value retained during the walk — an absolute path that was never
     decomposed — `Tree`/`Token`/`Version` set from the corresponding basenames, and
     `ResolvedBinary` set to the EvalSymlinks result. Assert this in review by checking
     that `filepath.IsAbs(InstallDir)` holds whenever the input was absolute.
