<objective>
Teach `codegraph upgrade` to recognize a Homebrew-managed install from the resolved
location of its own binary, refuse the mutation with an actionable pointer, and step
aside under `--check` — all before any network call.

Purpose: neither install path may lie about what is installed. A brew-managed binary
that self-replaces leaves Homebrew's own receipt describing a version that is no longer
on disk (UPGR-01). Detection must be structural and prefix-agnostic so it is correct on
every Homebrew prefix rather than only the one this machine happens to use (UPGR-02),
and the read-only path must stay read-only (UPGR-03).

Output: `internal/upgrade/brew.go` (detection + the shared pointer message),
`internal/upgrade/brew_test.go` (the constructed-tree table including the executing
false-positive rows), one new early branch in `Run()`, and three seam-based `Run()`
tests alongside the existing ones.

Placement is fixed by D-12: the new file pair lives in `internal/upgrade`, not a new
`internal/brew` package and not `internal/cli/upgrade.go`. `internal/upgrade` already owns
install-shape knowledge (`checkWritable`, `atomicSwap`, `releaseAssetName`), and putting the
guard anywhere above `Run()` would leave `upgrade.Run()` willing to download and swap over a
Caskroom when called directly — outside the seam that enforces everything else, and out of
reach of D-08's proof.
</objective>

<assumption_delta_decision>
**Detected signal:** `chosen` — "a custom prefix" in the phase scope (assumption-delta
scan, 2026-08-11).

**Noun now primary:** the **Homebrew prefix**. The generalized identity is "any prefix",
not `/opt/homebrew`.

**Decision: promote.** The general representation (an arbitrary, unnamed prefix derived
from the resolved path itself) is the primary and only representation the detector
carries. `/opt/homebrew`, `/usr/local`, a custom prefix and linuxbrew are demoted to
*rows in a test table*, never branches in the detector. There is deliberately no
prefix list, prefix constant, or prefix default anywhere in `brew.go` — the detector
locates the `Caskroom`/`Cellar` segment inside the resolved path and treats everything
to its left as the prefix, whatever it is.

**Rationale:** this is exactly what D-03 locks and what UPGR-02 requires; a
prefix-carrying representation alongside a prefix-agnostic one would be a second source
of truth that can disagree with the first. No accepted debt.
</assumption_delta_decision>

Implement `detectBrewManaged(targetPath string) (brewInstall, bool)`:
  1. Resolve with `filepath.EvalSymlinks(targetPath)`. On error, fall back to
     `targetPath` and continue — an unresolvable path is "not detected", never an error
     that blocks a legitimate non-brew upgrade (RESEARCH Pattern 3, and V5 in the
     security domain).
  2. Split the resolved path on `os.PathSeparator`. Scan candidate indices from the
     DEEPEST match outward for a segment equal to `Caskroom` or `Cellar` at index i where
     at least three more segments follow (token at i+1, version at i+2, and the payload at
     i+3 or deeper). Everything left of index i is the prefix — do not compare it against
     anything, do not carry a prefix list, and do not special-case an operating system.
  3. For each candidate, build the receipt path the tree implies:
     Caskroom -> `<prefix>/Caskroom/<token>/.metadata/INSTALL_RECEIPT.json`;
     Cellar -> `<prefix>/Cellar/<name>/<version>/INSTALL_RECEIPT.json`.
     Both locations were measured on a real Homebrew 6.0.16 install and confirmed against
     Homebrew's own `tab.rb`/`cask/metadata.rb` (RESEARCH § Summary).

     and do not read any field out of it; the file's contents are a Homebrew-internal
     format with no third-party stability contract (RESEARCH Pitfall 2). If the stat
     fails, continue to the next candidate; if no candidate has a receipt, return
     `brewInstall{}, false`.
  5. On success return the populated struct with `InstallDir` set to the joined
     `<prefix>/<Tree>/<Token>/<Version>` segments and `ResolvedBinary` set to the
