<objective>
Rehearse the one path that cannot be rehearsed — and measure the ordering claim
instead of trusting it.

Purpose: D-08 locks rehearsal to the maintainer's Mac before any tag push, because
the release pipeline runs exactly once per tag and a wrong answer cannot be
withdrawn. D-09 requires that rehearsal to hard-fail by name on a missing
certificate or API key rather than after a network round-trip — the rule this
repository wrote after a signing pipe hung for five minutes and then failed on an
expired token. D-07 declines a permanent ordering regression test in favour of a
one-time recorded mutation, and the D-18 ruling hands that mutation an obvious,
cheap subject: configure cosign the pre-ruling way, record which bytes the bundle
then authenticates, revert.

**Two review findings reshaped this plan and are worth stating up front, because
both were cases of a plan asking for something no mechanism could deliver.** First,
the pre-notarize hash cannot be captured between two pipes of one release run —
GoReleaser owns those transitions and exposes no hook — so the baseline now comes
from a notarize-DISABLED run of the identical command, and the determinism that
substitution depends on is measured here by a double build rather than borrowed
from a gate that does not cover darwin. Second, what
cosign signed cannot be recovered by re-hashing the path in the artifact metadata:
that metadata names the signature file, not its subject, and under the mutation
quill has already rewritten the file at that path. The subject is now determined
cryptographically, by verifying the bundle against both candidate files and
recording which one it authenticates. Gatekeeper assessment in this plan uses the
D-19 oracle (`-t install`, verdict by exit status), like everywhere else in the
phase.

The accepted consequence, stated plainly rather than glossed: a local rehearsal
does not exercise the CI environment, so first execution in CI remains genuinely
first execution.

Output: a guarded maintainer-only rehearsal target, and the measured SIGN-04
ordering evidence.
</objective>

zero assets):

1. Create one run-scoped temp dir tree for the generated config, the throwaway
   cosign key, the native GoReleaser build and the zig caches, removed by a single
   `trap`.
2. Generate a throwaway local cosign key pair and inject a key flag into a
   generated copy of the committed config with the same awk anchor
   `release:dry-run-signed` uses, then apply the same additions-only diff guard —
   any deletion or replacement line is a hard failure, and every added line must
   carry the key flag or the cosign password variable. The Apple credentials are
   NOT injected into the config; they reach quill through the process environment
   via the config's own templates.
3. When `SIGN04_MUTATE` is set to `1`, rewrite the generated copy so the cosign
   entry reproduces the PRE-RULING configuration. That takes **TWO** edits, not
   one:

   a. the top-level key changes from the release-scoped name to the build-scoped
      one, and
   b. the `ids: [raw]` line is **REMOVED**.

   **Both edits are mandatory, and (b) is the one a previous revision got wrong.**
   The two sign pipes resolve `ids:` in DIFFERENT NAMESPACES. The release-scoped
   pipe applies its id filter to uploadable ARCHIVE artifacts, where `raw` is a
   real archive id declared in `archives:`. The build-scoped pipe first filters to
   raw build artifacts of type Binary and then applies its ids against BUILD ids —
   which in this repository are the four `codegraph-<os>-<arch>` values. There is
   no build with id `raw`. Carrying `ids: [raw]` across the rename therefore
   selects ZERO artifacts.

   And a zero-match sign pipe does not fail. At source it logs a warning and
   returns nil — the run exits 0 having signed nothing and produced no sidecar. The
   mutation would then terminate as `SUBJECT-INDETERMINATE` for a reason that has
   nothing to do with pipe ordering, and the D-07 inversion — the entire
   evidentiary purpose of this experiment — could never be observed. This is
   precisely the failure class plan 02-02's own prohibition forbids: a pipe that
   matches nothing must fail loudly, never report success. The committed pre-ruling
   block carries no `ids:` field at all, which is exactly why it worked, and is the
   proof that a faithful mutation removes the line rather than renaming around it.

   **The mutation-mode diff guard must PERMIT exactly these two edits and nothing
   else.** The previous guard asserted that the only difference beyond the key
   injection was one key name — which did not merely miss the problem, it ENFORCED
   the broken shape and would have blocked an executor who spotted it. Widen it to
   a two-edit allowlist: one key-name change, one `ids:` line removal, and no other
   difference. Print the resulting diff.

3a. **Structurally validate the mutated config BEFORE any Apple round-trip.** Parse
   the generated mutated file and assert: exactly one build-scoped signing entry
   exists; no release-scoped signing entry exists; that entry declares NO id filter;
   and its `signature:` template and `args:` are unchanged from the committed
   block. Any failure here exits non-zero under the label
   `MUTATION-CONFIG-INVALID`, before the run reaches Apple. A malformed mutation
   must cost nothing but a parse.

3b. **Name the no-op as its own failure class.** After the mutated run, assert that
   the mutation produced at least one Signature-typed artifact. Zero signatures
   fails under the distinct label `MUTATION-PRODUCED-NO-SIGNATURE`. This is NOT
   `SUBJECT-INDETERMINATE`: "the mutation signed nothing" and "the mutation signed
   something that failed to invert" are different findings with different causes and
   different remedies, and collapsing them into one label is what would let a no-op
   masquerade as an inconclusive ordering result.
