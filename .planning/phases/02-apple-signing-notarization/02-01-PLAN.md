<objective>
Build the Gatekeeper gate, then watch it fail — before anything in this phase can
make it pass.

This is the phase's tracer slice: one thin, production-quality path from a
PUBLISHED release asset, through a real `com.apple.quarantine` xattr, to Apple's
own verdict, recorded as evidence. It touches every layer the rest of the phase
depends on (published-asset download, quarantine rig, Apple tooling, Taskfile
precondition discipline, phase evidence file) and it de-risks the two open
questions that could otherwise invalidate the SIGN-03 baseline itself:
whether `syspolicy_check distribution` even accepts a bare Mach-O, and whether a
synthetic quarantine xattr produces the same verdict as a genuine browser
download.

Purpose: SIGN-03 exists because four things in this project feel like
verification and are not — a green CI step, a passing `codesign -dvv` (which
already passes today on the adhoc-signed darwin/arm64 binary `spctl` rejects), an
Accepted `notarytool` history entry, and `spctl` on a file that was never
quarantined. This plan produces the one trustworthy gate and proves it can fire.

Output: a reusable `verify:gatekeeper` Taskfile target, a recorded RED baseline,
and resolved answers to research Open Questions 1 and 2.
</objective>

Add one new Taskfile target, `verify:gatekeeper`, wired end-to-end from a published
release asset to an Apple Gatekeeper verdict. It is the single definition both the
SIGN-03 RED baseline (Task 2) and the post-release GREEN check (plan 02-06) call.

Per D-02 the oracle is Apple-native and nothing else: the assessment command and
the distribution-policy check are the verdict, and a signature-inspection command
is explicitly not — it already passes today on the adhoc-signed arm64 binary
Gatekeeper rejects, so this target must not call it as evidence. Per D-06 the
baseline is the published v0.5.1 darwin assets, never the zero-asset v0.5.0, and
the quarantine attribute must be read back before assessment.

Inputs, all read from the environment, all guarded by their own named
precondition: TAG, REPO, GOOS, GOARCH, GH_TOKEN, and GATEKEEPER_EXPECT (accepted
or rejected). Tool preconditions: `gh`, `jq`, `xattr`, `spctl`. Add a
`[ "$(go env GOHOSTOS)" = "darwin" ]` host precondition with a message naming
namespace-profile-macos-6x14-tahoe as the CI runner class. Every `msg:` names the
missing variable or tool, the fix, and why the target needs it — matching the
existing style in `verify:release-assets` and `check:darwin-toolchain`. These must
halt by name before any network call, per D-09 and the five-minute `expired_token`
hang that produced that rule.

Body, in order:

1. Resolve the asset name as `codegraph_${TAG}_${GOOS}_${GOARCH}` — the raw
   binary, matching `internal/upgrade.releaseAssetName`'s contract. Never the
   `.zip`.
2. Download it with `gh release download` into a `mktemp -d` cleaned by a single
   `trap`. Downloading is not optional and a local `dist/` copy is never
   acceptable — plan 01-05's false negatives came from a verifier that read an
   artifact it never downloaded.
3. Record the downloaded asset's sha256 (prefer `sha256sum`, fall back to
   `shasum -a 256`, mirroring `verify:self-upgrade`) so a later plan can join this
   observation to SIGN-04's four comparison points.
4. Assess the file BEFORE applying any xattr and record that verdict on its own
   labelled line as the explicit non-evidence control. This is the observation
   that makes "spctl on a never-quarantined file" visibly distinct rather than
   silently conflated.
5. Apply the quarantine attribute with `xattr -w com.apple.quarantine` using the
   four-field flags/timestamp/agent/uuid form from RESEARCH.md's Code Examples,
   with flags `0081`. Build the hex timestamp and the UUID with `printf` and
   `uuidgen` in plain shell — no Go-template braces anywhere in this target, for
   the reason `release:dry-run-signed` has none.
6. Read the attribute back with `xattr -p com.apple.quarantine` and HARD-FAIL if
   it is absent or empty. An assessment that runs without this confirmation is not
   evidence and the target must refuse to produce one.
7. Run `spctl -a -vv -t exec` on the quarantined copy, capturing both stdout and
   stderr (spctl writes its verdict to stderr) and its exit status without letting
   `set -e` abort the run — a `rejected` result is the expected outcome on the RED
   path and must be reported, not crashed on.
8. Run `syspolicy_check distribution` on the same file, treating its presence,
   accepted input types and output as UNRESOLVED (RESEARCH.md Open Question 1).
   Record its exit status and output verbatim under a labelled line. Do not gate
   on it in this task; if the binary is absent, record that fact and continue.
   Task 3 tightens this into a hard assertion only if the recorded semantics
   support one.
9. Derive the observed verdict from the spctl output by testing for the literal
   `accepted` / `rejected` words, and additionally capture whether the output
   names `source=Notarized Developer ID`. Compare the observed verdict against
   GATEKEEPER_EXPECT and exit non-zero on any mismatch, including an
   unparseable verdict — an spctl output this target cannot classify is a hard
   failure, never a pass.
10. Emit, as the LAST lines printed and on both the pass and the fail path, a
    machine-parseable `GATEKEEPER-EVIDENCE` line carrying tag, goos, goarch,
    sha256, expect, observed, xattr_present, source, spctl_exit and
    syspolicy_exit; plus the separate labelled lines for the pre-xattr control
    assessment and the raw syspolicy output. A RED observation is the most
    valuable output this target can produce, so the evidence line must survive the
    failure path.

Do not add this target to any workflow in this plan — CI wiring is plan 02-06.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Releases CDN → local temp dir | An untrusted, network-fetched binary crosses into the local filesystem and is then executed-assessed (not executed) by `spctl` |
| Local test rig → Gatekeeper policy engine | A hand-written `com.apple.quarantine` xattr crosses into `syspolicyd`'s input, standing in for a real browser download |
| Recorded evidence → downstream phase decisions | `02-EVIDENCE.md` becomes the authority every later plan's GREEN claim is measured against |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Spoofing | `verify:gatekeeper`'s `xattr -w com.apple.quarantine` rig | high | mitigate | A synthetic xattr could spoof Gatekeeper's real input and produce a verdict that is an artifact of the rig (RESEARCH.md Pitfall 6 / assumption A2). Task 2 step 3 compares the synthetic copy against a genuinely browser-downloaded, byte-identical copy and Task 3 records a CONFIRMED/REFUTED verdict; a REFUTED result blocks the rig from being trusted for the GREEN criterion. |
| T-02-02 | Repudiation | The gate itself (silent-pass surface) | high | mitigate | A gate that cannot fire produces a green record that denies the failure ever happened — this repo's defining failure class. Mitigated three ways in one target: the `xattr -p` read-back hard-fails before assessment; an unclassifiable `spctl` output is a hard failure rather than a pass; and Task 2 step 2 runs the gate with a deliberately wrong `GATEKEEPER_EXPECT` and records the non-zero exit. |
| T-02-03 | Tampering | Published v0.5.1 darwin assets (the RED baseline) | medium | mitigate | The baseline cannot be recreated once notarization lands. `verify:gatekeeper` only ever reads via `gh release download` and writes exclusively into a `mktemp -d`; no path in this plan uploads, deletes or replaces a release asset. Reinforced by the plan's prohibition and by the `docs/RELEASE-PROCEDURES.md` §7.1 link Task 3 adds. |

Accepted on the existing precedent. |

   file." The substantive assumption underneath it is that `spctl -a -vv -t exec`

   would be unfounded. Carried, not resolved.

   Manual review: the assumption is that a RED observation recorded once, against
   two specific published assets on one specific macOS version, generalises to the
   gate being able to fire in future. It does not automatically — D-07 explicitly
   declines a standing ordering regression test, and this plan likewise produces a
   recorded observation rather than a permanent guard. Consequence if wrong: a
   future refactor could silently disable the gate with nothing firing. Carried
   deliberately; the compensating control is that `verify:gatekeeper` is the same
   target the post-release GREEN check calls (plan 02-06), so it re-runs on every
   release rather than only on the day it was hand-checked.
