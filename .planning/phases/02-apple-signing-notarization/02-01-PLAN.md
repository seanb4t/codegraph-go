<objective>
Build the Gatekeeper gate, then watch it fail — before anything in this phase can
make it pass.

This is the phase's tracer slice: one thin, production-quality path from a
PUBLISHED release asset, through a real `com.apple.quarantine` xattr, to Apple's
own verdict, recorded as evidence. It touches every layer the rest of the phase
depends on and it de-risks the remaining open question about whether a synthetic
quarantine attribute produces the same verdict as a genuine browser download.

Purpose: SIGN-03 exists because four things in this project feel like
verification and are not — a green CI step, a passing `codesign -dvv` (which
already passes today on the adhoc-signed darwin/arm64 binary Gatekeeper rejects),
an Accepted `notarytool` history entry, and `spctl` on a file that was never
quarantined. This plan produces the one trustworthy gate and proves it can fire.

**The oracle changed under D-19 (LOCKED) — read this before writing any command.**
Cycle 1 of plan review established that the previously-specified commands cannot
produce the required result for a bare Mach-O, and the maintainer reproduced both
measurements against two vendors' genuinely notarized Developer ID CLIs before
ruling. `spctl`'s `-t` is an assessment TYPE, not a formality: `-t exec` asks "may
I launch this as an application", and a bare Mach-O is rejected on SHAPE before
notarization is considered at all — which is why `origin=Developer ID
Application: …` still prints beside the rejection. `-t install` asks "may this be
installed from this origin", which is the question a downloaded CLI binary
actually poses, and it returns `accepted` / `source=Notarized Developer ID` on a
notarized subject while still rejecting the adhoc linker-signed shape this repo
ships today. `syspolicy_check distribution` is Fatal for anything unstapled, and
D-16 puts stapling permanently out of scope, so it is demoted to a recorded
observation and never gates.

The near-miss is worth naming, because it is this repo's two failure families
stacked in one check: under the old oracle this plan's RED baseline would have
gone red today for the RIGHT reason (adhoc, un-notarized) and stayed red after
notarization for a COMPLETELY DIFFERENT one (wrong assessment type) — a gate that
passes its RED demonstration and can then never go green, discovered only after
plan 02-07's irreversible publish.

Output: a reusable `verify:gatekeeper` Taskfile target, a recorded RED baseline,
and a settled verdict on the synthetic-quarantine rig.
</objective>

Add one new Taskfile target, `verify:gatekeeper`, wired end-to-end from a published
release asset to an Apple Gatekeeper verdict. It is the single definition both the
SIGN-03 RED baseline (Task 2) and the post-release GREEN check (plan 02-06) call.

Per D-02 the oracle is Apple-native and nothing else, and per D-19 the specific
command is `spctl -a -vv -t install` with the verdict taken from the EXIT STATUS.
A signature-inspection command is explicitly not evidence — it already passes today
on the adhoc-signed arm64 binary Gatekeeper rejects — so this target must not call
one as an oracle. Per D-06 the baseline is the published v0.5.1 darwin assets,
never the zero-asset v0.5.0, and the quarantine attribute must be read back before
assessment.

Inputs, all read from the environment, all guarded by their own named
precondition: TAG, REPO, GOOS, GOARCH, GH_TOKEN, and GATEKEEPER_EXPECT. Tool
preconditions: `gh`, `jq`, `xattr`, `spctl`. Add a
`[ "$(go env GOHOSTOS)" = "darwin" ]` host precondition naming
namespace-profile-macos-6x14-tahoe as the CI runner class.

Two precondition details the review raised and that are settled here rather than
left to judgement:

- GATEKEEPER_EXPECT needs VALUE validation, not merely presence. A value outside
  the accepted/rejected pair must halt by name. Addresses review concern (pi LOW):
  an unvalidated value fails safe but confusingly, turning every observation into
  a mismatch.
- `jq` earns its place — it is NOT dropped. Addresses review concern (codex LOW,
  pi LOW, both of which suggested dropping it): the reviewers' rationale for
  keeping it was `syspolicy_check --json` parsing, which D-19 demotes, so that
  justification is gone. Re-derived, `jq` has a better job: parse
  `gh release view --json assets` to read GitHub's own recorded per-asset digest
  and cross-check it against the recomputed sha256 of the downloaded file. That
  turns "the bytes I assessed" into "the bytes the release serves", which is a
  genuine provenance strengthening rather than a leftover.

Body, in order:

1. Resolve the asset name as `codegraph_${TAG}_${GOOS}_${GOARCH}` — the raw
   binary, matching `internal/upgrade.releaseAssetName`'s contract. Never the
   `.zip`.
2. Read the asset's metadata with `gh release view --json assets` and extract that
   asset's recorded digest and size. Treat an asset absent from the listing as a
   hard failure naming the asset and the tag.
3. Download it with `gh release download` into a `mktemp -d` cleaned by a single
   `trap`. Downloading is not optional and a local `dist/` copy is never
   acceptable — plan 01-05's false negatives came from a verifier that read an
   artifact it never downloaded.
4. Recompute the sha256 (prefer `sha256sum`, fall back to `shasum -a 256`,
   mirroring `verify:self-upgrade`) and compare it against the digest from step 2.
   A mismatch is a hard failure.

   **A missing digest must not fail open.** Addresses review concern (codex MEDIUM,
   pi MEDIUM — the highest-value item in the non-HIGH set): the previous revision
   emitted a sentinel and continued, which would let the target pass with
   `digest_match=unknown` on every line while the provenance strengthening this
   check exists for was never established. Sentinel-and-continue on a verification
   step is this repository's single most-repeated failure class.
   Bind the behaviour to `GATEKEEPER_EXPECT` instead:
   - When the expected verdict is ACCEPTED (the GREEN path, plan 02-06's CI job), a
     missing or malformed digest is a HARD FAILURE. GREEN is the claim that carries
     weight, so its provenance must be established, not assumed.
   - When the expected verdict is REJECTED (the RED baseline against a preserved
     older release, where the API may genuinely predate per-asset digests), record
     the sentinel and continue — but emit a clearly-labelled warning line naming the
     asset, and set `digest_match=unknown` so the downgrade is visible in the
     evidence rather than silent.
   State this asymmetry in a target comment so it reads as a deliberate scope
   decision rather than an inconsistency.
5. Assess the file BEFORE applying any xattr and record that verdict on its own
   labelled line as the explicit non-evidence control. This is the observation
   that makes "spctl on a never-quarantined file" visibly distinct rather than
   silently conflated.
6. Apply the quarantine attribute with `xattr -w com.apple.quarantine` using the
   four-field flags/timestamp/agent/uuid form from RESEARCH.md's Code Examples,
   with flags `0081`. Build the hex timestamp and the UUID with `printf` and
   `uuidgen` in plain shell — no Go-template braces anywhere in this target, for
   the reason `release:dry-run-signed` has none. Call this value SYNTHETIC in every
   comment, label and evidence field. Addresses review concern (codex MEDIUM): it
   is a simulation until Task 2 confirms it behaves like a browser download, and
   naming it "genuine" before that comparison would prejudge the one question this
   plan exists to settle.
7. Read the attribute back with `xattr -p com.apple.quarantine` and HARD-FAIL if
   it is absent or empty. An assessment that runs without this confirmation is not
   evidence and the target must refuse to produce one.
8. Run `spctl -a -vv -t install` on the quarantined copy, capturing stdout,
   stderr (spctl writes its verdict to stderr) and its exit status without letting
   `set -e` abort the run — a rejection is the expected outcome on the RED path
   and must be reported, not crashed on.
9. Derive the observed verdict from the EXIT STATUS ALONE: 0 is accepted, 3 is
   rejected, anything else is unclassifiable and therefore a hard failure. Do not
   grep the output for the verdict words. Addresses review concern (codex MEDIUM,
   and D-19's own third bullet): a substring search for the accepted word matches
   inside the rejection sentence and inside origin lines, so it does not merely
   classify weakly, it classifies wrongly.

   Separately capture whether the output names the notarized-Developer-ID source
   string, and record it as its own evidence field `source_assertion` with values
   pass or fail — NOT as part of the verdict. Addresses review concern (codex LOW):
   rejecting exit 0 when the source line is absent makes output formatting a second
   gate, which reads as a contradiction of "exit status is the oracle" unless it is
   named as what it is — a deliberate SECOND, INDEPENDENT assertion. So: `observed`
   derives solely from the exit status; `source_assertion` is a separate property;
   and a disagreement between them fails the target with both values printed, under
   its own label `SOURCE-ASSERTION-MISMATCH`, so the two failure kinds stay
   distinguishable in the evidence.

   **Specify the agreement mechanically, with a truth table — do not leave
   "disagreement" to interpretation.** Addresses review concern (codex LOW): on the
   RED path the notarized-source line is legitimately ABSENT, so a naive reading of
   "source assertion must pass" would make the RED baseline fail for the wrong
   reason and break the phase's first gate. The required pairing is:

   | observed (from exit status) | required source_assertion |
   |---|---|
   | accepted | pass — the notarized-Developer-ID source line must be present |
   | rejected | fail — that line is expected to be ABSENT, and its absence is correct |

   Only an off-diagonal pair fails. Write the table into the target comment so an
   executor cannot reconstruct it wrongly.

   Add a one-line comment recording that the exit-status values were measured on
   macOS 27.0 while the CI runner is Tahoe-class, so a future version drift is
   anticipated rather than surprising. Addresses review concern (pi LOW): the
   non-{0,3}-is-fatal rule already makes drift a loud failure rather than a wrong
   verdict, which is the correct failure direction — the comment records that this
   was reasoned about rather than lucky.
10. Run `syspolicy_check distribution` on the same file and record its exit status
    and output verbatim under a labelled line. It MUST NOT gate — D-19 removes it
    as a gating check because its Fatal verdict is definitionally unreachable while
    stapling is out of scope, and a gate that can never pass is one of the two
    failure families this phase exists to close. Write that reason as an in-target
    comment so a future reader cannot mistake the non-gating call for an oversight
    and "fix" it into a gate. If the binary is absent, record the sentinel and
    continue.
11. Compare the observed verdict against GATEKEEPER_EXPECT and exit non-zero on
    any mismatch.
12. Emit the evidence lines per the schema below, as the LAST lines printed, on
    BOTH the pass and the fail path. A RED observation is the most valuable output
    this target can produce, so the evidence must survive the failure path.

**Evidence-line schema — define it here, once, for the whole phase.** Addresses
the cross-plan review concern that multiple shell-generated evidence prefixes were
introduced with no defined quoting, escaping, missing-value or versioning rules,
making later automated joining fragile. Every evidence line in this phase, in every
plan, follows it:

- One line, beginning with the prefix, then space-separated `key=value` pairs.
- Keys are fixed per prefix and always all present, in a fixed order. A value that
  could not be obtained is never omitted — it is the literal sentinel `not-found`
  (the thing does not exist) or `unknown` (it exists but could not be read).
- Values are shell-safe: no spaces, no quotes, no newlines. Any value that would
  contain whitespace is emitted on its own separate labelled line immediately
  above, and the evidence field carries a short token instead.
- The first field is always `schema=1`, so a later consumer can detect a format
  change rather than mis-parse one.

For this target the prefix is `GATEKEEPER-EVIDENCE` with fields: schema, tag,
goos, goarch, sha256, gh_digest, digest_match, expect, observed, exit,
xattr_present, source_assertion, syspolicy_exit.

Do not add this target to any workflow in this plan — CI wiring is plan 02-06.
