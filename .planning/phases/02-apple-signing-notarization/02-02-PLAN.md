<objective>
Move cosign to the far side of quill, and turn on notarization — the two config
changes that make SIGN-04's byte-identity claim true by construction rather than
by coincidence, plus the static assertions that keep them true.

Purpose: D-18 (LOCKED, maintainer, 2026-08-09) settles the headline research
finding. GoReleaser's pipe order is a hardcoded Go slice, not driven by YAML block
order: the build-scoped cosign pipe runs BEFORE `notary.MacOS`, which is a
sign-and-notarize pipe that rewrites the Mach-O in place. Renaming one top-level
key moves cosign to the release-scoped pipe, which is registered after archive,
sbom and checksum — so all four of SIGN-04's comparison points describe the same
bytes. GoReleaser is not wrong and this is not an upstream bug; the current
configuration would simply be asking for the wrong thing.

Output: a `.goreleaser.yaml` whose signing and notarization pipes are ordered
correctly, whose load-bearing comments state what is true rather than what Phase 1
believed, and whose properties are pinned by resolve-and-assert tests.

**On the `one-way` rating in Task 2 with no preceding `checkpoint:decision`.** The
omission is deliberate, not an oversight. D-04 rated this ordering one-way once
published, and D-18 is the maintainer's own locked ruling on exactly this
configuration change, made during planning. The reversibility reference's own
anti-pattern list forbids gating a decision the human has already made — the door
is already walked through, and re-asking would produce checkpoint fatigue on the
one plan where the answer is least in doubt. The rating stays on the task so the
signal survives for later phases; the checkpoint does not.
</objective>
