<objective>
Publish the guarantee — exactly as strong as the evidence, and no stronger — and
hand the reader the commands to check it themselves.

Purpose: ROADMAP Phase 2 criterion 5. `docs/RELEASE.md` today documents cosign,
provenance and SBOM verification and says nothing about Gatekeeper, because until
this phase there was nothing true to say. The document must now state what a macOS
user actually gets — notarized, online-verified, not stapled — name offline first
launch as a known limitation rather than quietly omitting it, and give the literal
commands that reproduce criterion 2.

The commands matter more than the prose. A reader who runs a Gatekeeper assessment
on a file that was never quarantined gets a pass that means nothing; that failure
mode is called out explicitly in SIGN-03 and must be pre-empted in the
documentation, not only in the gate. D-02 decides which commands appear: the
assessment and the distribution-policy check, never a signature-inspection command
presented as sufficient. D-06 decides the ordering: the attribute is written and
read back before anything is assessed. D-16 decides the guarantee's ceiling:
stapling is out of scope, so the document must say not stapled and name the
offline gap.

Output: a Gatekeeper section in `docs/RELEASE.md` whose every claim traces to a
recorded measurement.
</objective>

Add a Gatekeeper verification subsection to `docs/RELEASE.md`. Place it inside §1
alongside the existing cosign, provenance and SBOM subsections, as a new lettered
subsection, and add a matching bullet to §1's opening list of what a tagged release
provides — this is a verification claim about the same published assets, so it
belongs beside its siblings rather than in a section of its own.

The section must carry, in this order:

1. **The guarantee, stated in the exact three-part form** the ROADMAP uses:
   notarized, online-verified, not stapled. Write it as a single sentence a reader
   can quote. Do not soften it and do not extend it.
2. **What each part means operationally.** That the darwin binaries carry a real
   Developer ID signature and an Apple notarization ticket; that Gatekeeper
   resolves that ticket over the network on first launch; and that no ticket is
   attached to the file itself.
3. **The known limitation, named.** First launch of a browser-downloaded binary on
   a machine with no network reachability to Apple cannot complete the ticket
   lookup. Describe the user-visible consequence rather than only the mechanism.
   State that this is a deliberate scope decision, that a bare Mach-O and a `.zip`
   are both categorically unstaplable and the signing tool has no attach command,
   and that this matches what the release tool ships for its own binary. Name the
   deferred requirement id so a reader can find the follow-up.
4. **The reproduction commands.** A download of the raw per-platform asset; the
   attribute write using the four-field flags/timestamp/agent/uuid form with the
   downloaded-and-first-launch flag value; the attribute READ-BACK; the Gatekeeper
   assessment; and the distribution-policy check. The read-back step is
   non-negotiable and must carry an inline comment saying it confirms the attribute
   before assessing.
5. **What a pass and a fail look like**, quoting the expected assessment output
   including the notarized-Developer-ID source string, and stating plainly that an
   assessment run on a file that was never quarantined returns a misleading pass —
   which is why step 4's read-back exists. Mirror §a's existing "this asserts two
   things" explanatory shape.
6. **What does not count as verification.** A short list, matching what the phase
   recorded: a green CI step; a signature-inspection command that already passes
   today on the adhoc-signed arm64 binary Gatekeeper rejects; an Accepted entry in
   the notarization submission history; and an assessment of a never-quarantined
   file. This list is the documentation half of SIGN-03 and is what stops a future
   reader substituting a cheaper check.

Scope the distribution-policy check by what plan 02-01 measured: if the evidence
file records it accepting a bare Mach-O with readable pass/fail semantics, present
it as a second assertion; if not, present it as an informational step and say so
in one clause. Do not present it as an assertion the project has not observed.

Every command must use the raw per-platform asset name, never the `.zip` — the
zip's contents are the same bytes but the assessment target a user runs is the
extracted executable, and mixing the two in a reproduction snippet is how a reader
ends up assessing an archive.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Published documentation → a user's verification decision | A reader substitutes the document's command for their own judgement; a command that passes for the wrong reason is worse than no command |
| Documented guarantee → user expectation of offline behaviour | An omitted limitation becomes a silent promise |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-14 | Spoofing | The documented reproduction sequence | high | mitigate | A published assessment command without the attribute write-and-read-back returns a pass on a never-quarantined file, spoofing a Gatekeeper verdict the user never actually obtained — and doing so in the project's own voice. Mitigated by making the read-back a mandatory documented step with an acceptance criterion asserting it precedes the assessment line, by quoting the expected pass output so a reader can recognise a wrong one, and by the explicit four-item list of checks that do not count. |
| T-02-15 | Repudiation | The guarantee statement's scope | medium | mitigate | A guarantee stated without its limitation lets the project later deny a promise a user reasonably read into it. Mitigated by requiring the not-stapled clause inside the guarantee sentence itself and the offline limitation immediately adjacent, with acceptance criteria on both, plus the plan-level prohibition forbidding any stronger claim anywhere in the file. |
</threat_model>
