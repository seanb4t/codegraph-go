<objective>
Cut the release, then make it prove every claim this phase has been building
toward — against the bytes a user actually downloads.

Purpose: everything before this plan is mechanism and rehearsal. ROADMAP Phase 2
criteria 2, 3 and 4 are all statements about a published release, and none of them
can be observed anywhere else. Criterion 2 needs the notarized published asset
assessed with a confirmed quarantine attribute. Criterion 3 needs a byte-identity
chain to close across five provenance points, one of which only exists after the
release job runs and another only after a re-download. Criterion 4 needs the real suite against
the real binary.

The two rules that shape how this plan behaves when something goes wrong. D-13:
release-please is the sole tag authority — no hand-created version tag, because
such a tag would match the release workflow's own trigger and falsely fire the
pipeline. D-12: a published release or tag is never deleted or re-pushed —
recovery is a new version. So a failure here is recorded and patched forward, not
erased.

D-05 governs how the byte-identity claim is proven: a chain of provenance points,
one of which must come from the RE-DOWNLOADED published asset. Re-downloading is not
optional; the prior phase's verifiers produced three false negatives, one of them
precisely because a verifier never downloaded the artifact it then read. D-02
governs the Gatekeeper half: Apple's own assessment is the oracle, never the
notarization tool's own success report. D-19 fixes which assessment: `-t install`,
verdict by exit status, with the distribution-policy check demoted to a non-gating
observation because its Fatal-when-unstapled verdict is unreachable by design here.

Output: the phase's central claim, measured, with the evidence a third party could
re-run.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| The release run → the permanently-published artifact set | This is the irreversible boundary; nothing published here can be withdrawn, only superseded |
| Published assets → every downstream consumer | The Homebrew cask in the next phase, the upgrade path, and browser downloaders all consume exactly these bytes |
| Recorded evidence → the phase's completion claim | If the evidence describes anything other than the published bytes, the claim is false regardless of how green the jobs were |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-22 | Tampering | A published release that silently shipped un-notarized | critical | mitigate | The notarize pipe treats an empty id filter as a non-fatal skip, so an id or template mistake ships un-notarized binaries behind a green run. Mitigated by three independent observers: the checkpoint requires reading the pipe's own log lines for a submission rather than a skip; the Gatekeeper job independently assesses the published asset and fails on a non-accepted verdict; and the maintainer's own browser download in checkpoint step 8 is the unproxied user experience. Recovery is patch-forward — a new version — never deletion. |
| T-02-23 | Repudiation | Evidence recorded from a source other than the published asset | high | mitigate | Presenting a rehearsal artifact or a green job log as the shipped bytes would make the phase's completion claim unfounded while appearing complete — the failure mode that produced three false negatives in the prior phase. Mitigated by the plan-level prohibition, by requiring provenance labels on all four byte-identity entries, by requiring quoted commands where a verification result stands in for a hash, and by an acceptance criterion asserting no published release was deleted or re-pushed. |
