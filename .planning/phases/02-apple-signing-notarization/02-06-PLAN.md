<objective>
Wire the credentials into the one job allowed to hold them, and make the release's
own claims re-prove themselves after every publish.

Purpose: SIGN-01 requires the certificate and API key to be held as CI secrets.
SIGN-02's green criterion must be checked against the re-downloaded published
asset, and criterion 4's suite must run against the notarized binary itself. Both
belong in the existing post-release verification workflow, which already
re-downloads assets for its signature and attestation checks — reusing proven
machinery rather than lengthening the single unrehearsable publish path, and
catching a failure after publish where the recovery is patch-forward.

Three standing constraints govern every edit here, and each has already cost this
project something. Exactly one job may hold the OIDC write scope, and the workflow
file name and tag trigger are pinned by the upgrade path's certificate-subject
check. Granting that scope or these secrets to anything a pull request can trigger
is a security regression, not a fix. And a conclusion guard without its
event-aware disjunct makes every job skip silently and report green.

Output: the credentials in exactly one place, and two new verification jobs that
can actually fail.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub repository secrets → the release job's process environment | An Apple code-signing private key and an App Store Connect API key become readable by every step and every action inside that job |
| Pull-request-triggerable workflows → the same secret namespace | A fork-controllable trigger must never reach these values or the OIDC write scope |
| Post-release job results → the project's public verification claims | These jobs are what convert a documented claim into a re-proved one |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-16 | Information Disclosure | Apple credentials reachable from a pull-request trigger | critical | mitigate | The credentials are added to exactly one step of one job in the tag-triggered workflow, with no `environment:` key and no new job. `TestAppleSecretsScopedToSingleReleaseJob` enumerates the workflow directory at runtime and fails if any credential name appears outside that job or in any pull-request-triggerable workflow — and the test is proven non-vacuous by observing it red against a deliberate violation. Reinforced by the standing rule that granting these to a pull-request-reachable workflow is a regression, not a fix. |
| T-02-17 | Elevation of Privilege | The OIDC write scope | high | mitigate | A second job holding that scope, or a renamed workflow file or changed tag trigger, silently breaks the certificate subject the upgrade path pins — and does so on a genuine, correctly-published release. Mitigated by adding no job and no permission, by an acceptance criterion diffing the workflow name, trigger and job set, and by the existing single-scope test remaining green. |
| T-02-18 | Repudiation | The conclusion guard on the two new jobs | high | mitigate | Under a manual dispatch the upstream-run object is null, so a bare conclusion test makes the job skip and the workflow report green while verifying nothing — and the retained historical re-verification trigger would be dead from the day it shipped. Mitigated by requiring the event-aware disjunct verbatim on both new jobs, by a count assertion over the file, and by a recorded dry evaluation of the guard under both trigger events. |
| T-02-19 | Tampering | The downloaded asset the suite executes | high | mitigate | **This row previously carried a mitigation that did not hold, and the correction is the substance of a HIGH review finding.** It argued that because the same workflow independently verifies the asset's signature and attestation, a tampered asset would fail there. Parallel independent jobs provide no ordering guarantee, so the binary would be made executable and RUN on the runner regardless of whether the sibling job later failed. Corrected mitigation: the target itself runs `cosign verify-blob` against the downloaded asset, with the same issuer and identity flags the published instruction uses, and hard-fails BEFORE any `chmod` or execution; the job additionally declares `needs:` on the supply-chain job so the ordering is legible in the graph as well as enforced in the body. The recorded sha256 remains, so the executed bytes stay identifiable after the fact. No second signature implementation is introduced — the same cosign invocation shape is reused. |
| T-02-20 | Spoofing | `TestAppleSecretsScopedToSingleReleaseJob`'s scope of proof | low | accept | Addresses review concern (codex MEDIUM): the test proves where credential NAMES are consumed in workflow files. It cannot prove the GitHub-side scope of the secrets themselves — repository versus organization versus environment — nor the access policies attached to them. Those are dashboard facts, covered by `user_setup` and by the checkpoint in plan 02-07 that lists them. Accepted rather than mitigated, with the limitation written into the test's own doc comment so a later reader does not over-trust a green result. |
| T-02-21 | Information Disclosure | The release step's process environment | low | accept | The five credentials are visible to every process the Release step launches. Accepted with that constraint stated, and reinforced by the acceptance criterion that the step's diff adds no new shell body. |

| T-02-24 | Tampering | The pre-existing `self-upgrade` job's download-then-execute path | medium | accept | ACCEPTED PRE-EXISTING EXPOSURE, recorded rather than passed over in silence.
