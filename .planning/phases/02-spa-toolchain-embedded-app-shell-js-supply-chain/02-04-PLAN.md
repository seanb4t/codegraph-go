<recorded_limitations>
## What this guard's reachability model does and does not cover

Addresses review concern (HIGH): the previous plan's truth claimed no JS toolchain was
"reachable anywhere in the signed release path" while the scanner examined only two YAML
documents' immediate scalars. The release workflow executes `task release:goreleaser`
(`release.yml:228`), `task release:record-final-hashes` (`:274`) and the local composite action
`.github/actions/install-task` (`:162`), which itself shells out (`action.yml:17-28`). Those
three edges are now IN the model — resolved from the workflow's own content, not hardcoded.

**Still outside the model, recorded rather than papered over:**

1. **Executable files a scanned scalar shells out to.** If a `run:`/`cmds:` body invokes
   `./scripts/foo.sh`, the scanner sees the invocation but does not open the script. Today no
   release-path scalar does this; if one is added, the token would have to be inside that script
   to evade the guard.
2. **A container image that ships Node.** A `container:` or `services:` image with a JS runtime
   baked in names no forbidden command and no forbidden action.
3. **A JS runtime installed by a general-purpose command** — `brew install node`, a `curl … | sh`
   installer, or a marketplace action outside `forbiddenJSToolchainActions`. The action fixture
   is a **curated denylist**, not a structural property, and this plan says so rather than
   implying otherwise (addresses review concern, MEDIUM).
4. **GoReleaser hook scripts** that are file paths rather than inline commands — same shape as (1).

Every one of the four is a deliberate boundary, not an oversight. Widening to any of them means
executing or sandboxing untrusted content at test time, which is a larger change than BLD-07's
requirement text asks for. `T-02-04-05` in the threat register carries the accepted-risk record
and the instruction for adding a newly-reachable file to the roots fixture.
</recorded_limitations>
