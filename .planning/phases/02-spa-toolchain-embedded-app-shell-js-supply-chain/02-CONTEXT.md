# Phase 2: SPA Toolchain, Embedded App Shell & JS Supply Chain - Context

**Gathered:** 2026-08-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Stand up a real, pnpm-built SvelteKit application; commit its build output;
embed that output in the Go binary; and gate the JavaScript supply chain — while
keeping every Node/pnpm invocation out of the signed release path.

**Requirements:** RPC-03, BLD-01, BLD-02, BLD-03, BLD-05, BLD-06, BLD-07

**In scope:** the frontend toolchain (pnpm + Corepack pin, SvelteKit,
Tailwind v4, shadcn-svelte init), the generated TypeScript Connect client, the
committed build output and its drift guard, the `go:embed` + SPA-serving handler
with fallback routing, and the two JS supply-chain gates (lifecycle-script
approval, `pnpm audit`) plus the structural assertion that the release path
stays pure Go.

**Out of scope:** any of the four views. Phases 3–6 fill the shell's navigation
slots. This phase ships the shell and one live `GetStatus` call proving the seam
works end-to-end — nothing more.

</domain>

<decisions>
## Implementation Decisions

### SPA Tree & Build Output Location

- **D-01:** The app is **SvelteKit with `adapter-static`**, not plain Svelte +
  Vite. The roadmap's own Notes cite Vite's `_app`-prefixed output as the reason
  `//go:embed` needs the `all:` prefix — and `_app/` is SvelteKit's client-asset
  directory, not plain Vite's (which emits `dist/assets/`, no underscore).
  Choosing SvelteKit makes the roadmap's Notes literally true and gives
  file-based routing for Phases 3–6.
  — **Reversibility:** costly — undoing this after Phase 3 means rewriting every
  view's routing and re-deriving the embed path, the drift guard's file
  enumeration, and the fallback handler's asset-prefix rule.

- **D-02:** The SPA source tree lives at **`web/`** in the repo root.
  Keeps the JS world visibly separate from the Go module tree and makes BLD-07's
  structural check expressible as a path-scoped rule.

- **D-03:** The committed build output is **`web/build/`** — `adapter-static`'s
  own default output name (`pages: 'build'`, `assets: 'build'`), NOT `dist/`.
  **This is a recorded deviation from the roadmap's Notes**, which say
  `//go:embed all:dist`; the directive becomes `//go:embed all:build`. The `all:`
  prefix is still required — SvelteKit emits `_app/`, and Go's default embed
  rules silently drop underscore-prefixed paths while the build still succeeds.

  **VERIFIED, so the planner does not need to invent a task for it:** `web/build/`
  is **not** gitignored and **no `.gitignore` change is required**. The existing
  rule at `.gitignore:4` is `/dist/` — leading-slash anchored, so root-only.
  Confirmed with `git check-ignore -v web/build` (not ignored) and
  `git check-ignore -v web/build/index.html` (not ignored), positive-controlled
  against `git check-ignore -v dist/artifacts.json` → `.gitignore:4:/dist/`.

- **D-04:** The SPA fallback file is **`index.html`**, keeping ROADMAP criterion 2's
  wording literally verifiable. SvelteKit's docs recommend `200.html` instead, but
  that advice targets static HOSTS that special-case filenames and prerendering
  collisions — we serve from our own Go mux and prerender nothing, so neither
  hazard applies. Configure `adapter-static` with `fallback: 'index.html'`.

### TypeScript Client Generation

- **D-05:** The browser client is generated by adding **`- local: protoc-gen-es`**
  to the existing root `buf.gen.yaml`. **Connect-ES v2 removed
  `protoc-gen-connect-es`** — service definitions now come from `protoc-gen-es`
  (Protobuf-ES v2) itself, and the client is constructed with
  `createClient(Service, transport)` from `@connectrpc/connect`. So the TS side is
  **one** plugin, where the Go side uses two.
  Consequence the planner must handle: `task proto:gen` currently needs only Go,
  git and buf-via-`go tool`; a `local:` plugin resolves out of `web/node_modules`,
  so it gains a Node/pnpm dependency. That precondition **must fail loudly**, never
  skip.

- **D-06:** The generated TypeScript is **committed and drift-guarded**, matching
  the Go side and the committed `web/build/`. This follows the repo's stated
  pattern (`ROADMAP.md:98`): the drift guard ships in the same phase as the
  artifact it guards.

- **D-07:** The TS drift check **extends `task proto:drift`** rather than getting
  its own task — one guard, one definition of codegen currency.

  **PLANNER TRAP, found by enumeration — resolve before setting the floor.**
  `task proto:drift` currently hardcodes its vacuity floor as
  `if [ "${nfiles}" -lt 3 ]` (Taskfile.yml, `proto:drift`), expecting exactly
  `graph.pb.go`, `ui.pb.go`, `ui.connect.go`. The buf module contains **two**
  protos — `internal/schema/graph.proto` (the on-disk storage schema) and
  `internal/uiproto/uiv1/ui.proto` — and `buf.gen.yaml` applies plugins
  **module-wide**. A bare `local: protoc-gen-es` therefore emits TypeScript for
  `graph.proto` too, which the browser has no use for and which would then be
  committed and guarded forever.

  So the new floor is **4** if `graph.proto`'s TS is excluded (preferred) and **5**
  if it is not. Per rule `84d1gfpywd` the floor must move to the *correct* number,
  not merely upward: setting it to 5 and generating both is the failure that looks
  safe. Scope the plugin (buf v2 supports per-plugin input filtering) so only
  `ui.proto` produces TS, then set the floor to 4 and extend the `git ls-files`
  enumeration with the TS glob.
  — **Reversibility:** costly — the floor and the enumeration are read by CI; a
  wrong floor is a silently weakened guard, not a build failure.

- **D-08:** The wire encoding is **Connect's JSON**, not binary protobuf. Phase 1
  verified the whole RPC surface with plain `curl` POSTs returning readable JSON
  (`01-VERIFICATION.md`); this product is a debugging tool, so keeping every RPC
  inspectable in devtools and reproducible from a shell is worth more than wire
  size on a loopback socket.

### SPA Fallback Routing (RPC-03)

- **D-09:** Discrimination is **`http.ServeMux` precedence**, not a hand-maintained
  prefix allowlist. Register the SPA handler at `"/"`; Phase 1 already mounts the
  Connect service via `mux.Handle(uiv1connect.NewUIServiceHandler(...))`, whose
  generated constructor returns a `(path, handler)` pair, so it sits at its own
  prefix. The repo is on **Go 1.26**, where `ServeMux` resolves most-specific-
  pattern-wins (Go 1.22+), so RPC-vs-SPA precedence is handled by the standard
  library. Nothing to keep in sync when Phase 6 adds a streaming method.

- **D-10:** A **miss under the immutable-asset prefix returns 404**; a miss
  anywhere else serves `index.html` as a client-side route. This is criterion 2's
  actual teeth: serving HTML for a missing hashed chunk produces a browser
  MIME/module error that points nowhere near the real cause.
  Explicitly **rejected**: the "any path with a dot is an asset" heuristic —
  Phase 3's deep links will carry file paths containing dots, which would wrongly
  404.

- **D-11:** Cache headers: **content-hashed assets under `_app/immutable/` get a
  long-lived cache; `index.html` gets `no-store`.** The failure this prevents is
  specific and silent — a user who upgrades the binary keeps booting the cached
  old app shell against a new RPC surface, which presents as a broken UI rather
  than as a stale cache.

- **D-12:** The handler lives in a **new file under `internal/uiserver`** (e.g.
  `spa.go`), beside `degrade.go` / `truncate.go` / `originguard.go` — matching how
  Phase 1 organised the package: one concern per file, doc comment naming its
  decision IDs.

### JS Supply-Chain Gates

- **D-13:** The JS gates **fold into the existing `test` CI job**, not a new named
  job.
  Rationale, verified against the tree: the required-status-check contexts are a
  literal fixture at `internal/upgrade/taskfile_shape_test.go:43` — six ruleset
  contexts plus `pr-title` — and membership is defined in **GitHub ruleset
  20157557, which does not live in this repo**. A brand-new job is therefore not
  required-to-merge until someone edits the ruleset out of band, i.e. it is a gate
  in name only and can fail without blocking. `test` is already required, so
  folding in inherits blocking status from the first commit with no ruleset edit
  and no fixture change.

- **D-14:** BLD-05 uses **`strictDepBuilds: true`** — pnpm itself exits non-zero
  when any dependency carries an unreviewed build script — **plus a positive
  assertion that the setting is actually in effect.**
  This supersedes the approach recorded at scoping time (grep the
  `Ignored build scripts` warning), which predates `strictDepBuilds`. Grepping
  couples the gate to an upstream warning *string*: if pnpm rewords it, the grep
  silently stops matching and the gate passes — the exact vacuous shape rule
  `84d1gfpywd` exists to catch. The positive assertion is still required because
  `strictDepBuilds` is itself a negative guard: silently losing the setting
  reverts install to exit-0-with-a-warning and nothing would notice.
  Approval state is committed as the **`allowBuilds`** map in
  `pnpm-workspace.yaml` (this replaced pnpm 10's `onlyBuiltDependencies`), written
  by `pnpm approve-builds`, which records **denials as `false`** rather than
  omitting them — so the committed file states both halves.

- **D-15:** BLD-06's sibling non-vacuity assertion **counts scanned packages from
  `pnpm-lock.yaml`** and never reads `pnpm audit`'s exit code. `pnpm audit --json`
  has no scanned-package-count field, so the count must come from the lockfile.
  This proves the scan had real input; it deliberately does **not** attempt to
  prove the detector can fire.
  Considered and not chosen: a deliberately-vulnerable JS fixture mirroring
  `task vuln:selftest` (which builds `testdata/vulnredpoc` and asserts govulncheck
  exits **exactly 3** and names `GO-2026-5932`). That is strictly stronger, but the
  fixture rots when the advisory ages out. **Note for the researcher:** if a
  low-maintenance way to pin a JS advisory exists, this is worth revisiting — the
  Go side already ships both shapes.

- **D-16:** pnpm is pinned by the **`packageManager` field in `package.json` via
  Corepack** — one source of truth, honoured by both a clean checkout and CI.
  No `pnpm/action-setup` in the workflow, which would state the version a second
  time and need its own parity assertion. pnpm auto-enables frozen-lockfile in CI
  and **fails rather than silently rewriting** when the lockfile came from a newer
  major, so version skew surfaces loudly on its own.

### App Shell Scope

- **D-17:** **Tailwind v4 + `shadcn-svelte init` land in Phase 2**, not Phase 3.
  The phase is named "Embedded App Shell"; installing the design system here means
  Phase 3 opens with `shadcn-svelte add <component>` and no toolchain work. It also
  means the committed `web/build/` and its drift guard are exercised against real
  CSS output from day one rather than a near-empty page.
  Current shadcn-svelte requires **Svelte 5 + Tailwind v4**; Tailwind v4 wires in
  through **`@tailwindcss/vite`** (a Vite plugin), not PostCSS.

- **D-18:** `/` renders a **root layout with navigation placeholders for the four
  future views** (Browse / Workbench / Graph / Health), so Phases 3–6 each fill a
  slot rather than restructuring. This is also what makes criterion 2 honestly
  testable: a single-route app cannot demonstrate SPA fallback at all, and a route
  invented purely for the test proves less.

- **D-19:** The shell **makes a real `GetStatus` call and renders the result**,
  proving the full seam in this phase: embedded asset → generated TS client →
  Connect JSON → Phase 1's handler → real index data. Phase 1 proved that path
  with `curl`; this proves the browser can walk it. `GetStatus` is the right choice
  because it is the one RPC that answers even when the store is degraded
  (Phase 1 D-16), so the shell renders something honest in every state.
  Without this, the generated TS client would ship committed and drift-guarded
  **without ever having been executed** — a client that generates cleanly but does
  not work would pass every other Phase 2 gate.

### Known Limitation — `pnpm audit` cannot see vendored components

**Recorded deliberately, not deferred silently.** `shadcn-svelte add <component>`
fetches from a registry over the network and writes `.svelte` **source files** into
the repo, which are then committed. Those files never enter `pnpm-lock.yaml`, so
**BLD-06's audit gate structurally cannot see them.**

The boundary, stated so Phase 3 inherits it named rather than discovering it:
BLD-06 covers the dependency tree in `pnpm-lock.yaml`. It does **not** cover
registry-fetched component source.

Considered and **not** adopted for this phase: pinning the registry version and
asserting committed component source matches what the pinned registry emits — the
same drift discipline applied to `web/build/` and the generated TS. That is real
scope growth and BLD-06's requirement text does not ask for it. Phase 2 ships no
components, so the gap is not yet live; it becomes live the moment Phase 3 adds
one.

## Existing Code Insights

### Reusable Assets
- **`task proto:drift`** (`Taskfile.yml`): already implements exactly what BLD-03
  asks of the `web/build/` guard — scratch-tree regeneration, a count printed
  before any comparison, and a hard failure below a named floor. The SPA drift
  guard should be built in its image rather than invented.
- **`task vuln:selftest`** (`Taskfile.yml`): the repo's reference non-vacuity
  proof, and the model BLD-06's sibling assertion is measured against.
- **`internal/mcp/resources.go`**: the `go:embed` precedent — embedded FS declared
  beside the code that serves it, with the URI map as the single source of truth.
- **`internal/uiserver`'s file layout**: `degrade.go`, `truncate.go`,
  `originguard.go` — one concern per file, doc comment naming decision IDs. D-12
  follows it.

### Established Patterns
- **Guards report a count and are watched RED first** (rule `84d1gfpywd`,
  `ROADMAP.md:99`). Applies to the `web/build/` drift guard, the extended
  `proto:drift` floor, the `strictDepBuilds` assertion and the `pnpm audit`
  sibling assertion — four separate places in this phase.
- **Toolchain pinning lives in isolated modfiles** (`go.tool.mod`,
  `go.tool-lint.mod`, `go.tool-proto.mod`), never the root `go.mod`;
  `forbiddenToolPackages` in `taskfile_shape_test.go` enforces it. `package.json` +
  `pnpm-lock.yaml` are the JS analogue.
- **Additive-only proto discipline (D-02a)** — field numbers never renumbered,
  retired fields reserved. Any `ui.proto` change in this phase inherits it.
- **Env vars are paired with flags** (`serve.go:300`); the repo has **no config-file
  mechanism**, and Phase 1 explicitly declined to add one.

### Integration Points
- **`internal/uiserver/server.go:111`** — `mux := http.NewServeMux()`; the SPA
  handler registers at `"/"` alongside the existing Connect registration.
- **`originHostGuard`** wraps the whole mux as the outermost handler, so the SPA
  handler inherits the DNS-rebinding protection with no extra work — and **must
  not** be mounted outside it.
- **`buf.gen.yaml`** — one added plugin entry, scoped to `ui.proto` (D-07).
- **`.github/workflows/ci.yml` §`test`** — where every JS gate attaches (D-13).
- **Phase 1's UAT gap G-01-1** (`GET / -> 404`) closes here; that closure is
  criterion 1 and should be verified explicitly, not assumed.
