<objective>
Ship BLD-03: a drift guard that proves the committed `web/build/` matches the SPA source it was
built from AND that its committed bytes are the ones `task web:build` produced, reports both
counts it inspected, and has been watched fail four ways before it is trusted green — plus the CI
plumbing (BLD-01's frozen-lockfile install at the pinned pnpm version, and an actual rebuild) that
the guard and every later JS gate run on top of.

Purpose: `web/build/` is committed, which means a developer whose build diverges from CI's
silently ships a different app than the one the source describes. This is ROADMAP criterion 3.
The shape matters as much as the existence: the obvious imitation of `task proto:drift` —
regenerate and byte-compare — is provably wrong here, and this plan implements the shape that
works instead.

The cross-AI review found two holes in the first draft of that shape, and this plan closes both:

1. **The marker bound only the source tree.** A contributor could edit
   `web/build/_app/immutable/*.js` by hand, leave the marker untouched, and `task web:drift`
   would pass — while those edited bytes are precisely what `//go:embed all:build` ships to every
   user. RESEARCH Pitfall 1 rules out *regenerate-and-byte-compare*; it does not rule out hashing
   the committed output tree **in place**, which has no reproducibility dependency at all. The
   marker therefore gains a second, independent digest: a manifest of `web/build/`'s own file list
   plus per-file content hashes.
2. **CI never built anything.** The planned steps were setup-node, `web:deps`, `web:drift` — so
   CI proved the marker matched the source and never proved the pinned toolchain still produces a
   working build. A new `task web:build:verify` builds into a scratch directory and asserts
   structural invariants on the fresh output, deliberately kept separate from byte-identity.

Output: `task web:deps`, `task web:build`, `task web:build:verify`, `task web:drift`, a committed
four-line marker binding both source and output, and four new steps in the existing `test` CI job.
</objective>
