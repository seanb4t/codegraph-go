<objective>
Cut a real release through the migrated pipeline and prove every supply-chain claim against
assets re-downloaded from it — then leave behind an automated job that re-proves those claims on
every future release rather than only on the day a human checked.

Purpose: REL-08, and the only place REL-06's success criterion becomes observable
(`gh release view <tag> --json assets` listing exactly one checksums file covering every published
asset exactly once). Local verification is explicitly insufficient: a local `dist/` file never
passes through the real GitHub Releases upload path, the Sigstore transparency log, or the
attestation subject binding, so verifying against it can pass while the actually-published asset
is broken.

Publishing is one-way. Once release-please cuts the tag, the release exists on the public shipped
line, `codegraph upgrade` clients may consume it, and it cannot be withdrawn without a human
deleting a tag — which is exactly the authority D-06R reserves and D-07 forbids using. This plan
therefore opens the publish with a blocking decision checkpoint.

Output: a permanent post-release verification workflow, a published release, and a recorded
evidence set a third party can re-inspect.
</objective>
