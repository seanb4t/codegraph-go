<objective>
Cut a real release through the migrated pipeline and prove every supply-chain claim against
assets re-downloaded from it — then leave behind an automated job that re-proves those claims on
every future release rather than only on the day a human checked.

Purpose: REL-08, and the only place REL-06's success criterion becomes observable
(`gh release view <tag> --json assets` listing exactly one checksums file covering every published
asset exactly once). Local verification is explicitly insufficient: a local `dist/` file never
passes through the real GitHub Releases upload path, the Sigstore transparency log, or the
attestation subject binding, so verifying against it can pass while the actually-published asset
is broken.

Publishing is one-way. Once release-please cuts the tag, the release exists on the public shipped
line, `codegraph upgrade` clients may consume it, and it cannot be withdrawn without a human
deleting a tag — which is exactly the authority D-06R reserves and D-07 forbids using. This plan
therefore opens the publish with a blocking decision checkpoint.

Output: a permanent post-release verification workflow, a published release, and a recorded
evidence set a third party can re-inspect.
</objective>

    **Reversibility: one-way.** Once release-please publishes the tag and the Release, that release

    What the merge mechanics require, and what makes them easy to get silently wrong:

    - This repository is **squash-only** with `squash_merge_commit_title=PR_TITLE`. release-please
      parses the PR TITLE, not the commit subjects. The PR title must be `feat(release): …` so
      release-please computes a MINOR bump (v0.4.0 → v0.5.0, matching the milestone's prediction).
      Getting the title wrong yields no release at all — and therefore no REL-08 evidence and no
      Phase-2 RED baseline. Verify the title before merging.
    - The `feat:` type is honest rather than gamed: the release genuinely gains a new user-facing
      asset shape — `.zip` archives for browser download and Homebrew (REL-09).
    - No human runs `git tag`, and no `Release-As:` footer or `release-as` config key forces a
      version (D-06R). release-please computes it, creates the tag and the Release, and
      `release.yml` fires on that tag push.
    - The repo's `protect-main` ruleset requires PR + squash + linear history and six status
      checks; the merge is gated there too.
    - A standing global deny blocks agent `gh pr merge`, so a human performs the merge. That is
      the intended shape of this gate, not a workaround.
