<objective>
Replace the third-party SLSA generic-generator reusable workflow with GitHub's first-party
`actions/attest-build-provenance`, and update every artifact that tells a human or a machine how
to verify the result.

Purpose: D-09/D-10, decided unconditionally by the maintainer and NOT gated on research. Research
has since confirmed the incompatibility that D-10 anticipated: `slsa-verifier verify-artifact`
cannot verify `actions/attest-build-provenance` output — they are architecturally different
attestation formats. REL-08 and Phase 1's Success Criterion 3 both currently name
`slsa-verifier verify-artifact` as a claim that must pass, so the reword is mandatory, not
cosmetic. D-10 named `gh attestation verify` as its accepted fallback and research confirms it
works and needs no CLI beyond `gh`, which is already ambient in every Actions job.

This is a ONE-WAY change to a published verification contract: releases under the two attestors
carry different provenance formats and different builder identities, the shipped line becomes
permanently mixed, and the verification commands in SECURITY.md and README.md are already
copy-pasted by users. The irreversible event, however, is the PUBLISH — not this edit — and it is
gated by plan 01-05's Task 2 blocking checkpoint. The decision checkpoint that previously opened
this plan has been removed as dead ceremony over an already-binding D-10 choice; see
`<binding_decision>` below. This plan is therefore autonomous.

Output: a native attestation step, one shape test replacing another, four rewritten documents,
and a reworded REL-08.
</objective>

## The replacement verification command is `gh attestation verify` — BINDING, no checkpoint

A `checkpoint:decision` task previously stood here asking the maintainer to choose between
`gh attestation verify` and `slsa-verifier verify-github-attestation`. **It has been removed.**
Both cross-AI reviewers independently flagged it as dead ceremony that reopens an already-settled
question (Codex Plan-04 LOW; pi §3 LOW: "wasted ceremony… the `halt` path and the
`slsa-verifier verify-github-attestation` option are dead weight that could invite a relitigation
the milestone has already closed"). D-10 names `gh attestation verify` as its accepted fallback,
and the choice was re-adjudicated as binding earlier in this session.

**The command every artifact in this plan writes is, verbatim:**

`gh attestation verify <asset> -R seanb4t/codegraph-go`

Do not paraphrase it, do not vary it between files, and do not reopen the choice. Where Task 2 or
Task 2 previously said "the command selected at Task 1's checkpoint", it now means this string.

**Why removing the gate is safe.** REVERSIBILITY_GATES is on and the attestor swap IS one-way in
format — but the one-way event is the PUBLISH, not this edit. Nothing in this plan reaches a user
until plan 01-05's Task 2 checkpoint authorises the merge that lets release-please cut the tag.
That checkpoint is retained, is blocking, and is the correct place for the irreversibility gate.
Adding a second gate here bought no additional reversibility and cost a stall plus a relitigation
risk. `internal/upgrade/verify.go` contains zero SLSA/in-toto references, so `codegraph upgrade`
is indifferent to the attestor — the blast radius of this plan alone is documentation, one shape
test, and one requirement sentence.

**Fact this rests on** (RESEARCH.md Pitfall 1, cross-checked against the slsa-verifier README):
`slsa-verifier verify-artifact` CANNOT verify `actions/attest-build-provenance` output — they are
structurally different formats, and GitHub-native attestations live in GitHub's Attestations API
rather than as a standalone `.intoto.jsonl` release asset. So REL-08's current wording,
`docs/RELEASE.md` § b, `docs/RELEASE-PROCEDURES.md`, `SECURITY.md` and `README.md` all currently
instruct a command that fails against every post-migration release. Task 2's rewrite is mandatory,
not cosmetic.
</binding_decision>
