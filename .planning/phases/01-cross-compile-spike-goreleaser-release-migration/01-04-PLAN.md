<objective>
Replace the third-party SLSA generic-generator reusable workflow with GitHub's first-party
`actions/attest-build-provenance`, and update every artifact that tells a human or a machine how
to verify the result.

Purpose: D-09/D-10, decided unconditionally by the maintainer and NOT gated on research. Research
has since confirmed the incompatibility that D-10 anticipated: `slsa-verifier verify-artifact`
cannot verify `actions/attest-build-provenance` output — they are architecturally different
attestation formats. REL-08 and Phase 1's Success Criterion 3 both currently name
`slsa-verifier verify-artifact` as a claim that must pass, so the reword is mandatory, not
cosmetic. D-10 named `gh attestation verify` as its accepted fallback and research confirms it
works and needs no CLI beyond `gh`, which is already ambient in every Actions job.

This is a ONE-WAY change to a published verification contract: releases under the two attestors
carry different provenance formats and different builder identities, the shipped line becomes
permanently mixed, and the verification commands in SECURITY.md and README.md are already
copy-pasted by users. It therefore opens with a blocking decision checkpoint.

Output: a native attestation step, one shape test replacing another, four rewritten documents,
and a reworded REL-08.
</objective>

  <decision>
    Confirm the attestor swap and the replacement verification command before any published

  </decision>

  <context>
    D-09/D-10 already decided the swap unconditionally: `actions/attest-build-provenance` replaces
    the `slsa-framework/slsa-github-generator` reusable workflow, because the GitHub-native
    attestor is less custom infrastructure than a third-party reusable workflow, and changing the
    verification surface is acceptable now.

    What needs an explicit confirmation, not an inference, is the REPLACEMENT COMMAND — and the
    fact that this is one-way.

    Research finding (RESEARCH.md Pitfall 1, cross-checked against the slsa-verifier README):
    `slsa-verifier verify-artifact` **cannot** verify `actions/attest-build-provenance` output.
    They are structurally different formats — GitHub-native attestations live in GitHub's
    Attestations API and transparency log rather than a standalone `.intoto.jsonl` release asset.
    `slsa-verifier` ships a separate, dedicated subcommand for the native format,
    `verify-github-attestation`, which D-10 did not name.

    So REL-08's current wording, Phase 1's Success Criterion 3, `docs/RELEASE.md` § b,
    `docs/RELEASE-PROCEDURES.md` § 224, `SECURITY.md` and `README.md` all currently instruct a
    command that will fail against every post-migration release. That is not a bug in the release;
    it is the wrong verifier.

    De-risking fact, already established: `internal/upgrade/verify.go` contains ZERO SLSA or
    in-toto references. It verifies the cosign bundle over the binary. `codegraph upgrade` is
    completely indifferent to which attestor is used — the blast radius is documentation, one
    shape test, and one requirement sentence.

    **Reversibility: one-way.** Releases published under the native attestor and releases published
    under the generic generator carry different provenance formats and different builder
    identities. Reverting fixes future releases but leaves the shipped line permanently mixed, and
    the published verification instructions will already have changed. Recovery posture is patch
    forward (D-07) — never delete or re-push a tag.
  </context>

  <options>
    <option id="gh-attestation-verify">
      <name>`gh attestation verify &lt;asset&gt; -R seanb4t/codegraph-go` (D-10's stated fallback — RECOMMENDED)</name>
      <pros>No new CLI dependency — `gh` is already a hard requirement of the release path and ships on every runner and most developer machines. It is the pairing GoReleaser's own docs recommend alongside `actions/attest`. Simplest instruction for an external verifier to follow. Named by D-10 in advance, so choosing it is honouring a locked decision rather than making a new one.</pros>
      <cons>`slsa-verifier` disappears as the named tool in public-facing docs, breaking textual continuity with SECURITY.md and README.md as they read today. Verification becomes GitHub-account-shaped rather than tool-shaped.</cons>
    </option>
    <option id="slsa-verifier-github-attestation">
      <name>`slsa-verifier verify-github-attestation --attestation-path &lt;bundle&gt; --source-uri github.com/seanb4t/codegraph-go &lt;asset&gt;`</name>
      <pros>Keeps `slsa-verifier` as the named verification tool, so SECURITY.md/README.md's "verifiable with `slsa-verifier`" claim survives with a smaller textual diff and the SLSA framing stays intact.</pros>
      <cons>Adds a second CLI dependency (`slsa-verifier` binary) beyond `gh`, which is installed nowhere in this repo's CI today. Requires an extra step — downloading the attestation bundle first via `gh attestation download` — so the published instruction is two commands rather than one. Not the command D-10 named.</cons>
    </option>
  </options>

  <resume-signal>Select: gh-attestation-verify, slsa-verifier-github-attestation, or halt. The selection is written into every artifact this plan touches; do not proceed with a silent default.</resume-signal>
