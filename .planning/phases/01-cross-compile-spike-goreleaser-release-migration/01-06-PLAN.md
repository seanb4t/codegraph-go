<objective>
Resolve the `binary_signs:` `${artifact}` template against a REAL GoReleaser sign pipe before the
one-way release, and prove it produces four distinctly-named `.sigstore.json` sidecars rather than
four colliding ones.

Purpose: this plan exists entirely because of the cross-AI review's central structural finding.
This phase applies "never trust a gate you have not demonstrated" to every contract EXCEPT the two
pipes that `goreleaser release --snapshot --skip=publish,sign` structurally cannot reach. Of those
two, the publish pipe is genuinely unexercisable (plan 01-02 Task 3 pins its config instead, and
plan 01-05's checkpoint names the residual risk). The SIGN pipe is not — it only looked
unexercisable because keyless signing implies OIDC. A throwaway local cosign key removes that
implication and costs one job.

The stake is specific and severe. All four build entries in `.goreleaser.yaml` name the binary
`codegraph` (`:49, :67, :84, :98`). RESEARCH.md Pattern 2 ASSUMES `${artifact}` in `binary_signs:`
resolves to the archive-templated asset name (`codegraph_<tag>_<goos>_<goarch>`). If it instead
resolves to the build binary name, the release produces four files all called
`codegraph.sigstore.json`, three of which overwrite the others — and `codegraph upgrade` 404s for
every platform whose sidecar lost the race, AFTER it has already downloaded the new binary.
D-14 calls this "the one contract whose breakage bricks every user's `codegraph upgrade`", and
`--skip=sign` in every existing dry run means it would otherwise first resolve during the
production release, where D-07 forbids withdrawal.

Output: one Taskfile target, one canary job, and four recorded filenames.
</objective>
