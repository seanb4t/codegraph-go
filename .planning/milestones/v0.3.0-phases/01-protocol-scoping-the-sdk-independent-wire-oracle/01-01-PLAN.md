    `func NormalizeWithLedger(raw []byte, subs Substitutions) ([]byte, map[string]int)` and
    `func Normalize(raw []byte, subs Substitutions) []byte` delegating to it and discarding the
    ledger. The ledger maps each `Rule.Name` to the number of substitutions that rule performed on
    this input.

    **Every rule is anchored on the JSON field name that owns the value, never on the value
    alone** — D-04 says named-field placeholder substitution, and a bare value-replacement rule
    would silently erase the same string appearing in a field that must stay verbatim. The three
    rules, applied in this fixed order:
    (1) `repoDir` — the value of a `"path"`-family field only. Match with a regexp anchored on the
    field-name prefix (`"path":"`, `"file":"`, `"root":"`, `"repoPath":"`) immediately followed by
    the capture-time absolute fixture directory string, and replace only the directory portion of
    the captured value with `<REPO>`; handle the JSON-escaped form of the path as a second anchored
    alternative. The same absolute path appearing inside free-text markdown content is NOT
    normalized by this rule — see the `<REPO>` acceptance note below and plan 07's negative case.
    (2) `serverVersion` — the value of the `version` key inside the `serverInfo` object only,
    matched with a regexp anchored on `"serverInfo"` followed by a bounded, whitespace-tolerant
    `"version"` key match, replaced with `<VERSION>`. Do not anchor on the fully-compact literal
    `"serverInfo":{"name":"codegraph","version":"` alone: that assumes both exact key order and
    compact serialization, and if either changes the rule silently stops matching and the real
    version leaks into frozen bytes. The ledger below is what turns that silent death into a named
    failure.
    (3) `timestamp` — the value of a timestamp-named field (`"timestamp":"`, `"time":"`, `"ts":"`)
    whose value parses as RFC3339 / RFC3339Nano, replaced with `<TS>`. An RFC3339-shaped string in
    any other field is left verbatim.

    re-encode the transcript through `encoding/json` — a round trip erases field presence/absence
    and key ordering, which is the only place an `omitempty`-on-bare-bool regression is visible
    (D-04, explicitly rejected). Document the three rules in a package doc comment as the complete
    allowlist, and state for each whether any current transcript actually exercises it.

## Flagged planner assumption (VRFY-02 mechanism — surface, do not silently score as met)

**The repo-owned protocol literal cannot control the negotiated wire value in Phase 1, and this
plan does not pretend otherwise.**

Verified at source: `BuildServer` calls `server.NewMCPServer("codegraph", version, ...)`
(`internal/mcp/server.go:94`), where `version = "0.1.0"` is documented as this server's MCP
*implementation* version (`internal/mcp/server.go:26`), not the protocol revision. The negotiated
revision is produced solely by the unexported `(*MCPServer).protocolVersion` method in
`mark3labs/mcp-go@v0.56.0` (`server/server.go:1196`), which returns only a member of
`mcp.ValidProtocolVersions` or `mcp.LATEST_PROTOCOL_VERSION`. Enumerating every `func With…` in
that package confirms **there is no `WithProtocolVersion` server option in v0.56.0**. No caller can
inject a repo-owned literal while mark3labs is the backend.

This plan therefore implements the *assertion* mechanism and adds no invented wiring:
`internal/mcp.ProtocolVersion` is an **asserted compatibility pin**. It currently equals the SDK's
`LATEST_PROTOCOL_VERSION`, so a dependency bump that moved the SDK value turns the oracle's spec
anchor red — which is what REQUIREMENTS.md VRFY-02 ("asserted against a repo-owned literal", line
35) asks for.

**The unresolved conflict, surfaced for verify-phase rather than resolved here:** ROADMAP.md
success criterion 3 says the declared version **"reads from"** a repo-owned literal. That stricter
reading is not satisfiable in Phase 1 and lands in Phase 2, when the SDK swap supplies a backend
whose protocol revision a caller can actually supply. This plan does not edit ROADMAP.md or
REQUIREMENTS.md — reconciling the two wordings is the developer's call, and criterion 3 must not be
scored as fully met by this phase without that decision being made explicitly.
</verification>
