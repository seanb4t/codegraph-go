<objective>
Stand up the tap and the credential that writes it — a credential whose scope is a
structural property rather than a checkbox somebody has to remember.

Purpose: ROADMAP criterion 5 asks for a token that can write `seanb4t/homebrew-tap`
and nothing else. A classic repository-scoped token fails that outright, and a
fine-grained token passes it while carrying an expiry that becomes an operational
item exactly like the Developer ID certificate's. A GitHub App installed on one
repository makes the boundary a fact about the installation, which is why D-16 chose
it.

Two things about placement have to be settled on evidence rather than preference.
The first is where the token is minted. `release.yml` records that exactly one job in
the file may hold `id-token: write`, because that job's OIDC token is what produces
the cosign certificate subject the upgrade verifier anchors on — and every additional
Action inside that job sits within its reach. The existing guard forbids a second
*holder* of that permission, not a second *job*, so minting elsewhere is structurally
permitted. The second is whether a masked App token actually survives being passed
between jobs, which decides whether the first answer is usable at all. That is a
measurable fact about GitHub Actions and this plan measures it on a real run before
the release depends on it.

Output: the tap repository, the App-backed credential, the mint wired into
`release.yml` where the measurement says it belongs, and shape tests that hold the
scoping the same way the Apple secrets are already held.
</objective>

**Measure the job-output question.** RESEARCH.md's Open Question 2 recommends minting
the tap token in a separate job with no `id-token: write` and passing it to the
release job through job outputs, and records the operational tradeoff as the only open
part. There is a prior question underneath it that decides whether the recommendation
is usable at all: GitHub Actions masks the value `actions/create-github-app-token`
produces, and masked values are subject to redaction when they cross a job boundary as
an output. If redaction applies, the release job would receive an empty or redacted
string, GoReleaser would fall back to its default client, and the tap push would fail
— or worse, appear to succeed against the wrong repository. Neither the action's own
README nor the workflow-syntax page states the answer plainly; both were checked.

Measure it, cheaply and safely, before anything depends on it:

- Create a scratch branch and put a single probe workflow on it, triggered by `push`
  restricted to that branch name. Do not use a dispatch trigger: dispatch requires the
  workflow to exist on the default branch, and this one must never land there.
- Job A mints the token with the same pinned action and SHA `release-please.yml` uses,
  scoped by owner and to the tap repository only, and exposes it as a job output.
- Job B consumes that output and asserts, WITHOUT ever echoing the value: that it is
  non-empty, that its length is in a plausible range for an installation token, and
  that a single authenticated read against the tap repository using it succeeds while
  the same read against `seanb4t/codegraph-go` does not. Emit only booleans, the
  length, and the two status codes.
- Record the run URL and every emitted line. Then delete the scratch branch. It must
  never be merged: while it exists, a workflow outside the release file references the
  new secret names, which is precisely what Task 3's scoping test forbids.

The measured answer decides Task 3's structure. Both branches are legitimate and both
are recorded rather than silently chosen:

- **Token survives the hop** — mint in a separate job with no `id-token: write` and
  pass by output. This keeps D-16's stated concern fully addressed: no additional
  Action executes inside the job holding the OIDC token that produces the cosign
  certificate subject.
- **Token is redacted across the hop** — mint inside the release job, immediately
  before the release step, pinned by SHA. Record explicitly that this places one more
  Action inside the OIDC boundary, that it was chosen because the alternative was
  measured not to work rather than because it was preferred, and that the compensating
  controls are the SHA pin and the step-level scoping Task 3 asserts.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `seanb4t/codegraph-go`'s release run → `seanb4t/homebrew-tap` | A cross-repository write. The default release token cannot make it, which is the entire reason a second credential exists. |
| The OIDC-bearing release job → every Action executing inside it | That job's token produces the cosign certificate subject the upgrade verifier anchors on; anything running inside the job is inside that token's reach. |
| Repository secrets → the single job entitled to read them | Scope here is enforced by a test that enumerates workflows at runtime, not by convention. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-07 | Elevation of Privilege | The tap-writing credential's reach | high | mitigate | A credential able to write both repositories defeats ROADMAP criterion 5 and would let a compromised tap push reach the release repository. Mitigated structurally: a separate App installed on one repository, the mint additionally scoped to that repository at request time, a test asserting the new secret names are not the release-please App's, and plan 03-04's one-time recorded refusal. Residual and named: by D-17 this is proven once, so a later widening of the installation is not detected — recorded as an accepted limitation, not as coverage. |
| T-03-08 | Information Disclosure | A live installation token crossing a job boundary as an output | medium | mitigate | Cross-job output passing has a marginally larger blast radius than a token that never leaves the step context that created it. Mitigated by measuring the behavior on a real run before depending on it, by scoping the token to one repository at mint time so disclosure is bounded to a repository holding only a generated cask, by the token's roughly one-hour lifetime, and by never echoing the value in any probe or log. If the measurement says REDACTED, the placement moves inside the release job and the tradeoff inverts to the accepted-and-recorded one. |
| T-03-09 | Tampering | A release completing green with the tap credential absent or wrong | high | mitigate | An unset variable resolves to nothing and the cask client falls back to the release's own token; a variable set equal to the release token pushes with the wrong credential. Either produces a run that looks successful. Mitigated by two preconditions on the release target — present, and distinct — each demonstrated by running the target in the failing state, and by the plan-level prohibition against a quietly degraded release. |
| T-03-10 | Elevation of Privilege | Additional Actions inside the OIDC-bearing job | medium | mitigate | Every Action inside the release job sits within reach of the token producing the cosign certificate subject. Mitigated by preferring a separate mint job when the measurement permits it; when it does not, by pinning the added Action to the same 40-character SHA already trusted elsewhere in this repository, by scoping its inputs to step level, and by recording the widened surface in a comment rather than letting it land unremarked. |
