## Summary

This phase's mechanics are almost entirely governed by three files this session read directly: the pinned GoReleaser `v2.17.1` module's own `pkg/config/config.go` and `internal/pipe/cask/*.go`, and the real Homebrew 6.0.15 Ruby source installed on this machine (`/opt/homebrew/Library/Homebrew/cask/**`). Both confirm every locked decision in CONTEXT.md's Decisions section is directionally correct, with two consequential corrections the planner needs before writing tasks:

1. **D-18's parenthetical "(--snapshot/local release)" is not achievable as literally read.** `goreleaser release --snapshot` sets `skips.Publish`, and the entire cask-push (and GitHub-release-upload) machinery lives inside one `Publish` pipe (`internal/pipe/publish/publish.go`) that is skipped wholesale under that flag — `cask.Pipe{}.Publish()` is never even attempted under `--snapshot`. A snapshot run cannot be used to demonstrate a failing tap push. The only way to reproduce this locally is a real (non-snapshot) `goreleaser release` run against a **disposable scratch repo/tag** with a deliberately invalid `homebrew_casks.repository.token`, never against `seanb4t/codegraph-go`'s real release history. Flag this to the maintainer before planning D-18's evidence task — the mechanism named in CONTEXT.md needs replacing, not merely implementing.

2. **`generate_completions_from_executable`'s failure mode is a soft `opoo` warning, not a hard install failure** (`Cask::Artifact::GeneratedCompletion#write_completion` wraps its own popen-read of the binary in `rescue => e; opoo e`). This *reinforces* D-10 rather than contradicting it: the completions stanza cannot be relied on as BREW-05's gate even in principle, so the post-install hook's explicit `system_command` calls (which do NOT swallow errors — `SystemCommand.run!` defaults `must_succeed: true` and raises `ErrorDuringExecution`) are the only mechanism that can play this role. Document this as the mechanistic *reason* D-10 is correct, not just an assertion of it.

Three further primary-source findings materially help the planner and are new information beyond what CONTEXT.md already recorded: the exact `ids:` filter needed to avoid GoReleaser's `ErrMultipleArchivesSameOS` (must scope to `ids: [zip]`, excluding the `raw` binary archive entry, or the pipe throws because both archive shapes match the same OS/Arch pairs); the exact publish-pipeline ordering proving BREW-06's premise (`release.Pipe{}` runs strictly before `cask.Pipe{}` inside `publish.New()`'s literal Go slice, with the pipeline's own comment stating why); and a corrected man-page-count estimate (35, not "~27" — traced from the live command tree plus Cobra's auto-registered `completion` subtree, which the CONTEXT.md estimate did not account for).

**Primary recommendation:** Draft `homebrew_casks:` with `ids: [zip]` (never `raw`), leave `url.template` unset (the default is name-derived and immune to the repo's four-times-recorded Path-vs-Name defect class), mint the GitHub App token in a **separate job with no `id-token: write`** in `release.yml` (structurally permitted by the existing `TestOIDCWriteScopedToSingleGoreleaserJob` guard, which only forbids a *second holder* of that permission, not a second job), and correct D-18's reproduction mechanism to a scratch-repo run before the planner writes that task.

### Pattern 1: `ids:` scoping to avoid `ErrMultipleArchivesSameOS`

**What:** `homebrew_casks[].ids` is an archive-id filter (not a build-id filter — a different namespace, the same distinction this repo's `signs:`/`notarize.macos` blocks already document for their own `ids:` fields).

**When to use:** Always, in this repo — because `.goreleaser.yaml` declares TWO archive entries (`raw` and `zip`) covering the identical 4 platforms, and `cask.Pipe{}`'s default artifact filter (no `ids:` set) matches BOTH shapes simultaneously.

**Why it is load-bearing, not stylistic:** traced from `internal/pipe/cask/cask.go`'s `doRun()`:
```go
// Source: goreleaser/v2@v2.17.1, internal/pipe/cask/cask.go:217-231 (read this session)
filters := []artifact.Filter{
    artifact.ByGooses("darwin", "linux"),
    artifact.ByGoarches("amd64", "arm64", "all"),
    artifact.Or(
        artifact.And(
            artifact.Not(artifact.ByFormats("gz")),
            artifact.ByType(artifact.UploadableArchive),   // matches the `zip` entry
        ),
        artifact.ByType(artifact.UploadableBinary),         // matches the `raw` entry
    ),
    artifact.OnlyReplacingUnibins,
}
if len(brew.IDs) > 0 {
    filters = append(filters, artifact.ByIDs(brew.IDs...))
}
```
Without `ids:`, both the `raw` binary artifacts AND the `zip` archive artifacts match for every one of the 4 platforms, and `dataFor()` (`cask.go:450-454`) then hits:
```go
for _, v := range platformCounts {
    if v > 1 {
        return result, ErrMultipleArchivesSameOS
    }
}
```
`ErrMultipleArchivesSameOS = "one tap can handle only one archive of an OS/Arch combination. Consider using ids in the homebrew_casks section"` — the pipe's own error message names the fix. **Set `ids: [zip]` explicitly.**

### Pattern 2: Leave `homebrew_casks.url.template` unset

**What:** GoReleaser's default `ReleaseURLTemplate` (used whenever `url.template` is empty) is:
```go
// Source: goreleaser/v2@v2.17.1, internal/client/github.go:696-701 (read this session)
fmt.Sprintf(
    "%s/%s/%s/releases/download/{{ urlPathEscape .Tag }}/{{ .ArtifactName }}",
    downloadURL, ctx.Config.Release.GitHub.Owner, ctx.Config.Release.GitHub.Name,
)
```
This is `.ArtifactName` — **Name**-derived, not the `${artifact}` (env-var, **Path**-derived) shorthand this repo has hit the Path-vs-Name collision bug against four separate times (`signs:`, `sboms:`, and two prior instances per this repo's own comments in `.goreleaser.yaml`).

**When to use:** Leave `url.template` absent in the `homebrew_casks:` block entirely. If a future need arises to override it (e.g. a CDN mirror), use `{{ .ArtifactName }}`, never `${artifact}`.

**Why:** `dataFor()` calls `tmpl.New(ctx).WithArtifact(art).Apply(cfg.URL.Template)` per platform — if `url.template` is left empty, `cfg.URL.Template` is populated from `cl.ReleaseURLTemplate(ctx)` (the safe default above) BEFORE templating; only an explicit, hand-written `url.template` using `${artifact}` would reintroduce the collision class.

### Pattern 3: The post-install hook as BREW-05's gate

**What:** `homebrew_casks.hooks.post.install` is templated Go-template text emitted verbatim inside a `postflight do ... end` Ruby block (see `cask.rb`'s template, read this session). The available Ruby context is `Cask::DSL::Postflight < Base`, which delegates to the cask object:
```ruby
# Source: /opt/homebrew/Library/Homebrew/cask/dsl/base.rb:25 (read this session, Homebrew 6.0.15)
def_delegators :@cask, :token, :version, :caskroom_path, :staged_path, :appdir, :language, :arch
```
So `token`, `version` (the cask's own declared version — set from GoReleaser's `.Version`/`.Tag` at render time), `caskroom_path`, `staged_path`, `appdir`, `language`, `arch` are all directly callable inside the hook body with no prefix. `HOMEBREW_PREFIX` is a top-level Ruby constant available process-wide (used throughout Homebrew's own cask internals, e.g. `cask/artifact/generated_completion.rb:171`), so `#{HOMEBREW_PREFIX}/bin/codegraph` resolves correctly.

**Failure semantics (the load-bearing part of D-10):** `system_command` calls `SystemCommand.run!`, whose default is `must_succeed: true`:
```ruby
# Source: /opt/homebrew/Library/Homebrew/system_command.rb:129-134,164-166 (read this session)
def self.run!(executable, args: [], ..., must_succeed: true, ...)
  run(executable, args:, ..., must_succeed:, ...)
end
...
result = Result.new(command, @output, T.must(@status), secrets: @secrets)
result.assert_success! if must_succeed?   # raises ErrorDuringExecution on non-zero exit
```
And the caller, `Cask::Installer#install_artifacts`, does NOT swallow that exception — it rolls back already-installed artifacts and re-raises:
```ruby
# Source: /opt/homebrew/Library/Homebrew/cask/installer.rb:330-354 (read this session)
artifact.install_phase(...)
...
rescue => e
  begin
    already_installed_artifacts&.each { |artifact| ... revert ... }
  ensure
    purge_versioned_files
    raise e
  end
```
`#install` (the top-level entry point) calls `install_artifacts` with no further rescue, so the exception propagates all the way out and `brew install` exits non-zero. **This is a primary-source, mechanistic confirmation of D-10 — not an inference.**

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| "Does the binary actually run after install" | A separate post-release CI job that `brew install`s and probes | The post-install hook itself (D-10) | A separate CI job checks a DIFFERENT event than the one BREW-05 cares about — the first real user's install. Rejected in CONTEXT.md already; this session's Ruby trace confirms the hook mechanism genuinely can play this role (unlike `generate_completions_from_executable`, which cannot — see Pitfall 1) |
| Shell completion generation | A `tools/`-generated completion file checked into the repo or the zip | Cobra's built-in `completion <shell>` + GoReleaser's `generate_completions_from_executable` | Already verified working (D-06); Homebrew's own `GeneratedCompletion#install_phase` popen-reads the installed binary, so completions structurally cannot go stale |
| Man page roff formatting | A hand-rolled roff writer | `cobra/doc`'s `GenManTree` (wraps `go-md2man`) | Roff is a fussy, easy-to-get-wrong format; `go-md2man` is the same renderer Docker/Moby/containerd/`gh` ship |
| Cross-repo write-scoped credentials | A classic PAT with manual scope discipline | GitHub App installation token, installed only on the tap repo | A PAT's scope is a checkbox that can silently widen later; an App's installation is a structural boundary — criterion 5 (the negative proof) is a property of the App's *installation*, not of anyone remembering to keep a checkbox narrow |

**Key insight:** Every mechanism this phase needs (completions, man pages, install-time validation, tap credential scoping) already has a first-class, primary-source-verified home in either GoReleaser's `homebrew_casks:` pipe or Homebrew's own Cask DSL. The only genuinely new code this phase writes is the `codegraph man <dir>` Go subcommand — everything else is configuration.

## Common Pitfalls

### Pitfall 1: `generate_completions_from_executable` cannot substitute for a broken-cask gate

**What goes wrong:** A planner might assume completions generation, since it also executes the binary, could serve (or reinforce) BREW-05's gate.

**Why it happens:** `Cask::Artifact::GeneratedCompletion#write_completion` wraps its own execution of the binary in a blanket rescue:
```ruby
# Source: /opt/homebrew/Library/Homebrew/cask/artifact/generated_completion.rb:138-148 (read this session)
def write_completion(completion, executable)
  ...
rescue => e
  opoo "Failed to generate #{completion.fetch("shell")} completions from #{executable}: #{e}"
end
```
`opoo` is a warning, not a raise. A binary that cannot execute at all will make completions generation warn and continue — `brew install` still succeeds.

**How to avoid:** Rely exclusively on `hooks.post.install`'s explicit `system_command` calls (D-10/D-11) for the gate. Document this mechanistic reason in the plan/PLAN.md rationale, not just the decision.

**Warning signs:** If a future contributor "simplifies" the cask by dropping the postflight hook and pointing to `generate_completions_from_executable` as "good enough" evidence the binary runs, that is this exact regression.

### Pitfall 2: Reusing the release-please GitHub App for the tap

**What goes wrong:** `release-please.yml` already mints a GitHub App installation token (`actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3.2.0`, using `secrets.APP_ID`/`secrets.APP_PRIVATE_KEY`) for tag/PR creation on `codegraph-go` itself. [VERIFIED: .github/workflows/release-please.yml:73-84, read this session]

**Why it happens:** It is the path of least resistance to reuse an already-working App-token pattern.

**How to avoid:** D-16 requires a credential that can write `seanb4t/homebrew-tap` and CANNOT write `seanb4t/codegraph-go` (criterion 5). The release-please App is, by definition, installed on `codegraph-go` (it needs `contents: write`/`pull-requests: write`/`issues: write` there). Reusing it for the tap push would either (a) fail because it has no installation on `homebrew-tap`, or (b) if additionally installed there, would still be able to write `codegraph-go` — failing criterion 5 outright. **A second, distinct GitHub App, installed on `homebrew-tap` only, is required.** The action version/pin (`v3.2.0`, SHA `bcd2ba49...`) can and should be reused verbatim — only the App identity and secret names differ.

**Warning signs:** A plan or PR that reuses `secrets.APP_ID`/`secrets.APP_PRIVATE_KEY` for the tap-token-minting step.

### Pitfall 3: D-18's "--snapshot" cannot reach the cask-push failure path

**What goes wrong:** A plan task literally runs `goreleaser release --snapshot` (or `--snapshot --skip=publish,sign`, this repo's existing `release:dry-run` idiom) expecting to observe a failed tap push.

**Why it happens:** `--snapshot` sets `skips.Publish` (`cmd/release.go:161-163`, read this session: `if options.autoSnapshot ... ctx.Snapshot = true` and `if ctx.Snapshot { skips.Set(ctx, skips.Publish, skips.Announce, skips.Validate) }`), and `publish.Pipe{}.Skip(ctx)` is `skips.Any(ctx, skips.Publish)` — the WHOLE publish pipeline (including `cask.Pipe{}.Publish()` and `release.Pipe{}.Publish()`) never runs. There is no partial-skip flag that reaches only the cask publisher while still attempting it.

**How to avoid:** Reproduce the failure with a real (non-`--snapshot`) `goreleaser release` invocation against a **disposable scratch git repo and tag** — never the real `codegraph-go` release history — with `homebrew_casks.repository.token` deliberately pointed at an invalid/unauthorized value. This satisfies D-18's actual intent ("never against a published release") without relying on a flag that structurally cannot demonstrate the failure. **Flag this to the maintainer before planning** — it is a correction to a locked decision's stated mechanism, not merely an implementation detail.

**Warning signs:** A plan/task whose acceptance criterion is "run `task release:dry-run` and observe the cask push fail" — `release:dry-run` (Taskfile.yml:716+ family) uses `--snapshot --skip=publish,sign` per its own established idiom, which cannot reach this failure.

### Pitfall 4: MANPATH does not include `/opt/homebrew/share/man` by default in a non-interactive/clean environment

**What goes wrong:** `man codegraph` is assumed to "just work" the moment the hook writes pages under `$(brew --prefix)/share/man`.

**Why it happens:** [VERIFIED: commands run this session on this machine, Apple Silicon, `/opt/homebrew` prefix]
```
$ manpath | tr ':' '\n' | grep -i homebrew
/usr/local/share/man
/opt/homebrew/share/man
$ env -i /usr/bin/manpath
/usr/local/share/man:/usr/share/man:...
```
In an interactive shell (this session's fish shell, which has sourced `brew shellenv`), `/opt/homebrew/share/man` IS on the resolved manpath. In a genuinely clean environment (`env -i`, no shell profile sourced), it is NOT — only `/usr/local/share/man` (the Intel path) is present, via `/etc/manpaths` (`cat /etc/manpaths` → `/usr/share/man`, `/usr/local/share/man`; `/opt/homebrew/share/man` is absent from that system-level file). `/opt/homebrew/share/man` reaching `manpath` depends entirely on `brew shellenv` having exported `MANPATH` in the user's shell profile — which is Homebrew's own standard post-install instruction, so it holds for essentially every real interactive brew user, but NOT for a bare script or CI environment that never sourced a shell profile.

**How to avoid:** Document this explicitly in `docs/RELEASE.md`/user-facing docs rather than assuming it "just works" — and if the phase needs an automated `man codegraph` check (e.g. for BREW-04's verification), invoke `man` inside a shell that has run `eval "$(brew shellenv)"` first, or use `man -M "$(brew --prefix)/share/man" codegraph` to bypass MANPATH resolution entirely for the verification step.

**Warning signs:** A verification task that runs bare `man codegraph` inside a non-interactive CI shell and reports false-negative failure, or (worse) false-positive success because the runner's image happens to have Homebrew's shellenv already sourced in `.bashrc`/`.zshrc` while a genuinely clean end-user machine would not.

2. **GitHub App token placement (D-16's flagged question) — evidence gathered, not yet a maintainer decision.**
   - What we know: `TestOIDCWriteScopedToSingleGoreleaserJob` only forbids a SECOND holder of `id-token: write`, not a second job in `release.yml`. Structurally, minting the tap App token in a new job with no `id-token: write` is compatible with the existing guard.
   - What's unclear: the operational cost of passing a live installation token across a job boundary via `needs.<job>.outputs.<name>` (GitHub auto-masks `actions/create-github-app-token`'s own output via `core.setSecret()`, but cross-job output passing is a documented, if standard, GitHub Actions pattern with a marginally larger blast radius than a same-job token that never leaves the job's own step context).
   - Recommendation: mint in a separate, `id-token`-free job (keeps D-16's stated concern — "every additional Action inside the OIDC job sits within its reach" — fully addressed) and pass the token via job outputs; document the marginal tradeoff in the plan rather than silently picking one.
