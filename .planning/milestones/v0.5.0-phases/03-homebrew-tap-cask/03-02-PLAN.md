<objective>
Turn the proven slice into the real cask: the install gate that BREW-05 actually
names, the completions BREW-03 names, the sentinel Phase 4 will read, and the removal
that matches the creation.

Purpose: plan 03-01 proved the mechanism — a hook can execute the installed binary
and its effects land. That is not yet a gate. A hook that runs `codegraph man` and
ignores what came back is the exact shape this repository has a standing rule against:
it passes whether or not it did anything, and when its anchor stops matching, the
symptom is silence rather than an error. D-11 closes that with two assertions covering
two genuinely different failures — "did not run" and "ran, but is the wrong artifact"
— and those two assertions are, by D-12's own accepted cost, the ONLY permanent
protection this gate ever gets. There is no automated re-fire. They are load-bearing.

The other half of this plan is the symmetry D-05 bought. Man pages and the sentinel
are written by a hook into the Homebrew prefix, and brew does not track files a hook
writes. They survive `brew uninstall` unless something removes them. One matched pair
in one config block, so a future reader finds both halves in the same place.

Output: a `homebrew_casks:` block that is complete, and shape tests that hold each
non-obvious field as a property rather than as a literal string.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| The downloaded archive → the installed binary the hook executes | Everything before this point is the release pipeline's guarantee; everything after is this hook's. The hook is where the two meet on the user's machine. |
| The hook's assertions → the user's belief that the install succeeded | A green `brew install` is the only signal most users will ever read. |
| The sentinel → `internal/upgrade` in Phase 4 | A file written by Ruby on the user's machine, read later by Go on the same machine, with no schema negotiation between them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Tampering | The two post-install assertions — the only permanent protection this gate gets | high | mitigate | D-12 accepts that the RED proof does not re-fire, which makes these two assertions the whole standing guard. A version check written as containment rather than equality would pass for a mismatched version sharing a prefix, and a page check that only tests exit status would pass for a binary that ran and wrote nothing. Mitigated by requiring equality on normalized values, by requiring the page assertion to read the directory rather than the exit code, and by Task 1's deliberate version perturbation which records the assertion firing. |
