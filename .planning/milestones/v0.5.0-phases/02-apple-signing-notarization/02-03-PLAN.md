<objective>
Give the real-binary test harnesses a seam that points them at an already-built
binary — and make that seam incapable of silently falling back.

Purpose: ROADMAP Phase 2 criterion 4 requires the full CLI and MCP integration
suite to run green against the notarized, hardened-runtime binary ITSELF rather
than a locally rebuilt one, so a library-validation load failure surfaces as a
test failure instead of as a user's first-run crash. Neither harness can do that
today: both hardcode a `go build` of the checked-out source. The precedent to
transplant already exists in this repository — the release-verification e2e test
resolves its artifact from the environment before falling back.

The design constraint that matters more than the seam itself: a fallback on a bad
override would reproduce this project's signature failure — a green run that
verified something other than what it claimed. So the resolver has exactly two
outcomes when the variable is set: use that file, or abort by name.

Output: a pure, unit-tested path resolver consumed by both `TestMain` functions.
This seam is what makes D-10 executable — the criterion-4 suite runs inside the
existing post-release verification workflow, against the re-downloaded published
asset rather than a locally rebuilt one, so a failure is caught after publish and
handled patch-forward rather than lengthening the single unrehearsable path.
</objective>

    - `resolveTestBinPath("")` returns `useEnv=false`, no error — the caller falls through to the existing build path.
    - `resolveTestBinPath(<path to an existing regular file with an executable mode bit>)` returns that path with `useEnv=true` and no error.
    - `resolveTestBinPath(<path that does not exist>)` returns an error whose message names both the environment variable and the path.
    - `resolveTestBinPath(<path to a directory>)` returns an error naming the variable and stating the path is not a regular file.
    - `resolveTestBinPath(<path to an existing regular file with no executable mode bit>)` returns an error naming the variable and stating the file is not executable.
    - `resolveTestBinPath(<relative path to an existing executable>)` returns an ABSOLUTE path — every test in the package spawns the binary from a different working directory, so a relative override would resolve differently per test.
    - No input causes the function to return `useEnv=true` together with a non-nil error, and no non-empty input returns `useEnv=false` with a nil error. There is no third outcome; that absence is the property that forbids a silent fallback.
    - The resolver's checks are STAT-LEVEL only, follow UNIX mode semantics deliberately, and the doc comment says both. Addresses review concern (codex LOW): mode-bit checking is platform-specific, and while this repository's harnesses target macOS and Linux only, the comment should state that the choice is intentional rather than leave a future reader guessing whether a non-Unix host was overlooked. Addresses review concern (codex MEDIUM): a mode bit proves neither architecture compatibility nor that the file is a valid Mach-O, so the resolver rejects obvious errors and nothing more. The real "does this binary actually run on this machine" question is answered by the suite itself failing — which under criterion 4 is exactly the signal wanted, since a hardened-runtime library-validation failure should surface as a test failure. Do not add a probe-execute here; a resolver that runs the binary to check it can be run is both a redundant surface and a foot-gun in a path that also handles untrusted downloads.
