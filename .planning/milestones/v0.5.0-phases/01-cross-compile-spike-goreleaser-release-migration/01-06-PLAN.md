<objective>
Resolve the signing and SBOM templates against REAL GoReleaser pipes before the one-way release,
and prove each produces four distinctly-NAMED published artifacts rather than four colliding ones.

Purpose: this plan exists entirely because of the cross-AI review's central structural finding.
This phase applies "never trust a gate you have not demonstrated" to every contract EXCEPT the two
pipes that `goreleaser release --snapshot --skip=publish,sign` structurally cannot reach. Of those
two, the publish pipe is genuinely unexercisable (plan 01-02 Task 3 pins its config instead, and
plan 01-05's checkpoint names the residual risk). The SIGN pipe is not — it only looked
unexercisable because keyless signing implies OIDC. A throwaway local cosign key removes that
implication and costs one job.

The stake is specific and severe. All four build entries in `.goreleaser.yaml` name the binary
`codegraph` (`:49, :67, :86, :98`). RESEARCH.md Pattern 2 ASSUMES `${artifact}` resolves to the
archive-templated asset name (`codegraph_<tag>_<goos>_<goarch>`). It does not: GoReleaser expands
`${artifact}` from an artifact's PATH, while the release pipe publishes that artifact under its
NAME, and for a `formats: [binary]` archive those two DIFFER because the rename lives only in
metadata. So the four published signature assets all carry the name `codegraph.sigstore.json`,
three of which clobber the others at upload — and `codegraph upgrade` 404s for every platform
whose sidecar lost the race, AFTER it has already downloaded the new binary. D-14 calls this "the
one contract whose breakage bricks every user's `codegraph upgrade`", and `--skip=sign` in every
existing dry run means it would otherwise first resolve during the production release, where D-07
forbids withdrawal.

The cycle-3 review established that this is one DEFECT CLASS, not one defect, and that the
`sboms:` pipe carries it identically: `documents: ["${artifact}.spdx.json"]` names every SBOM
record `codegraph.spdx.json`, and `SBOM` is release-uploadable. Today's shell pipeline
(`.github/workflows/release.yml:271-278`) iterates the ALREADY-RENAMED assets and emits four
distinct `codegraph_<tag>_<goos>_<goarch>.spdx.json` files, so collapsing them to one is a
REGRESSION against D-17, DIST-03 and REL-09 — and `replace_existing_artifacts: true` makes it
silent. Both pipes run under `--skip=publish`, so ONE rehearsal run proves both.

It also established that the oracle must read NAMES, not on-disk filenames: for `formats:
[binary]` outputs the on-disk basenames are identical under the broken config and the correct
fix, so a filesystem glob false-REDs the preferred remediation and is blind to exactly the
quantity that collides at publish.

Output: one Taskfile target, one canary job, and eight recorded artifact names — four signature,
four SBOM.
</objective>
