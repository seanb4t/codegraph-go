<objective>
Make both `pull_request_target` workflows' multi-line `$GITHUB_OUTPUT` writes unterminable by a
fork-controlled file path, and pin it with a harness that exercises the shell block the workflows
actually ship.

Purpose: GH #15 is a real, if narrow, GitHub Actions multi-line-output injection: a fork PR that
adds a file whose path is exactly the fixed heredoc delimiter closes the heredoc early and lets the
remaining paths be interpreted as further `$GITHUB_OUTPUT` assignments. Both workflows carry the
byte-identical vulnerable shape and both run under `pull_request_target` with a write-capable token.

**Correction to the researched fix shape, discovered during planning and load-bearing:**
01-RESEARCH.md § Investigation 6 and 01-PATTERNS.md both recommend extracting the block into a shared
`scripts/write-multiline-output.sh` invoked from both workflows. That is NOT viable for
`require-issue-link.yml`: that workflow performs **no checkout at all**, which its own header comment
records as a security property under `pull_request_target` ("Safe here: NO checkout... No head code
executes"). A repo script is not on disk in that job, so calling one would require adding a checkout —
trading a narrow injection defect for a broader one. The delimiter is therefore generated **inline in
both files**, and the "fix only one" risk is closed a different way: the harness extracts and
exercises BOTH workflows' blocks, so a single-file fix leaves it red.

Output: `scripts/check-workflow-output-delimiter.sh`, a Taskfile target, and the per-run delimiter
in both workflows.

**TDD note:** this is a shell harness, not a Go or TAP test. RED→GREEN is carried by this plan's own
verify gates plus pasted transcripts.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| fork PR author → `pull_request_target` job | the file paths a fork chooses flow into a job running with the base repository's write-capable token; the author fully controls those strings |
| `$GITHUB_OUTPUT` file → consuming step's environment | anything that reaches this file becomes a step output, and step outputs are interpolated into later steps' env and `if:` expressions |
| the repository working tree → a `pull_request_target` job | `require-issue-link.yml` deliberately has NO checkout, so no repo file — including a helper script — is reachable from it |
