# Feature Landscape: v0.14.0 "Polish & Agent Reach"

**Domain:** Go CLI polish (color/help UX) + multi-harness AI-agent skill/instructions/nudge distribution
**Researched:** 2026-09-14
**Scope:** CLI glow-up, verb fold, grouped help, agent reach (skill/instructions/nudge across 8 harnesses), Codex parity. Bug-burn-down bucket (WINDOWS #26–36, GH issues) is NOT covered here — it's mechanical fix work, not a "what does this feature typically look like" question.

## Table Stakes

Features users/agents expect from a 2026-grade Go CLI + MCP-shipping tool. Missing = feels dated or broken relative to peers.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| `NO_COLOR` honored (any non-empty value disables color) | De facto Unix standard; codegraph **already does this** via `present.ChoosePresentation(isTTY, noColor)` — table stakes already met, don't regress it | Low (preserve) | `internal/cli/present/tty.go`. gh CLI has had open bugs (2026-05, `cli/cli#13335`) where `NO_COLOR`/`CLICOLOR=0` were silently ignored after a refactor — a cautionary tale: color-seam changes must keep a regression test pinning this, not just eyeball it. |
| TTY-gated styling; plain output when piped | Piping into `less`/scripts/agents must not leak ANSI; codegraph already TTY-gates via `isTTY` | Low (preserve) | Same seam. `present` package already never reads env/fd itself (D-03) — good separation, keep it. |
| Agent/MCP output path byte-unchanged by the color work | Every downstream contract (MCP wire oracle, agent parsers) depends on this; explicitly called out in milestone scope | Medium (discipline, not code) | Requires the `present` archtest boundary (D-01 in styles.go: "the sole home for lipgloss styling") to keep holding as more verbs move onto it. |
| `--help` readable at a glance for a 24-verb (soon ~22-verb) surface | A flat, ungrouped list of 20+ subcommands is a known UX failure mode once a CLI passes roughly a dozen verbs — this is why gh, docker, kubectl all group | Low–Medium | `cobra.Group`/`AddGroup` is built into the already-adopted `spf13/cobra` v1.9.x — no new dependency. [cobra.dev](https://cobra.dev/docs/how-to-guides/working-with-commands/) (official, HIGH confidence). |
| A renamed/removed verb tells the user the new name and exits non-zero, for at least one release | Maintainer has already decided this (see milestone_context) — it's the standard "hard deprecation" shape used by mature CLIs (see kubectl below) | Low | Do **not** use bare Cobra `Command.Deprecated` for this — see Anti-Features below, it has the wrong semantics. |
| Skill + instructions + MCP config reach every harness that has *any* mechanism for each | Directly named in milestone scope (AGENT-04…07 un-deferred); competitor MCP-server-shipping tools increasingly ship a skill package alongside the server rather than MCP-config-only | Medium–High | See Agent Reach section — highly harness-specific, must be verified per-harness not assumed uniform. |
| Non-blocking nudge, never a denial | Explicit reframe in milestone scope: GUARD-HOOK-01/02 went from "redirect" (could have implied blocking) to "add context" | Low–Medium | Precedent already shipped for Claude Code SessionStart (`session-nudge.sh`) — this milestone's job is PreToolUse (a different event) plus porting the *pattern* to other harnesses' equivalent mechanisms. |
| Codex parity: project-local skill reachable, not just global MCP | Codex is a harness the maintainer actually uses (stated in milestone rationale); current `codexTarget.SupportsLocation` returns `false` for `LocationLocal` unconditionally, which per current research is **now stale** — see Codex section | Medium | This is the single highest-value finding in this research — see below. |

## Differentiators

Not universally expected, but valuable given this specific project's shape (agent-facing CLI, multi-harness distribution).

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Full semantic color palette (headers/labels/values/paths/counts/warnings/errors as distinct hues, not just bold/faint/underline) | Current palette (`styles.go`) has exactly 3 styles, all monochrome (`Bold`, `Faint`, `Bold+Underline`) — zero actual color. A real palette (e.g. path=cyan, count=magenta/number-accent, warning=yellow, error=red) is the visible "glow-up" the milestone promises and matches what gh/glamour-based tools do by default | Medium | `charm.land/lipgloss/v2` is already the pinned dependency (D-01 in styles.go) — this is a within-package expansion, not a new dependency. |
| Adaptive light/dark palette (`lipgloss.AdaptiveColor` / `HasDarkBackground`) | Terminal background varies per user; a palette that reads badly on `Solarized Light` or macOS Terminal's light theme is a real, reported class of complaint for TUI/CLI tools | Medium | `lipgloss.HasDarkBackground(os.Stdin, os.Stdout)` is the official v2 API ([pkg.go.dev/charm.land/lipgloss/v2](https://pkg.go.dev/charm.land/lipgloss/v2), HIGH confidence, official docs). Must be read once at the `internal/cli` call sites per the existing D-03 discipline (present package itself stays side-effect-free), not inside `present`. |
| `--color=auto\|always\|never` flag, layered under/over `NO_COLOR` | Table stakes is honoring `NO_COLOR`; a differentiator is giving the user an *override* for the opposite case — forcing color into a pipe (e.g. `codegraph status --color=always \| less -R`) or forcing it off without touching env. gh has open, unresolved feature requests for exactly this ([cli/cli#9751](https://github.com/cli/cli/issues/9751), [cli/cli#4035](https://github.com/cli/cli/issues/4035)) — i.e. gh itself does *not* have this yet, so shipping it is a genuine differentiator, not table stakes | Low–Medium | Precedence convention to adopt (matches ripgrep/git/most modern CLIs): explicit `--color=always` wins over `NO_COLOR`; `--color=never` wins over a TTY; bare (no flag) falls back to the existing `isTTY && NO_COLOR==""` logic. `CLICOLOR_FORCE` (any value) is a secondary, lower-precedence env convention some tools (gh via `CLICOLOR`) also honor — optional, lower priority than the flag. |
| `charmbracelet/fang` as the help/error/version chrome instead of hand-rolled lipgloss help templates | Fang is a thin wrapper over Cobra apps (`fang.Execute(rootCmd)`) adding styled help/errors/version/manpages/completions "for free," actively maintained into 2026 ([github.com/charmbracelet/fang](https://github.com/charmbracelet/fang), MEDIUM confidence — official repo, but library is explicitly labelled "experimental" by its own maintainers) | Low to adopt, Medium to evaluate fit | Milestone scope already says "evaluate `fang` before any help template is hand-rolled" — this research confirms it's a real, current, low-friction option worth spiking rather than skipping straight to a hand-rolled template. Risk: it wraps `Execute()`, so it needs to compose with this project's existing `SilenceUsage`/`SilenceErrors` + caller-prints-errors convention (`cmd/codegraph/main.go`) — verify that composition in a spike, don't assume. |
| Session-start-style "skill list at conversation start" equivalent on harnesses that don't have Claude-style hooks (Gemini CLI, Antigravity) | These harnesses don't need a *nudge hook* at all — their skill-discovery mechanism already injects skill names+descriptions into the system prompt automatically at session start. "Reach" there is entirely a packaging/placement problem (right directory, right `SKILL.md` filename case), not a hook-authoring problem | Low (once directories are right) | See Agent Reach table — this is why AGENT-04…07 can un-defer cheaply for some harnesses and expensively for others. |
| Codex PreToolUse hook mirroring the Claude Code nudge | Codex CLI shipped a `hooks.json` PreToolUse mechanism (first in v0.114, March 2026) with a JSON shape ([codex.danielvaughan.com, MEDIUM confidence — cross-checked against agenticcontrolplane.com and hookstack.app independently](https://codex.danielvaughan.com/2026/04/15/codex-cli-hooks-complete-guide-events-policy-patterns/)) close enough to Claude Code's own (`matcher` + `hooks[].type=command`) that the existing `.claude/hooks/session-nudge.sh` pattern is directly portable in spirit | Medium | **Caveat, load-bearing**: this hook system is explicitly documented as experimental and **disabled by default**, and **not available on Windows**. Milestone scope already hedges with "if one exists" — treat as differentiator-if-feasible, not a hard requirement, and verify in a real Codex session before counting it done. |

## Anti-Features

Things that would be noise, break scripts, or violate the milestone's own stated constraints. Explicitly do NOT build these.

| Anti-Feature | Why Avoid | What to Do Instead |
|--------------|-----------|---------------------|
| Using bare Cobra `Command.Deprecated` for the verb-rename stubs | Cobra's built-in `Deprecated` field prints a warning **but the command still executes** — it does not stop, does not change the exit code, and does not refuse to run ([cobra.dev](https://cobra.dev/docs/how-to-guides/working-with-commands/), official docs, HIGH confidence, consistent across every Cobra version's documented behavior). This is the *opposite* of what the maintainer decided: "removed verbs exit non-zero naming their replacement... then vanish." A bare `Deprecated` field silently keeps old semantics alive under a new label — exactly the "must NOT silently forward with different semantics" failure mode the question calls out, except inverted (it silently forwards with the *same* semantics, which is still wrong because it never actually removes the surface). | A dedicated stub `cobra.Command` (or a `RunE` guard on the still-present name) whose entire body prints `Error: "query" has been renamed to "search --full"` (or equivalent) to stderr and returns a non-nil error — giving the existing `SilenceUsage`/`SilenceErrors` + caller-exit convention a non-zero exit for free. This is closer to what `kubectl`/`docker` do for hard removals: the old verb becomes a dead end with a pointer, not a working alias. |
| A hidden alias that silently forwards `query` to `search --full` with identical output | This is the literal "must NOT" the question warns about: it looks like a rename but is actually alias-with-different-flag-semantics (recall `query`/`search` already share one ranking function and differ only in `--json` shape — so a silent forward changes *default* output shape for anyone still typing `query`). Silent aliasing also means scripts depending on the old verb's exact output never get a signal to update, and the "for one release then vanish" plan has nothing to remove later because nothing ever broke | The explicit non-zero-exit stub above. Loud, not silent. |
| Nudge that fires on every matching tool call within a session | Named directly in the question as the noise failure mode. Confirmed pattern from Claude Code hook literature: hooks support a `once: true` semantics / state-file throttling specifically to prevent PreToolUse from re-announcing itself on every `grep`/`find`/`Read` call in a long session (multiple cross-checked blog sources, MEDIUM confidence — no single official doc found, but converges from independent write-ups) | Fire once per session (state marker — e.g. a lock/sentinel file under a session-scoped tmp path, or an env var the hook process can observe was already set this session) and go silent afterward, mirroring the existing SessionStart nudge's "one constant line" design, ported to a "one line, once" design for the higher-frequency PreToolUse event. |
| A PreToolUse hook that ever returns `permissionDecision: "deny"` or blocks via exit code 2 | Milestone scope explicitly reframes GUARD-HOOK-01/02 from "redirect" to "add context," and states "never denies." Claude Code's hook JSON schema *supports* `permissionDecision: deny`/`ask` — using it here would violate the maintainer's own reframe and reintroduce the risk the earlier deferral was worried about (an agent's real tool call blocked by a heuristic false-positive) | Use `hookSpecificOutput.additionalContext` (Claude Code) — a note injected into context, never altering `permissionDecision` — or the closest equivalent field on any other harness's hook schema. Verify the exact non-blocking field name per-harness rather than assuming Claude Code's shape transfers verbatim (Codex's schema, per research above, explicitly warns "do not return `updatedInput`... the parser strictly rejects unsupported fields" — schemas are not interchangeable). |
| Rewriting the agent/MCP-facing human-readable text (`query`/`search`'s plain lines, MCP tool descriptions) as part of the color glow-up | Milestone scope is explicit: "the agent/MCP path byte-unchanged." MCP tool names are frozen by the wire oracle. Any styling work that touches a code path shared with the MCP/agent-parseable output (rather than going exclusively through `present`) risks exactly this | Keep the `present`-only boundary (already enforced by an archtest per `styles.go`'s own doc comment) as the hard line; any new styled verb must route its *human* branch through `present` and leave its non-TTY/`--json`/MCP branch untouched. |
| Assuming AGENTS.md-style reach is "done" for Cursor because Cursor generically reads repo-root `AGENTS.md` | Multiple 2026 sources now describe `AGENTS.md` as a broadly-adopted convention read natively by Cursor, Gemini CLI, and others, not just Codex ([blog.buildbetter.ai](https://blog.buildbetter.ai/agents-md-complete-guide-for-engineering-teams-in-2026/), [tembo.io](https://www.tembo.io/blog/agents-md), MEDIUM confidence, blog-tier but multiply cross-checked) — this *contradicts* this project's own current code comment (`instructions.go`: "only 4 of 8 targets that get an instructions file... Claude, Codex, opencode, Gemini"). Do not silently assume the broader-adoption claim is true and skip work, and do not silently assume the code comment is still accurate either — both could be stale | Verify directly in a real Cursor session per-harness (the milestone's own evidence standard) whether a repo-root `AGENTS.md`/marker block is picked up with zero Cursor-specific write path, before deciding whether Cursor needs its own instructions-file target or can ride the shared block for free. This is a cheap, high-value probe to run early in planning. |
| Treating Codex's "no per-project config" claim in `codex.go` as still true without re-verifying | The milestone scope itself calls this out as something to re-verify, and this research found **direct evidence it changed**: Codex CLI now supports a project-scoped `.codex/config.toml` merged on top of `~/.codex/config.toml`, gated on the project being marked `trust_level = "trusted"` ([github.com/openai/codex#13025](https://github.com/openai/codex/issues/13025), [#13056](https://github.com/openai/codex/issues/13056), MEDIUM confidence — GitHub issues from the official repo describing current/recently-changed behavior, cross-checked against a third-party MCP-management article). `codexTarget.SupportsLocation(LocationLocal)` unconditionally returning `false` is very likely now **factually wrong**, not just conservative | Re-verify in a real Codex session (trust a project, add project-local MCP config, confirm Codex actually loads it) before changing `codex.go` — this is exactly the kind of claim the milestone says needs live verification, not a doc citation alone, because GitHub issues describing "current" behavior can themselves be stale or partially-shipped. |

## Feature Dependencies

```
Real color palette (differentiator) → requires TTY-gate + NO_COLOR (table stakes, already shipped) to remain intact
--color=auto|always|never (differentiator) → layers on top of ChoosePresentation; changes its signature/call sites, not its concept
fang evaluation → gates whether "grouped --help" is hand-rolled cobra.Group markup or fang's own help renderer — decide fang first, then implement grouping once, not twice
Verb fold (query → search --full) → must land before/with the non-zero-exit stub, since the stub's message names the new form
Grouped --help taxonomy → benefits from the verb fold landing first (fewer, cleaner verb names to categorize) but does not strictly require it
Codex project-local re-verification → gates whether AGENT-04..07 Codex work is "add a project-scope write path" (new capability) or "confirm global-only is still correct" (no-op) — this is a blocking prerequisite for scoping the Codex parity work, not parallel to it
Cursor AGENTS.md auto-pickup probe → gates whether Cursor needs a new instructions-target implementation at all
PreToolUse nudge hook (Claude Code) → independent of the SessionStart nudge; both can coexist, but the "once per session" throttle should share a design (if not a mechanism) with lessons already learned from SessionStart's resume-matcher investigation (transcript-grep is not a valid verification oracle — use a side-channel or ask-the-model, per NUDGE-live-session.md)
```

## MVP Recommendation (research-informed prioritization within this milestone's already-fixed scope)

The milestone's scope is fixed by the maintainer (this is not a scope-choice document), but within it:

1. **Re-verify the Codex project-local-config claim first**, before writing any Codex `codex.go` code — it's a blocking prerequisite (see Dependencies) and the cheapest possible probe (one `codex mcp add` at project scope in a scratch trusted repo).
2. **Decide `fang` vs hand-rolled before touching `styles.go`** — adopting it after a hand-rolled grouped-help implementation exists means throwing that work away.
3. **Land the verb-fold non-zero-exit stubs early** — every other agent-reach and instructions-text change (nudge wording, `AGENTS.md`/skill content mentioning verb names) should reference the *final* verb names, not the pre-fold ones.
4. **Probe Cursor's AGENTS.md auto-pickup before writing Cursor-specific code** — likely the cheapest possible win in the whole "agent reach" bucket if the 2026 broad-adoption claim holds for this project's exact block format.

Defer within-scope items that need their own live-session evidence gathering (Codex nudge hook, since it's experimental/disabled-by-default) to *after* the higher-confidence items land, so a negative result there doesn't block the rest of the milestone.
