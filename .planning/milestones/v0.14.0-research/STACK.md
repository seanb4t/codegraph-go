# Stack Research — v0.14.0 Polish & Agent Reach

**Domain:** CLI styling glow-up (lipgloss v2 / cobra groups / fang) + multi-harness agent-install surface (Codex parity + 6 other harnesses) + a non-blocking Claude Code nudge hook
**Researched:** 2026-09-14
**Confidence:** HIGH for lipgloss v2/cobra/fang (Context7 + primary GitHub source, cross-checked against this repo's own go.mod/go.sum); MEDIUM for Codex CLI's current config/hooks/skills surface (official developers.openai.com/learn.chatgpt.com docs fetched today, but the product is moving fast — flagged per-claim); MEDIUM for the other 6 harnesses (vendor docs fetched today, several via WebSearch synthesis rather than a single canonical page — flagged per-claim)

## Executive Summary

Nothing here requires a new supply-chain-relevant Go dependency for capability (1)/(2): `charm.land/lipgloss/v2` (already at v2.0.5) and `github.com/charmbracelet/colorprofile` (already an *indirect* dependency, pulled in transitively by bubbletea v2, pinned at v0.4.3) cover the whole color story — profile detection, NO_COLOR/CLICOLOR_FORCE/TERM=dumb, and adaptive light/dark. The only go.mod change for (1) is promoting `colorprofile` from indirect to direct. `cobra` command grouping (`AddGroup`/`GroupID`/`SetHelpCommandGroupID`) needs zero new dependency — it has existed in cobra since well before the project's pinned v1.10.2.

`charmbracelet/fang` (now `charm.land/fang/v2`, latest v2.0.1) is a real, cgo-free, actively maintained option for capability (2)'s "before any help template is hand-rolled" evaluation gate — but it ships its **own hidden `man` subcommand and its own `completion` subcommand by default**, both of which collide by name with surface this project already owns (`internal/cli/man.go`'s hidden `man <dir>` command using `doc.GenManTree`, and cobra's own auto-registered `completion` command that GoReleaser's `generate_completions_from_executable` already relies on). Adopting fang is viable but only with `fang.WithoutManpage()` and `fang.WithoutCompletions()` set explicitly — otherwise it is a same-name command collision, not a soft conflict.

The biggest finding is in capability (4): **the milestone's own premise — "Codex CLI has no per-project config concept" — is now false**, verified against `developers.openai.com`/`learn.chatgpt.com` docs fetched today. Codex CLI has shipped project-scoped `.codex/config.toml` (trust-gated), a skills mechanism, AGENTS.md discovery with override semantics, and — the most consequential discovery — a **hooks system whose event set and output contract are nearly a structural match for Claude Code's** (`SessionStart`, `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, regex matchers, and a `hookSpecificOutput.additionalContext` non-blocking output shape). This directly unblocks "Codex's nudge/hook mechanism if one exists" — one exists, and it's shaped almost identically to the one already built for Claude Code.

Capability (5) shows the wider ecosystem converging on two shared standards this milestone can lean on directly: the **`.agents/skills/` directory** (repo and `~/.agents/skills/` user-level) that Cursor, opencode, and Antigravity all read in addition to their own native directory, and **`AGENTS.md`** as the cross-tool instructions-file standard (Cursor, opencode, Antigravity, and — per the config-basic doc — Codex all read it; Gemini CLI still primarily uses its own `GEMINI.md`, and Kiro treats `AGENTS.md` as one more steering-file source alongside its native `.kiro/steering/`). Writing the skill package once to `.agents/skills/codegraph/SKILL.md` (plus `~/.agents/skills/codegraph/SKILL.md` for global) is very likely enough to reach Cursor, opencode, and Antigravity's discovery in one write — this should be verified per-harness in a live session per the milestone's own evidence standard, not assumed as fully general.

### Claude Code — PreToolUse non-blocking nudge contract (capability 6)

| Element | Value | Source |
|---------|-------|--------|
| Non-blocking context-add output | `{"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":"..."}}` — omit `permissionDecision` entirely; its presence (`"allow"`/`"deny"`/`"ask"`) is what would turn this into a gate instead of a nudge. Exit code 0 with this JSON is required. | code.claude.com/docs/en/hooks, fetched 2026-09-14 |
| Matcher syntax | Exact tool name (`"Bash"`), pipe- or comma-separated multi-match (`"Bash|Grep|Glob|Read"` / `"Bash, Grep, Glob, Read"`), regex (`"^Notebook.*"`), MCP-scoped (`"mcp__<server>__.*"`). This directly supports a single matcher entry covering grep/find/Read (`"Grep|Glob|Read"`, or `"Bash|Grep|Glob|Read"` if shell-invoked grep/find should also trigger it). | code.claude.com/docs/en/hooks |
| Keeping it cheap | `PreToolUse` command-hook timeout defaults to 600s but should be set explicitly low (docs show `"timeout": 5` in the worked example) since a nudge script should be a fast, local, no-network check (e.g. "does `.codegraph/` exist"). Avoid any blocking I/O; this is exactly the profile of GUARD-HOOK-01/02's design ("on grep/find/Read in an indexed repo it points at `codegraph_explore` and never denies"). | code.claude.com/docs/en/hooks |

This is a straightforward extension of the SessionStart hook infrastructure Phase 7 (v0.10.0) already built and dogfooded in `.claude/hooks/session-nudge.sh` / `hooks.json` — same script-writing and marker-fenced-registration machinery in `claude.go`, new event name (`PreToolUse`) and matcher instead of `SessionStart`.

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Adopting `charm.land/fang/v2` with its default man/completion commands enabled | `fang.Execute` without `fang.WithoutManpage()` installs a hidden `man` subcommand — but this repo's `internal/cli/man.go` **already owns a hidden `man <dir>` command** (`Use: "man <dir>"`, wired to `doc.GenManTree`, invoked by the Homebrew cask's post-install hook). Cobra panics/behaves undefined on duplicate command registration at the same tree position; at minimum this is a silent behavior change to a command GoReleaser's release pipeline depends on. Same reasoning for `fang.WithoutCompletions()` against cobra's own auto-registered `completion` command, which `generate_completions_from_executable` in `.goreleaser.yaml` already relies on. | `fang.Execute(ctx, root, fang.WithoutManpage(), fang.WithoutCompletions(), ...)` if fang is adopted at all. |
| Treating `charm.land/fang/v2` as a drop-in replacement for `docs/CLI-REFERENCE.md`'s `cobra/doc`-generated reference | Fang generates man pages via Mango (`muesli/mango-cobra`), a **different generator** than `cobra/doc` (`doc.GenManTree`) this project already standardized on in v0.13.0 Phase 12 specifically to avoid "reimplementing cobra doc" (maintainer ruling, per PROJECT.md). Two generators for two audiences (man pages vs. a markdown CLI reference under a drift gate) is not itself wrong, but conflating "fang gives us manpages" with "fang replaces our reference generator" would re-litigate a settled Phase 12 decision. | Keep `tools/clidoc` + `cobra/doc` as the sole source of `docs/CLI-REFERENCE.md`; fang (if adopted) only ever touches interactive `--help`/error/version chrome, with its own manpage path disabled. |
| Assuming Codex's `.codex/skills/` (the path most third-party blog posts describe) is the current, sole skill directory | The one official-looking `learn.chatgpt.com/docs/build-skills` page fetched today names `.agents/skills/` and `~/.agents/skills/`, described explicitly as "the open agent-skills standard," while independent community sources (agensi.io, jmerta.github.io/codex-skills) describe `~/.codex/skills/`/`.codex/skills/`. Committing to one without a live-session check risks shipping a skill file Codex never discovers. | Write to **both** `.agents/skills/codegraph/` and verify in a genuinely fresh Codex CLI session (this milestone's stated evidence standard) which path (or both) Codex actually loads before finalizing `codex.go`'s skill-install path. |
| Reading env or calling `term.IsTerminal`/`colorprofile.Detect` from inside `internal/cli/present` | Violates this package's own documented constraint (D-03: "present must NOT read os.Getenv or call term.IsTerminal itself... real fd/env values are read only at the RunE call sites in internal/cli"). `colorprofile.Detect(w, os.Environ())` is exactly this kind of env read. | Call `colorprofile.Detect` (and `lipgloss.HasDarkBackground`) in `internal/cli`'s `RunE` functions (same call sites that already resolve `isTTY`/`noColor` for `ChoosePresentation`), and pass the resolved `colorprofile.Profile` / `lipgloss.LightDarkFunc` into `present`'s renderers as a parameter. |

## Stack Patterns by Variant

**If the CLI glow-up adopts fang:**
- `Execute()` in `internal/cli/root.go` changes signature to accept/build a `context.Context` and call `fang.Execute(ctx, newRootCmd(), fang.WithoutManpage(), fang.WithoutCompletions(), fang.WithVersion(versionLine()))` instead of `newRootCmd().Execute()`.
- The `styles.go` header comment's "present is the sole home for charm.land/lipgloss/v2 styling (D-01)" claim becomes narrower in practice (fang also emits styled chrome, from `internal/cli`/`cmd/codegraph`, not `present`) — this is a **documentation update**, not an archtest violation, since `TestCharmCgoClosure`'s `go list -deps -json internal/cli/...` scan already covers the whole `internal/cli` tree and would pick up `charm.land/fang/v2` in the same non-cgo audit it already runs. The `TUI-01` import-graph archtest's *forbidden* list (`internal/query`, `internal/mcp` must never import charm) is unaffected either way — fang lives in `internal/cli`/`cmd/codegraph`, nowhere near that boundary.

**If the CLI glow-up declines fang and hand-rolls cobra groups + a help template instead:**
- No `context.Context` plumbing change to `Execute()`.
- `cobra.Group{ID, Title}` values are defined once (likely in `root.go` alongside `newRootCmd`), `AddGroup(...)` on the root command, then each subcommand constructor sets `GroupID` — mechanical, low-risk, but delivers grouping only, no styled error/version/theming.

**If Codex's project-local `.codex/config.toml`/`.codex/hooks.json`/`AGENTS.md` writes are added:**
- `codexTarget.SupportsLocation` must change from `loc == LocationGlobal` to `true` (mirroring `claudeTarget`'s `SupportsLocation(Location) bool { return true }`), and `Install`/`Uninstall`/`DescribePaths` need the same global/local branch shape `claude.go` already establishes — this is a structural parity change, not a new pattern.
- The project-local `.codex/` write is **only effective if the project is Codex-trusted**; `install` cannot force trust and should not silently assume it — surfacing "wrote `.codex/config.toml`, but it will not take effect until this project is marked trusted in Codex" is the honest behavior, analogous to how `claude.go`'s `AutoAllow` option is explicit and opt-in rather than assumed.
