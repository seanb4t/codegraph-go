## One guard this plan deliberately does NOT add

D-03 decides that no hard byte or line budget is enforced on resource documents, unlike the
600-byte cap `TestInstructionsStaysWithinWireBudget` places on the `instructions` string. That cap
exists because `instructions` is JSON-encoded into every frozen transcript, so its growth inflates
every transcript diff forever; a `resources/read` response is its own transcript and carries no
such per-transcript cost. Fact-sheet-only content (D-01) stays short by discipline. Do not add a
size, line-count, or token-budget assertion over `resourcesFS` in this plan — the absence is the
decision, not an oversight, and adding one would be scope this phase's source artifacts explicitly
declined.

Note also that this plan touches neither `instructions` nor `internal/agents/instructions.go`.
GUARD-01's requirement text names "resources/skill/instructions", but the skill is Phase 6 and the
`instructions` rewrite is Phase 8 (WIRE-01); Phase 5 owns only the resources third of that
sentence. `instructions_contract_test.go` already guards the `instructions` third and must be left
untouched.

## On what "RED first" means for a guard

A guard written against already-correct content passes on its first run, so the ordinary
test-then-implement cycle does not apply. This repository's standing rule supplies the real RED
step: *a gate is not trusted until it has been demonstrated RED against a confirmed-applied
mutation.* Tasks 1 and 2 therefore each write the checker AND its synthetic non-vacuity sub-test
in one motion — the sub-test IS a genuine red-then-green cycle at the checker level, exactly the
`TestREADMEGateCheckerIsNotVacuous` precedent already in this package — and Task 3 supplies the
demonstrated-red proof against the real tree for the two properties the phase's success criteria
name explicitly. Do not skip Task 3 and assert from reading the guard; criterion 3 forbids it in
those words.
