## Summary

Every one of the 19 locked decisions in `02-CONTEXT.md` is implementable exactly as decided; nothing in this research contradicts a locked decision. Two decisions, however, have a discretion clause or an open sub-question that this research **resolves concretely** rather than leaving to plan-time guesswork, and two more have a **real risk this research surfaces that CONTEXT.md did not anticipate**:

1. **D-07 (buf scoping)** is now a fully specified mechanism: a **second** `buf.gen.yaml` template (e.g. `buf.gen.ts.yaml`) whose `inputs:` entry is `directory: internal/uiproto/uiv1` (not `.`), invoked as a second `buf generate --template buf.gen.ts.yaml` call in the same Taskfile target. This sidesteps buf.yaml's `.claude/worktrees` exclude entirely (the scoped directory has no worktrees under it) and — critically — **`opt: target=ts` must be set explicitly**, because `protoc-gen-es`'s default target is `js+dts` (two files), not `ts` (one file). With `target=ts` set, exactly **one** file is emitted (`ui_pb.ts`, containing both message types and the `UIService` schema — Connect-ES v2 folded service generation into `protoc-gen-es` itself). New `proto:drift` floor: **4** (3 Go files + 1 TS file), confirming CONTEXT's own "preferred" branch.

2. **BLD-03's drift guard cannot be a byte-diff of two SvelteKit builds.** Two primary-source, still-open/declined-as-"not planned" Vite GitHub issues (#15555, #13071) confirm that repeated Vite/Rollup builds of *identical* source can legitimately produce different content-hash filenames — the exact failure mode `task proto:drift`'s regenerate-and-byte-compare pattern assumes cannot happen. ROADMAP's own success-criterion-3 wording ("the guard reports how many **source files** it **hashed**") already points at the correct alternative: hash the **source tree**, not the build output, and compare against a stored digest — the same pattern regardless of whether Rollup's chunk splitting is deterministic that day.

3. **Pitfall 5 (embed `..` constraint) is a genuine correction to D-12's discretion clause**, not merely an implementation detail: `internal/uiserver` cannot contain the `//go:embed all:build` directive at all, because `web/build/` is reachable from `internal/uiserver/` only via `../../web/build`, and Go embed patterns may not contain `..` — this repo already hit and documented this exact constraint for `claudeassets.go`. The directive must live in a file **inside `web/`** (mirroring `internal/mcp/resources.go`'s in-package embed, not `claudeassets.go`'s root-level embed).

4. **A freshly scaffolded `web/.gitignore` will re-break D-03's "no `.gitignore` change needed" verification** if copied verbatim from SvelteKit's own template — its default `.gitignore` contains a bare `/build` line. The ROOT `.gitignore` verification CONTEXT.md already did is correct and does not need redoing; a *new, nested* `web/.gitignore` is a different, unverified file that must be pruned.

**Primary recommendation:** Build the SPA toolchain exactly per the 19 locked decisions; resolve D-07 with the second-`buf.gen.yaml`-template mechanism above; build BLD-03's guard as a source-hash staleness check (not a build-output byte-diff); place the `go:embed` directive inside `web/`, not `internal/uiserver`; and audit any scaffolded `web/.gitignore` for a `build`/`dist` line before trusting D-03's verification.

### Pattern 1: Scoping a second codegen language to a subset of a buf module (D-07)

**What:** buf v2's `inputs:` list accepts a `directory:` entry that overrides the default `.` (whole-module) input for that specific `buf generate --template <file>` invocation, while still resolving through the same `buf.yaml` module/workspace configuration `[CITED: buf.build/docs/generate/usage]`.

**When to use:** when different plugins must run against different subsets of a single buf module — buf v2 does not support per-plugin path filtering within ONE `buf.gen.yaml`; every plugin listed under one `plugins:` block runs against the same resolved input set.

**Example:**
```yaml
# buf.gen.ts.yaml — new file, sibling to the existing buf.gen.yaml
# Scoped to internal/uiproto/uiv1 only (contains exactly one .proto file:
# ui.proto) so protoc-gen-es never sees internal/schema/graph.proto.
# Using `directory:` here (rather than `.` + --path) also sidesteps
# buf.yaml's .claude/worktrees exclude entirely: that exclude only matters
# when the input root is the repo root.
version: v2
inputs:
  - directory: internal/uiproto/uiv1
plugins:
  - local: protoc-gen-es
    out: web/src/lib/gen
    opt:
      - target=ts   # REQUIRED — default is "js+dts" (2 files), not "ts" (1 file). See Pitfall 3.
```
```bash
# Taskfile.yml proto:gen, appended after the existing `buf generate` call:
PATH="${scratch}:${web_node_modules_bin}:${PATH}" {{.GO_TOOL_PROTO}} buf generate --template buf.gen.ts.yaml
```

Output: exactly **one** file, `web/src/lib/gen/ui_pb.ts`, containing both the message types and the `UIService` `GenService` schema (Connect-ES v2 folded service-schema generation into `protoc-gen-es` itself — no separate `_connect.ts` file, confirmed against Protobuf-ES's own generated-code reference `[CITED: github.com/bufbuild/protobuf-es/docs/.../generated-code/index.md]`).

### Pattern 2: Enumerating an `embed.FS` and diffing it against an on-disk tree (Criterion 1)

**What:** `fs.WalkDir(embeddedFS, ".", func(path string, d fs.DirEntry, err error) error {...})` — this repo already has TWO precedents doing exactly this, both worth imitating directly.

**When to use:** Criterion 1's file-list diff (embedded FS vs. on-disk `web/build/` tree) and BLD-02's `all:` prefix regression test.

**Example — read verbatim from this repo, `[VERIFIED: internal/agents/claude_skillpackage_test.go:459-481]`:**
```go
func TestClaudeAssets_EmbedsNoVerificationTranscripts(t *testing.T) {
	var walked []string
	err := fs.WalkDir(claudeassets.FS, ".", func(path string, d fs.DirEntry, err error) error {
		if err != nil {
			return err
		}
		if !d.IsDir() {
			walked = append(walked, path)
		}
		return nil
	})
	if err != nil {
		t.Fatalf("walk claudeassets.FS: %v", err)
	}
	if len(walked) != 3 {
		t.Fatalf("expected exactly 3 embedded files, got %d: %v", len(walked), walked)
	}
	// ...
	// Guard-the-guard: prove the walk assertion above is not vacuously
	// green by confirming the real on-disk verification/ directory it
	// must NOT have picked up is actually non-empty.
	verificationDir := filepath.Join("..", "..", ".claude", "skills", "codegraph", "verification")
	entries, err := os.ReadDir(verificationDir)

```
Adapt this shape for criterion 1: walk the embedded SPA `embed.FS` via `fs.WalkDir`, walk `web/build/` on disk via `filepath.WalkDir`, and assert the two **sets** of relative paths are identical (missing/orphaned diff, same pattern as `internal/mcp/resources_schema_drift_test.go`'s `resourceStemSetDiff`, `[VERIFIED: internal/mcp/resources_schema_drift_test.go:39-66]` — quoted in full in Code Examples). This test goes RED by construction if `//go:embed build` (no `all:`) is substituted for `//go:embed all:build`: every `_app/`-prefixed path (dot/underscore-excluded by Go's default embed rule `[CITED: pkg.go.dev/embed — "If a pattern begins with the prefix 'all:', then the rule for walking directories is changed to include those files beginning with '.' or '_'"]`) would show up as "missing" in the diff.

### Pattern 3: Hand-written SPA fallback handler (RPC-03) — do not use bare `http.FileServer`

**What:** `http.FileServer`/`http.FileServerFS` redirect any request ending in `/index.html` to the same path without the trailing filename `[CITED: pkg.go.dev/net/http — "ServeFileFS redirects any request where r.URL.Path ends in '/index.html' to the same path, without the final 'index.html'. To avoid such redirects either modify the path or use ServeContent."]`. That redirect behavior, plus `FileServer`'s directory-index and `..`-cleaning logic, is more machinery than D-10's simple three-way rule (immutable-prefix-miss → 404; anything-else-miss → serve `index.html` literally, never redirected) needs, and risks surprising interaction with SvelteKit's own client router expecting `index.html` to be served verbatim, not 30x-redirected.

**Recommended shape:** a hand-written handler using `fs.ReadFile`/`fs.Stat` directly against an `fs.Sub`-derived sub-filesystem (stripping the embed's `build/` prefix so lookups are `_app/immutable/foo.js`, not `build/_app/immutable/foo.js`), setting `Content-Type` via `mime.TypeByExtension` and `Cache-Control` per D-11's two classes explicitly, with zero implicit redirect or directory-listing behavior.

### Anti-Patterns to Avoid

- **File-extension heuristic for asset-vs-route discrimination:** explicitly rejected by D-10 — Phase 3's deep links carry dotted file paths that would false-404.
- **Regenerate-and-byte-diff for the SPA build:** the `proto:drift` pattern this repo established for Go codegen does NOT transfer to Vite/SvelteKit output — see Pitfall 1.
- **`http.FileServer` for the whole SPA tree:** its automatic `index.html` redirect and directory-listing behavior fight D-04's literal-`index.html`-fallback requirement — see Pattern 3.
- **Relying on `protoc-gen-es`'s default `target`:** silently emits 2 files (`js`+`dts`) instead of 1 (`ts`) — breaks D-07's floor arithmetic if unnoticed. See Pitfall 3.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Connect protocol client/transport | A hand-rolled `fetch()` wrapper for Connect's JSON wire format | `@connectrpc/connect` + `@connectrpc/connect-web` | Already the locked wire protocol (D-05/D-08); hand-rolling reimplements envelope/error-detail encoding this library already gets right |
| Tailwind + shadcn design tokens | Hand-authored CSS custom properties matching shadcn's palette | `shadcn-svelte init`'s own generated `app.css`/`components.json` | The token set (`--background`, `--foreground`, `--primary`, …) is exactly what every future shadcn-svelte component this project adds expects; hand-rolling it risks a mismatch the CLI's own `add` commands don't detect |
| Class-name conflict resolution (`bg-red-500 bg-blue-500` collisions) | A custom string-merge utility | `clsx` + `tailwind-merge`'s `cn()` pattern | This is the exact problem `tailwind-merge` exists to solve; every shadcn-svelte component ships assuming `cn()` is available at `$lib/utils` |
| JS dependency vulnerability scanning | A custom npm-registry-advisory poller | `pnpm audit` (BLD-06) | Already locked; do not build a parallel scanner |

**Key insight:** almost nothing in this phase's JS-facing surface should be hand-built — the entire point of D-01/D-05/D-17's toolchain choices is to inherit the SvelteKit/shadcn-svelte/Connect-ES ecosystems' own conventions rather than reinvent them in a Go-shop's house style. The one place this project genuinely must write custom code is the **SPA fallback handler** (RPC-03) and the **drift guard** (BLD-03) — both are Go-side, both have no off-the-shelf library, and both are addressed in Patterns 2/3 above.

## Common Pitfalls

### Pitfall 1: Byte-identity is not achievable for BLD-03's drift guard — Vite/SvelteKit builds are not reproducible across runs

**What goes wrong:** Two builds of *identical* SvelteKit source can legitimately produce different content-hash filenames (e.g. `stores.GflRvHvF.js` vs. `stores.nX1Zqub0.js` from the same commit, same machine, consecutive runs). A drift guard that regenerates into a scratch dir and byte-compares (imitating `task proto:drift` literally) will go RED on a clean, non-stale tree — a false positive that erodes trust in the gate exactly the way rule `84d1gfpywd` warns against.

**Why it happens:** Confirmed via two primary-source GitHub issues: `vitejs/vite#15555` ("SvelteKit v2 reproducibility issue with asset hash file names," reported against SvelteKit v2/Vite 5.0.10, **closed as "not planned"** by the Vite maintainers) and `vitejs/vite#13071` ("Getting different hashes when running build on the same files," open/pending-triage, reporter noted 30 consecutive runs alternating between two hash variants on one machine). Neither issue's root cause is nailed down precisely in what's public, but the practical conclusion is: this is a known, currently-unfixed, maintainer-declined-to-fix class of Vite/Rollup behavior, not a configuration mistake specific to this project.

**How to avoid:** Do not attempt output byte-identity. Build BLD-03's guard as a **source-hash staleness check** instead: hash the sorted, concatenated content of every file `git ls-files` reports under `web/src`, `web/static`, and the toolchain config files (`package.json`, `pnpm-lock.yaml`, `svelte.config.js`, `vite.config.ts`, `tailwind`/`components.json`), store that digest in a small committed marker (e.g. `web/build/.source-sha256`, written by the build step itself), and have the drift guard recompute the current source hash and compare against the stored marker. This matches ROADMAP's own success-criterion-3 wording — **"the guard reports how many source files it hashed"** — which already names the source tree, not the build tree, as what gets hashed. Pair this with an actual `pnpm install --frozen-lockfile && pnpm build` run elsewhere in CI (BLD-01's own requirement) to prove the toolchain still produces a working build; that is a *separate* concern from "is the committed `web/build/` stale."

**Warning signs:** a drift-guard CI run that is RED on a PR that touches nothing under `web/` — that is the byte-diff approach's specific failure mode, not evidence of real staleness.

### Pitfall 2: A scaffolded `web/.gitignore` re-ignores `web/build/` even though the root `.gitignore` is clean

**What goes wrong:** D-03's verification ("no `.gitignore` change needed") checked the ROOT `.gitignore` only, and correctly found `/dist/` there root-anchored and irrelevant to `web/build/`. But `sv create` (SvelteKit's own scaffolding CLI) and every current `create-svelte`-descended template ship a `.gitignore` inside the new project directory containing a bare `/build` line `[VERIFIED via WebFetch: raw.githubusercontent.com/sveltejs/kit-template-default/main/.gitignore, fetched 2026-08-23 — literal contents: "node_modules\n\n# Output\n.output\n.vercel\n.netlify\n.wrangler\n/.svelte-kit\n/build\n..."]`. If that file is used verbatim as `web/.gitignore`, `web/build/` becomes untracked and D-03's requirement silently fails — `git status` would show nothing to commit, `git add web/build` would appear to do nothing, and the omission is easy to miss because it presents as "nothing changed" rather than an error.

**Why it happens:** SvelteKit's default template is written for the common case (build output is a deploy artifact, not something you commit) — this project deliberately inverts that convention (D-03), and scaffolding tools have no way to know that.

**How to avoid:** After scaffolding, explicitly inspect `web/.gitignore` and remove (or never add) the `/build` line. `/.svelte-kit` should stay ignored (it is `.svelte-kit`'s internal cache, not the committed output). `node_modules` must stay ignored (BLD-01: only the lockfile is committed).

**Warning signs:** `git status` after `pnpm build` shows no new files under `web/build/` even on the very first build.

### Pitfall 3: `protoc-gen-es`'s default `target` option emits 2 files per proto, not 1 — breaks D-07's floor arithmetic if `opt: target=ts` is omitted

**What goes wrong:** Without an explicit `target=ts` option, `protoc-gen-es` defaults to `target=js+dts`, emitting **two** files per input proto (`ui_pb.js` and `ui_pb.d.ts`) instead of one TypeScript source file (`ui_pb.ts`). `[CITED: github.com/bufbuild/protobuf-es/packages/protoc-gen-es/README.md — "The default is 'js+dts'."]` If this is missed, `proto:drift`'s new floor should be 5 (3 Go + 2 JS/DTS), not 4 — and worse, the committed TS client code (`web/src/lib/gen/`) would be plain JS with a separate `.d.ts`, not source-readable TypeScript, which is a worse developer experience and arguably not what D-05/D-06 intend by "generated TypeScript."

**Why it happens:** `protoc-gen-es` (JS-target-by-default plugin) inherits protobuf-es's original "runs on Node without a build step" design philosophy, unlike a TS-generation plugin; `target=ts` is an explicit opt-in.

**How to avoid:** always set `opt: target=ts` in `buf.gen.ts.yaml`. Verify the emitted file count is exactly 1 (`ui_pb.ts`) before locking the drift-guard floor.

**Warning signs:** `git ls-files web/src/lib/gen/` shows 2 files instead of 1, or a `.js`/`.d.ts` pair instead of a single `.ts`.

### Pitfall 4: Corepack is no longer bundled with Node.js 25+ — a CI runner on the wrong Node line breaks `corepack enable`

**What goes wrong:** The Node.js TSC voted to stop distributing Corepack starting with Node.js 25 `[CITED: github.com/nodejs/corepack, github.com/nodejs/nodejs.org#7555]`. If the CI job's `actions/setup-node` step (needed for this phase but not present in `ci.yml` today) resolves to Node 25+ (e.g. via a `node-version: 'latest'`/`'*'` spec, or simply drifts forward over time with no explicit pin), `corepack enable` in that job either fails outright or requires an additional `npm install -g corepack` step D-16's design didn't anticipate.

**Why it happens:** D-16 correctly avoids `pnpm/action-setup` (a second version-of-truth) in favor of Corepack + the `packageManager` field — but that design implicitly assumes Corepack is present, which is no longer universally true across Node's own release lines as of this research date.

**How to avoid:** pin `actions/setup-node`'s `node-version` explicitly to **Node 24** (confirmed Active LTS as of 2026-08-23 `[CITED: endoflife.date/nodejs, nodejs.org/en/blog/announcements/evolving-the-nodejs-release-schedule]` — Node 22 is Maintenance LTS, Node 26 is Current, not yet LTS). Node 24 still bundles Corepack `[CITED: github.com/nodejs/corepack — "Corepack has been removed from Node.js 25+ distributions but remains bundled with Node.js 24 LTS and earlier"]`, so `corepack enable` works with no extra install step. Do not pin `'latest'`.

**Warning signs:** `corepack enable` failing with a "command not found" or unrecognized-subcommand-shaped error on a CI runner that previously worked, coinciding with no change to this project's own config — the runner's default Node line moved past 25 upstream.

### Pitfall 5: `internal/uiserver` cannot contain the `go:embed` directive at all — Go embed patterns forbid `..`

**What goes wrong:** D-12's discretion clause frames this as a choice between "a small dedicated file under `internal/uiserver`" and "alongside the handler in `spa.go`" — both options place the `//go:embed all:build` directive inside `internal/uiserver/`. But `web/build/` is reachable from `internal/uiserver/` only via `../../web/build` (they are sibling subtrees off the repo root, not ancestor/descendant), and **Go embed patterns may not contain `..`** `[CITED: pkg.go.dev/embed — "Patterns may not contain '.' or '..' or empty path elements, nor may they begin or end with a slash."]`. This repo has already hit and documented this exact constraint once, for `claudeassets.go` `[VERIFIED: claudeassets.go:7-17]` — the corrected mental model is directly reusable here, not a new problem to rediscover.

**Why it happens:** `//go:embed` patterns resolve relative to the directory containing the source file carrying the directive, with no upward traversal permitted — a structural Go language constraint, not a buildability nuance.

**How to avoid:** put the `go:embed` directive in a file **inside `web/`** (e.g. `web/embed.go`, `package web`, `//go:embed all:build`, `var BuildFS embed.FS` — mirroring `internal/mcp/resources.go`'s in-package embed pattern, where the embedding file lives alongside the directory it embeds `[VERIFIED: internal/mcp/resources.go:1-14]`), and have `internal/uiserver/spa.go` import that package and consume its exported `embed.FS`. D-12 itself (the *handler* living in `internal/uiserver`) is unaffected — only the discretion clause about where the directive lives needs correcting.

**Warning signs:** a `go build` failure citing "invalid pattern syntax" or "pattern .. is invalid" the moment the directive is written under `internal/uiserver`.

### Pitfall 6: `http.ServeFileFS`/`http.FileServer` auto-redirect `/index.html` requests — silently fights D-04's literal-fallback requirement

**What goes wrong:** if the SPA fallback handler is implemented by delegating to `http.FileServerFS` for the whole tree (not just the immutable-asset prefix), any client request whose path happens to end in `/index.html` gets redirected rather than served directly `[CITED: pkg.go.dev/net/http]`. This is a minor edge case for THIS phase (nothing deep-links to `/index.html` literally) but is exactly the kind of `http.FileServer` implicit behavior Pattern 3 recommends avoiding wholesale, since it also affects directory-listing and trailing-slash handling in ways D-10's simple rule doesn't need.

**How to avoid:** use `fs.ReadFile`/`fs.Stat` directly (Pattern 3) rather than `http.FileServer`/`http.FileServerFS` for anything beyond the narrowest possible use (e.g. it MAY still be reasonable to use `http.ServeContent` for the immutable-assets prefix specifically, since that prefix has no `index.html`-shaped paths and its behavior is otherwise simple byte-serving with a `Cache-Control` override).

### Set-diff pattern for embed-vs-on-disk comparison (reused for Criterion 1's test)

```go
// Source: internal/mcp/resources_schema_drift_test.go:39-66 (this repo, read this session)
// resourceStemSetDiff reports, given an expected and an actual resource
// stem set, which stems are missing (named in expected but absent from
// actual) and which are orphaned (present in actual but never expected).
func resourceStemSetDiff(expected, actual []string) (missing, orphaned []string) {
	expectedSet := make(map[string]bool, len(expected))
	for _, s := range expected {
		expectedSet[s] = true
	}
	actualSet := make(map[string]bool, len(actual))
	for _, s := range actual {
		actualSet[s] = true
	}
	for s := range expectedSet {
		if !actualSet[s] {
			missing = append(missing, s)
		}
	}
	for s := range actualSet {
		if !expectedSet[s] {
			orphaned = append(orphaned, s)
		}
	}
	sort.Strings(missing)
	sort.Strings(orphaned)
	return missing, orphaned
}
```
Adapt directly for criterion 1: `expected` = paths from `filepath.WalkDir` over on-disk `web/build/`, `actual` = paths from `fs.WalkDir` over the embedded `web.BuildFS`. Both empty ⇒ criterion 1 satisfied; a non-empty `missing` slice after removing the `all:` prefix is exactly the regression this criterion exists to catch.

### Applicable ASVS Categories

|---------------|---------|-----------------|

| V3 Session Management | No | No sessions |

| V6 Cryptography | No | Nothing new; TLS/crypto out of scope for a loopback tool |
| V14 / Configuration & supply chain (numbering varies by ASVS version) | Yes | `strictDepBuilds`, `allowBuilds`, `pnpm audit`, Corepack-pinned `packageManager` — this phase's whole JS supply-chain-gate scope (BLD-05/BLD-06) |
| V12 (or equivalent) Static resource handling | Yes | Serve embedded assets with `X-Content-Type-Options: nosniff` to prevent MIME-sniffing on served static assets — new attack surface introduced by this phase (previously the server only emitted JSON) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malicious npm postinstall/lifecycle script executing during `pnpm install` | Tampering / Elevation of Privilege | `strictDepBuilds: true` + committed `allowBuilds` approval map (D-14/BLD-05) — already locked |
| Known-vulnerable JS dependency shipped in the committed `web/build/` bundle | Tampering | `pnpm audit` gate (BLD-06) — already locked |
| MIME-type confusion / content-sniffing on served static assets (new in this phase — previously only JSON responses existed) | Tampering / Information Disclosure | Set `X-Content-Type-Options: nosniff` on every response the new SPA handler serves; low-cost, standard hardening not explicitly named in CONTEXT.md's locked decisions but consistent with D-11's Cache-Control precedent of "the handler sets response headers deliberately, not by accident" |
| Stale cached app shell after a binary upgrade (talks to an RPC surface it doesn't understand) | — (availability/correctness, not a STRIDE security category, but load-bearing) | D-11's `no-store` on `index.html` — already locked |
| Origin/Host rebinding against the new static-asset routes | Spoofing | Already covered — `originHostGuard` wraps the WHOLE mux (Phase 1, D-09 confirms the SPA handler inherits this with no extra work) |
