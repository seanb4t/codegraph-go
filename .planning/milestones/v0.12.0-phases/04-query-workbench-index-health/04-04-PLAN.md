<objective>
Build the Workbench out from the tracer: four tabs, one per analysis, with the
selected tab carried in the `mode` URL parameter (D-13), and the two remaining
symbol-input analyses — `Impact` with its depth control (WRK-01) and `Callees`
with its limit control (WRK-03) — wired through the shell the tracer proved.

The tracer already established the shape: one `DataTable` shell, one
`ColumnDef<Location>[]` per analysis, one composed failure taxonomy, one URL
grammar. This plan does not invent anything new; it instantiates that shape three
more times and factors the per-analysis repetition into one `AnalysisPanel`
wrapper so the fourth instantiation (04-06's `Affected`) is a column file and a
request function, not another copy of the panel.

WRK-01's criterion is specific and is the easiest thing here to get wrong: moving
the depth control must change the blast radius **without leaving the page**. That
is an assertable property — the route component is not re-mounted and no
navigation is dispatched — not a feeling, so it is asserted in code.

Purpose: WRK-01 and WRK-03 are delivered here; WRK-04's sortable-table and
named-failure criteria become true for three of the four analyses.
Output: the `tabs` primitive vendored, two more column definitions, one shared
analysis panel, and a `/workbench` route where three of four tabs are live.
</objective>
