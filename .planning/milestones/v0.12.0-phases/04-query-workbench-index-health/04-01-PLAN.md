<assumption_delta_decision>
**Noun:** the URL grammar's file target — one file becomes many files.

**The seam.** `web/src/lib/browse-url.ts` has exactly ONE `file`, read with
`params.get('file')`, which silently discards every occurrence after the first.
D-11 introduces a MULTI-valued `file=` for the Workbench, read with
`params.getAll('file')`. That is a genuine singular→plural transition in a shape
this codebase already models singularly.

**Decision: `add-alongside`.** D-10 chose a sibling `web/src/lib/workbench-url.ts`
that imports browse-url's exported shape primitives, rather than PROMOTING
`browse-url.ts` itself to a multi-valued reader. The general guidance prefers
promote over add-alongside; this is a deliberate, recorded deviation.

**Rationale.** Phase 3's Browse grammar is frozen, round-trip-asserted
(`web/tests/browse-url.test.ts`) and shipped. Widening its known-key reader from
`get` to `getAll` would change the canonical key space of every Browse link that
already exists in the wild — `?file=a&file=b` currently round-trips through Browse
as `file=a` plus a dropped value, and promoting would silently change what a
previously-shared link resolves to. D-13 (Phase 3) scopes `browse-url.ts` as the
one grammar *for the Browse view*; a sibling grammar for a different view is
within that scope, not a violation of it.

**Accepted debt.** Two URL grammars now exist that share primitives but not their
readers. The concrete future trigger that would make this untenable and force a
promote to a shared multi-valued core: **a third view needing the same
multi-valued target** (Phase 5's graph view selecting several files), **or Browse
itself gaining multi-file selection** (the file-tree-with-checkboxes idea D-15
deferred to Phase 5). Either event means three copies of "how do I read a repeated
key", and at that point the correct move is to promote `browse-url.ts`'s reader
into a shared core both views import — with a migration for existing Browse links.

**What keeps the debt visible.** `workbench-url.ts`'s module doc comment must
state this decision and name both triggers, so the next author of a multi-valued
URL key reads it before adding a third grammar.
</assumption_delta_decision>
