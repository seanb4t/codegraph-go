<objective>
Give the graph a way to ask what is inside a file, because nothing in the existing
surface can answer that.

GRF-03 needs a file's symbols. The research assumed that data already crossed the
wire through the existing node-detail rpc, and it does not: that rpc's file mode
populates a path and a source blob and nothing else, and the engine type behind it
carries exactly two fields. There is no engine method anywhere in `internal/query`
that enumerates the symbols declared in one file. This is a real gap found by reading
the code, not a shape that needs rearranging.

The fix is a thirteenth additive read-only rpc, for the same reason Phase 4 added a
separate health rpc rather than widening the status message: the node-detail message
is fetched on every Browse navigation, and hanging every symbol in a file off it
would make that view pay for data it never renders. One concern, one rpc.

Two things make it more than mechanical. It takes a caller-supplied path, so it is
the first rpc this phase adds that needs the repository-root confinement the
node-detail and permalink rpcs already apply — reused, never re-implemented. And a
generated file with a very large symbol count is the one unbounded shape here, so the
response caps, counts and says so, following the truncation discipline this server
already uses for source blobs.

Purpose: 05-07 cannot expand a file into anything without this.
Output: an engine method, a thirteenth rpc with its handler and mapper, regenerated
clients, and the read-only fixtures moved in the same commit.
</objective>
