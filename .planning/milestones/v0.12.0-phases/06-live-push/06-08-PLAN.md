<objective>
Close the criterion-1 gap the live browser UAT found after this phase verified 5/5: the
root Status route (`/`) — the default landing view `codegraph ui` opens — never applies
live events. It fetches `GetStatus` once in `onMount` and subscribes to nothing, so after
a re-index it renders counts a generation behind while simultaneously asserting
`Stale: no`.

Wire it to the same `liveStore` the other four surfaces already use, mirroring
`health/+page.svelte`'s coalescing and `requestId` discipline exactly. This adds no new
rpc, no new transport, no new dependency, and no second status surface.
</objective>

## Task 1 — RED: the root route's missing live coverage, as a failing test

Add a `describe('+page.svelte (root Status route): live-triggered re-fetch (LIV-02)')`
block to `web/tests/live-route-refetch.test.ts`, mirroring the existing health block's
harness (same fake client, same live-store driver).

Three cases, each of which MUST fail against the current `+page.svelte`:

1. Delivering one live event issues exactly ONE additional `getStatus` call; a replayed
   or lower generation issues none.
2. The pending-generation coalescer: an event arriving during an in-flight re-fetch
   issues no second concurrent call, and exactly one follow-up carries the newer
   generation once the first settles.
3. CR-01 regression on this site: a live event arriving while the **mount** fetch is
   still unresolved must not let the stale mount response overwrite the newer
   live-triggered one.

**Prove RED before writing Task 2.** Run the block and record the failure output. A test
that has never failed is not a regression test. Count the named `--- PASS`/`FAIL` lines —
a `-t` pattern matching nothing exits 0.
</task>

<task>
## Task 2 — GREEN: subscribe the root route to the live store

Edit `web/src/routes/+page.svelte`:

- `import { getContext } from 'svelte'` and `import type { LiveStore } from '$lib/live/live-store'`.
- Introduce ONE monotonic `requestId`, incremented by both the mount fetch and every
  live-triggered fetch, and guard every `.then`/`.catch` on `id !== requestId` — this is
  `health/+page.svelte`'s CR-01 discipline, not a new invention.
- Extract the mount fetch's body into `issueLiveStatusFetch(generation)` so both paths
  issue the identical `uiClient.getStatus({})` call. Do NOT read any field off the live
  event to render — the event is a **trigger**, and `GetStatus` remains the only source
  of the numbers (D-05).
- Subscribe with the same three-part gate health uses: treat the store's synchronous
  initial delivery as a BASELINE not a trigger; ignore generations `<=` the last issued;
  and when a fetch is in flight, record the newest pending generation and issue exactly
  one follow-up when it settles.

Do not change the rendered markup, the nine `<dl>` rows, or `classify()`. This plan
changes *when* the data is fetched, never *what* is displayed.

Re-run Task 1's three cases: all GREEN. Then run the full `pnpm test` suite and confirm
no regression in the other three route blocks.
</task>
