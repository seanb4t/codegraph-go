  <behavior>
    - Starting the client calls the generated streaming method once and iterates it with `for await`, handing each event to the callback as it arrives. A test that resolves the async iterable's second value only after the first callback has already fired proves consumption is incremental; collecting the iterable first would deadlock that test.
    - Each delivered event updates the client's last-seen generation.
    - **Every successful (re)establishment of the stream increments a connection EPOCH, and each delivered event is handed to the callback with the epoch it arrived under.** This is not bookkeeping for its own sake: the server's generation counter is per-process and starts again at 1 after a restart, so a tab holding last-seen generation 4 that reconnects to a restarted server would ignore every event forever under a strict "greater than" gate. Scoping the gate to an epoch fixes that without weakening ordering within a connection, where one ordered stream plus capacity-1 coalescing means generations only ever move forward.
    - **A stream that ends cleanly is restarted after the SAME backoff delay a thrown failure gets** — not immediately. An immediately-restarted clean EOF is a tight reconnect loop against a server that is closing streams for any reason (shutdown in progress, a proxy cycling), which is the storm LIV-03 exists to prevent. Only an explicit client stop terminates without a retry. A test drives at least 5 consecutive clean EOFs and asserts the scheduled delays grow, exactly as the thrown-failure test does.
    - The delay grows exponentially across consecutive failures and includes jitter, in a SHAPE THAT IS PINNED rather than left open: the base term is `LIVE_BACKOFF_BASE_MS * LIVE_BACKOFF_FACTOR^n` (factor 2), and the SCHEDULED delay is `baseTerm * (1 + u)` where `u` is drawn from a continuous uniform distribution over `[-LIVE_BACKOFF_JITTER_SPREAD, +LIVE_BACKOFF_JITTER_SPREAD]`.
    - **`LIVE_BACKOFF_JITTER_SPREAD` must be strictly less than 1/3**, and is 0.25 here. That bound is what makes strict growth of the SCHEDULED delay — not merely of its base term — a theorem rather than a hope: the largest value at level n is `base*f^n*(1+s)` and the smallest at level n+1 is `base*f^(n+1)*(1-s)`, so growth is guaranteed exactly when `1+s < f*(1-s)`, i.e. `s < 1/3` at `f = 2`. Verified numerically this session: `s` of 0.10, 0.25 and 0.33 guarantee it; 0.34 and 0.50 do not.
    - Over a run of N consecutive failures the SCHEDULED delays are strictly increasing, and two clients failing in lockstep do not schedule identical delays.
    - The delay resets to its base after any successfully received event — a long-lived stream that drops once does not inherit an hour-old backoff.
    - Every restart sends the last-seen generation as the request's resume cursor; the first ever connection sends zero.
    - Stopping the client aborts the in-flight request and schedules no further reconnect; a pending backoff timer scheduled before stop never fires a reconnect after it.
    - **Every event and every connection attempt is recorded on `window.__codegraphLiveObservations`**, a declared, observation-only seam. A test asserts that after N events and one reconnect the seam holds N event records and 2 connection records, with the second carrying a non-null `scheduledDelayMs` — paired with an assertion that the FIRST connection's `scheduledDelayMs` is null, so "it recorded something" cannot be satisfied by a recorder that stamps every entry identically.
    - The seam is bounded: after more than `LIVE_OBSERVATION_CAP` events the array length stops growing and retains the NEWEST entries. Asserted with a floor (the array is non-empty) and a ceiling (it never exceeds the cap), and by checking the last entry is the newest generation.

    ## The live observation seam — declared here because this is where the facts exist

    Declare a THIRD window seam in `web/src/app.d.ts`, alongside the two the graph already
    publishes, and populate it from this client:

    ```ts
    __codegraphLiveObservations?: {
        events: Array<{
            generation: number;
            epoch: number;
            seeded: boolean;        // true for the connect-time current-state message
            receivedAtMs: number;   // performance.now() when the client delivered it
            appliedAtMs: number | null; // set by the store when the gate ADMITS it; stays null when dropped
        }>;
        connections: Array<{
            epoch: number;
            attempt: number;                  // 1-based attempt index since the last successful open;
                                              // attempt 1 of a run is the INITIAL connect, which has no delay
            baseDelayMs: number | null;       // the un-jittered base term for this attempt; null for the first connect
            scheduledDelayMs: number | null;  // baseDelayMs * (1 + u); null for the first connect
            requestedSinceGeneration: number; // the resume cursor this attempt sent
            openedAtMs: number | null;        // null if the attempt never established
        }>;
    };
    ```

    Why this is not optional, and why it lives in THIS plan: `06-06`'s multi-tab gate reads
    eight per-tab facts, and two of them are not observable from outside the application at
    all. "The tab APPLIED this event" is a post-decode, post-epoch-gate fact — it is exactly
    what Task 2's gate filters out, so a network observer sees the event either way. And the
    resume cursor sits inside a length-prefixed Connect protobuf envelope; nothing in the
    phase teaches a Playwright harness to decode one. `06-06` owns two scripts and a JSON
    record, cannot add browser source, and runs in wave 5 behind a frozen client — so if the
    seam is not declared here it does not exist anywhere. This mirrors how the graph work is
    already structured: `06-05` reads the geometry seam and cites its declaration, because
    `GraphCanvas.svelte` declares and publishes it.

    Rules on the seam, all load-bearing:
    - **Observation only.** Nothing in `web/src/` may ever READ it. It is written by the
      client and the store and read only by a real browser harness — the same contract the
      two existing `__codegraph*` seams hold.
    - **Installed before the first connection attempt**, so attempt 1 is recorded. A seam
      created lazily on first event loses the initial connection record.
    - **Both `baseDelayMs` and `scheduledDelayMs` are recorded, and they must agree.**
      `06-06` asserts `|scheduledDelayMs / baseDelayMs - 1| <= LIVE_BACKOFF_JITTER_SPREAD`
      for every entry. Recording only the base would let a client that schedules a
      non-growing delay report a growing base and pass; recording only the scheduled value
      would leave the jitter magnitude unauditable. The pair binds them.
    - **Both are null for the initial connect** — no delay was scheduled for it. `06-06`
      filters those entries out before asserting anything, and this plan states the null so
      that filter is derivable here rather than guessed there.
    - **`scheduledDelayMs` is the delay THIS CLIENT SCHEDULED**, taken from the same value
      handed to the injected timer — never inferred from network timestamps. A
      network-derived interval folds in process startup, the proxy's 502 handling, fetch
      scheduling and browser background throttling, so a correct exponential backoff can
      produce observed intervals that are not strictly increasing. `06-06` asserts strict
      growth, and that assertion is only sound over client-scheduled values.
    - **Bounded.** Cap both arrays at a named `LIVE_OBSERVATION_CAP` (256 is ample for any
      harness run), discarding OLDEST first so the newest state is always present. An
      unbounded recorder on a long-lived tab is a leak.
    - Document the seam's lifetime in `app.d.ts` the way the existing two document theirs.
    - Write no plan id, phase number or planning-artifact name into the declaration or its

    Health view: re-issue its existing health call. Browse: re-issue whatever it currently
    fetches for the file or symbol in view, keeping its own supersession guard. Workbench's
    analysis panel: re-issue only if it currently holds a result — a live event must not
    launch an analysis the developer never asked for.

    Each subscription must respect the guard the route already has (the request-id or
    generation supersession convention this app uses everywhere) so a live-triggered fetch
    and a user-triggered one cannot race to a stale answer. Do not widen
    `navigationIdentity`, and do not route the live trigger through `notifyNavigated` — its
    identity guard exists to suppress duplicate navigations, and a live event is not a
    navigation.

    Coalesce at the consumer, and implement it as a PENDING-GENERATION flag, not as
    suppression. If an event arrives while that view's own re-fetch is still in flight, do not
    stack a second request — record `pendingGeneration = Math.max(pendingGeneration, event.generation)`,
    and when the in-flight request settles, if `pendingGeneration` is newer than the generation
    that request was issued for, start exactly ONE follow-up request for it and clear the flag.
    Merely suppressing the concurrent fetch permanently loses the newest event: the view would
    settle on the older generation's data and never learn about the newer one. The publisher
    already coalesces server-side; this keeps the client from undoing that, without dropping
    the tail.

    Write the mounted-component tests in `web/tests/live-route-refetch.test.ts` — one file,
    named in this task's own files list and in the plan's `files_modified`. `live-client.test.ts`
    and `live-store.test.ts` are the wrong homes: those cover pure modules with no Svelte
    import, and mounting Health and Workbench in them would drag a component harness into
    files deliberately kept free of one.

    The graph route is deliberately out of scope here — its live update needs layout-stability
    work and is `06-05`'s whole subject. List and table views do not exhibit that failure.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| loopback server -> browser | The event is server-controlled data rendered into chrome |
| browser -> loopback server | Reconnect traffic; a badly-shaped retry is a self-inflicted flood |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-13 | Denial of Service | reconnect storm from many tabs after a server restart | high | mitigate | Exponential backoff with jitter, with the jitter proven by test to desynchronise two lockstep clients. Base delay and cap are named constants. |
| T-06-14 | Denial of Service | request amplification from live-triggered re-fetches | high | mitigate | Per-view coalescing (no second request while one is in flight) plus the server-side coalescing publisher; the live trigger deliberately bypasses, rather than widens, `navigationIdentity`. |
| T-06-15 | Tampering | a replayed or out-of-order event reverting the displayed verdict | medium | mitigate | Strictly-increasing generation gate in the store, plus the existing monotonic supersession id in the status gate covering the live/unary interleaving. |
| T-06-16 | Denial of Service | an abandoned reconnect timer firing after teardown | medium | mitigate | Stop aborts the in-flight request and cancels the pending timer; asserted by a test that no further call occurs after stop. |
| T-06-17 | Information Disclosure | event fields rendered into chrome | low | accept | The event carries only fields already exposed by the existing status rpc over the same loopback-only, origin-guarded surface. |
| T-06-18 | Spoofing | a cross-origin page opening the stream | high | mitigate | Unchanged and inherited: the streaming rpc mounts through the same handler constructor and the same exact-match Origin/Host guard as the 13 unary rpcs; no new bypass is introduced. |
| T-06-41 | Denial of Service | a strict generation gate silently deafening every open tab after a server restart | high | mitigate | The generation gate is scoped to the connection epoch: the first event of a new connection is always applied regardless of its generation, because the server's counter is per-process and restarts at 1. Asserted by the three-case gate test, including the lower-generation-in-a-new-epoch case a bare monotonic gate fails. |
| T-06-42 | Denial of Service | a tight reconnect loop against a stream that ends cleanly and repeatedly | medium | mitigate | The same exponential backoff with jitter applies to a clean stream end as to a thrown failure; only an explicit client stop terminates without retry. Asserted by a 5-consecutive-clean-EOF test bounding the attempt count inside a fixed virtual-time window. |
</threat_model>
