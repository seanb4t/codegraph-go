  <what-built>
    `main` carries the full v1.0 history by fast-forward, the automated 6-target pre-tag gate passed, and release-please has an open release PR proposing the natural next version with a substantive changelog (plan 09-06).   </what-built>
  <how-to-verify>
    Approving this runs a real, deliberately disposable release cut. Understand what it does before approving:

    1. It merges release-please's open release PR. That creates a **real tag** and a **real GitHub Release** on this repository.
    2. The tag push starts `release.yml`, which builds all six targets, signs each binary with cosign keyless, and therefore writes entries into the **public Sigstore transparency log**. Transparency-log entries are permanent and cannot be deleted — this is inherent to any keyless-signed release and is the same exposure the real release will have. Nothing secret is written: the entries record this repository's name and workflow identity, which the existing `v0.1.0` release already published.
    3. Immediately after the Release object appears, the disposable release is flagged as a prerelease so GitHub's `releases/latest` redirect — the exact URL `internal/upgrade`'s `resolveLatestVersion` follows — continues to resolve to `v0.1.0`. This repository is also private today, which bounds the exposure further.
    4. Afterwards the tag, the Release and the version-bump commit on `main` are all removed (Task 3).
    5. **This cut consumes the same version number the real cut will use.** Nothing forces a version here or in plan 09-08 (D-06R), so release-please computes the same value from the same commits both times; teardown deletes the disposable tag and reverts the manifest so that recomputation is possible. Two consequences follow, and neither is reversible: the transparency log will end up carrying entries for that tag name twice, from two different commits, and the tag name gets reused after deletion. Reuse is defensible here only because the disposable release is a prerelease for its entire life, `releases/latest` never resolves to it, and this repository is private — so no user can ever have resolved or verified it. Task 3 records that as evidence rather than assuming it.

    Confirm before approving:
    - `gh pr list --repo seanb4t/codegraph-go --search 'chore(main): release' --json number,title` shows the open release PR from plan 09-06.
    - `gh release list --repo seanb4t/codegraph-go` shows the current releases, so the pre-proof state is on the record.
    - `curl -sI https://github.com/seanb4t/codegraph-go/releases/latest` currently redirects to the `v0.1.0` release.

    Alternative if this is not acceptable: close the release PR and stop the phase here. Every mechanical guarantee is already in place; what is forgone is the evidence that the real release will work before it is cut — which is precisely the gap that blocked Phase 8's UAT twice.
  </how-to-verify>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| release-please's tag creation -> `release.yml`'s signing identity | the first time an automated actor's ref drives keyless signing for this repository |

| downloaded artifact -> local verification commands | the artifact under test is fetched over the network before being trusted |
