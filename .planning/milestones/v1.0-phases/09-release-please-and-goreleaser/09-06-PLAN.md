<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Merge-shape decision (D-09, one-way)</name>
  <decision>How the v1.0 integration branch lands on `main`: fast-forward preserving full history, squash into one commit, or an explicit merge commit.</decision>
  <context>
    This is one-way. The merge shape is fixed the moment it lands on `main`, and a squashed history cannot be un-squashed to regenerate a changelog.

    What the repo evidence says (verified, not inferred): `main` contains zero merge commits — the v0.1 milestone landed by fast-forward. `main` is an ancestor of `gsd/v1.0-drop-in-parity-human-ux` today, so a fast-forward is possible as-is with no rebase. The branch is roughly 477 commits ahead, of which about 160 are `feat`/`fix`/`perf` and about 217 are planning-only `docs(...)` commits.

    Under fast-forward, release-please sees all 477 commits and generates a genuinely rich `v1.0.0` changelog from those ~160 entries, while its default changelog sections hide `docs`/`chore`/`ci`/`test` — so the planning commits are filtered automatically rather than by hand. Under squash, all 477 collapse into a single message and the `v1.0.0` changelog becomes one line, discarding exactly the input release-please exists to consume.

    Conflict on record: Phase 8's `08-CONTEXT.md` D-08 says "squash-merge to `main`". Phase 9's D-09 supersedes only that wording, and only on repo evidence — D-08's substance (integration branch → `main` → tag on `main`) is honoured in full. CONTEXT flags this as "the one decision here worth overriding" if a true squash was actually intended.

    Also decide here, in the same breath, whether to proceed at all right now: the merge starts `ci.yml`, `pr-title.yml` and `release-please.yml` on `main` and makes the v1.0 work the repository's default-branch state.
  </context>
  <options>
    <option id="fast-forward">
      <name>Fast-forward, preserving full history (D-09's recorded decision)</name>
      <pros>Matches what v0.1 actually did; possible today with no rebase; gives release-please its real changelog input; `docs`/`chore` noise is filtered by release-please's own defaults rather than by hand.</pros>
      <cons>`main`'s history gains ~477 commits including planning-only ones; the default branch's log is verbose.</cons>
    </option>
    <option id="squash">
      <name>Squash into one commit</name>
      <pros>A single reviewable commit on `main`; a compact default-branch history.</pros>
      <cons>Reduces the `v1.0.0` changelog to one line; contradicts what `main`'s own history shows was done for v0.1; irreversible — the discarded messages cannot be recovered into a changelog afterwards.</cons>
    </option>
    <option id="merge-commit">
      <name>Explicit merge commit</name>
      <pros>Preserves history and records an integration point.</pros>
      <cons>Introduces the first merge commit `main` has ever had, breaking the zero-merge-commit property; no benefit over fast-forward for changelog generation.</cons>
    </option>
  </options>
  <verify>
    <human-check>The merge shape is chosen explicitly and, if it is not fast-forward, the changelog consequence is understood and accepted.</human-check>
  </verify>

    - If any option other than `fast-forward` is selected, the SUMMARY records that D-09 was overridden and why, and plan 09-08's changelog expectations are adjusted before that plan runs.
  </acceptance_criteria>
  <done>The merge shape is decided at a gate rather than discovered after the fact.</done>
