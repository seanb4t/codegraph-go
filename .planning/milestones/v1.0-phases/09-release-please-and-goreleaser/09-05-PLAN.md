  <instructions>
    Perform the setup (this mirrors `docs/RELEASE-PROCEDURES.md` §9 — if the runbook and reality disagree, fix the runbook):

    1. **Create the App.** GitHub -> Settings -> Developer settings -> GitHub Apps -> New GitHub App. Name it for this repo (for example `codegraph-go-release-please`). Homepage URL can be the repo URL. Uncheck Webhook -> Active — release-please needs no webhook.

    2. **Scope it, minimally.** Under Repository permissions grant exactly three, all at Read and write: **Contents** (create the tag, the Release, and the version-bump commit), **Pull requests** (open and update the release PR), **Issues** (the `autorelease: pending` / `autorelease: tagged` PR labels — GitHub governs PR labels under the Issues scope). Grant nothing else. Leave "Where can this GitHub App be installed?" on the account-only option.

    3. **Install it** on `seanb4t/codegraph-go` only — not on all repositories.

    4. **Capture the credentials.** From the App's About page copy the numeric **App ID**. Under Private keys click Generate a private key and keep the downloaded `.pem`.

    5. **Store the secrets** (names must match `release-please.yml` exactly):
       - `gh secret set APP_ID --repo seanb4t/codegraph-go --body '<numeric app id>'`
       - `gh secret set APP_PRIVATE_KEY --repo seanb4t/codegraph-go < /path/to/downloaded.pem`
       Then **delete the downloaded `.pem` from disk** — the repository secret is the only copy that should survive.

    6. **Pre-flight the Actions configuration** (RESEARCH Open Question 1):
       - `gh api repos/seanb4t/codegraph-go/actions/permissions` — confirm Actions are enabled.
       - Repository -> Settings -> Actions -> General -> Workflow permissions — confirm "Allow GitHub Actions to create and approve pull requests" is enabled. release-please-action's own README calls this out as a common blocker.

    7. **Confirm, without exposing values:**
       - `gh secret list --repo seanb4t/codegraph-go` — must name both `APP_ID` and `APP_PRIVATE_KEY`. This command prints names and update times only, never values. Do not run any command that reads a secret's value.

    8. **Note for later:** the token action's `app-id` input is deprecated in favour of `client-id`. They take different values — the numeric App ID versus the App's Client ID string — so switching later means re-seeding the secret, not just renaming an input. `release-please.yml` uses `app-id` today; that is intentional and matches D-02's secret naming.
  </instructions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub App private key -> repository secret store | the PEM leaves the maintainer's machine and must not remain on it |
| App installation scope -> everything the App can do in this repository | the installation grant is the real authorisation surface, independent of any workflow's `permissions:` block |
| repository Actions configuration -> whether an automated actor may open PRs | a setting outside any file in this repo gates the whole pipeline |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-05-01 | Elevation of Privilege | over-scoped App installation permissions (ASVS V4) | high | mitigate | Exactly three permissions granted, each justified in the step list; the granted set is recorded in the SUMMARY as an auditable list with a three-entry acceptance criterion; account-only installation, single-repository install |
| T-09-05-02 | Information Disclosure | the App private key (ASVS V2, V6) | high | mitigate | The PEM is piped into `gh secret set` from stdin and the local file is then deleted; verification uses `gh secret list`, which returns names only; a working-tree check asserts no `*.pem`/`*.key` file was left behind; the prohibition list forbids the key appearing in any artifact |
| T-09-05-03 | Spoofing | a compromised App token authoring a tag push | high | accept | Installation tokens are short-lived by construction, and the signing identity every shipped binary checks is anchored to the *ref shape*, not to the actor — an App-authored tag and a human-authored tag produce the same signing identity, so the token grants no ability to produce a differently-trusted artifact. Residual risk is bounded by the three-permission scope and key rotation |
| T-09-05-04 | Repudiation | an under-scoped App failing only at first real use | medium | mitigate | The failure mode is a visible, immediately-diagnosable authorisation error rather than a silent one (RESEARCH Assumption A1); the disposable live proof in plan 09-06 is deliberately sequenced to surface it before the real release |
| T-09-05-05 | Denial of Service | the repository Actions setting blocking PR creation | medium | mitigate | Explicit pre-flight step 6 checks it before anything depends on it |
</threat_model>
