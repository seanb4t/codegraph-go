<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Contributor shell -> local toolchain | `task` targets execute arbitrary build/test commands on a contributor machine from a repo-controlled file |
| CI runner -> apt package source | The mingw-w64 install step fetches a system package into the gating environment |
| Missing toolchain -> gate outcome | Whether an absent cross-toolchain produces a failure or a pass determines whether the whole local signal is trustworthy |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-02-01 | Repudiation | `vet:daemon-windows` / any cross-toolchain target | high | mitigate | Gate exclusively with `preconditions:` carrying an actionable `msg:`; never with a host-OS restriction or up-to-date short-circuit, both of which report success without running. `TestTaskfileGatesFailLoud` enforces this and is demonstrated red before being trusted. Rationale: a "green" run that silently skipped a leg is a false attestation of correctness. |
| T-10-02-02 | Tampering | `Taskfile.yml` as an executable file in the repo | medium | accept | Every target body is ported verbatim from an existing, reviewed CI step; the file is reviewed like any other source change and no target fetches or executes remote content. Accepted: a Taskfile is no more privileged than the workflow files it replaces. |
| T-10-02-03 | Denial of Service | `Install mingw-w64` apt step | low | accept | Pre-existing step, unchanged by this plan; an apt outage fails the job loudly. |
| T-10-02-04 | Tampering | New `go vet ./...` gate surfacing pre-existing findings | low | mitigate | Findings are fixed in Task 1 rather than suppressed; no vet directive is added to silence a finding without a written justification. |
| T-10-02-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no npm, pip, or cargo package. The only new module dependency is govulncheck, resolved through the Go module proxy with checksum verification. |
</threat_model>
