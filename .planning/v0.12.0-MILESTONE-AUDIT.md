## Finding 1 — Phase 1 shipped without a security audit (found and closed by this audit)

**This is the audit's main catch.** Phase 1 — "Engine Seam, Wire Protocol & Secure
Transport" — had **no `01-SECURITY.md`**, despite:

- `security_enforcement: true`, `security_asvs_level: 1`, `security_block_on: high` active in
  project config throughout;
- all **11** of its plans carrying a `<threat_model>` block;
- it being the phase that establishes the loopback bind and the exact-match Origin/Host guard
  that every later phase's HTTP surface inherits by construction — the surface the ROADMAP
  overview cites a documented CVE class for.

It was the **only such omission in project history**: 27 phase `SECURITY.md` files exist
across five shipped milestones, and v0.12.0's phases 2–6 all had one.

**Closed during this audit.** A retroactive audit ran against **HEAD, not phase-1-era
commits** — so a mitigation present when Phase 1 shipped but since removed would count as
OPEN rather than closed. Result: **SECURED, 40/40 threats closed, `threats_open: 0`.**

|---|---|
| Register rows across 11 plans | 52 |

Two findings came back **better** than the plans claimed: the WR-03 symlink-escape gap that

`block_on`, so non-blocking.

## Finding 2 — Criterion 1 of Phase 6 was reopened after verification passed

Recorded here because it bears on how much weight a phase-level `passed` should carry.

Phase 6 verified **5/5** with primary-source evidence per criterion. A live browser UAT
afterwards found that the **root Status route** — the default landing view `codegraph ui`
opens — never applied live events: it fetched `GetStatus` once on mount, subscribed to
nothing, and rendered counts a generation behind while displaying `Stale: no`.

The verification report had said "four surfaces subscribe to the same liveStore", listing
`health:81`, `browse:140`, `graph:243`, `AnalysisPanel:152`. **That enumeration was correct.**
The defect lived in its complement. Closed by plan 06-08 and independently re-verified from a
surface set derived the other way — wire contract inward, then intersected with
`getContext('liveStore')` — with RED demonstrated twice.

The transferable rule, now recorded in project memory: *for an "every X does Y" criterion,
derive X from a source independent of Y, then intersect.* Enumerating what exists cannot
surface what is missing. A positive control does not help here — the instrument was not
broken.

### Phase 4's PARTIAL — `web:components:drift` (WINDOWS #31)

```
::error::web:components:drift: web/src/lib/components/ui/button/button.svelte
        differs from shadcn-svelte@1.5.1's regeneration
```

**The gate is working, not broken** — it named one specific file, which is a discriminating
result, and 04-07 recorded all eight vendored families reproducing byte-identically at
vendoring time.

- **Ruled out:** local tampering. `button.svelte` has exactly **one** commit in its history
  (`205da685`, human-approved vendoring in 03-06) and was never hand-edited.
- **Not ruled out, and untestable from this host:** the toolchain. `packageManager` pins
  `pnpm@11.23.0` and the workflow resolves it via Corepack, but **corepack is not installed
  here**, so the target fell back to pnpm 12.3.4 by its own report.
- **Blocks nothing.** The gate is `schedule` + `workflow_dispatch` only and deliberately never
  a required check (D-16) — a live registry fetch has no place in a merge gate.
- **Next step:** dispatch `components-drift` manually, where Corepack pins 11.23.0. RED there
  too → diff and re-vendor. GREEN → local-toolchain artifact, waive #31.

This is the honest classification rather than the convenient one: coverage is complete, so
`nyquist_compliant: true` was available — but one declared command does not currently exit 0,
and PARTIAL is what the workflow's own matrix calls that.

## Notes on this audit's own method

Two of this audit's own checks returned a false zero and were caught before being reported:
a windows summary printed `total: 0` against a ledger holding 29 entries (wrong JSON path in
the parser), and an `rg -h` invocation meant `--help` rather than "no filename" (caught by the
`rg-guard` hook). Both were re-run correctly. Recorded because a zero you did not predict is
indistinguishable from a broken instrument, and this milestone has now produced four
documented instances of exactly that.

The integration checker reported `mutatingVerbs` as having "18 verb-prefixes" while correctly
listing nineteen. Re-derived from source: **19**. Its verdict was unaffected, but the count was
wrong — the third recorded instance in this project of a subagent miscounting its own
enumeration. Countable claims from subagents are re-derived here as policy, not as suspicion.

Both subagents dispatched by this audit were overridden from the configured `haiku` to
`sonnet`, on the basis of three recorded incidents in this repository of haiku subagents
returning fabricated evidence and, in one case, a wrong verdict.
