# Pitfalls Research — v0.12.0 Local Graph UI

**Domain:** Adding a local, read-only, browser-based UI (ConnectRPC + Protobuf + Svelte SPA, `go:embed`'d) to a mature single-static-binary Go CLI/MCP product with a hard reproducible-build/SBOM/SLSA3 release pipeline.
**Researched:** 2026-08-22
**Confidence:** HIGH on documented library/CVE behavior (Ollama CVE-2024-28224, MCP SDK CVE-2025-66414/66416, `go:embed` spec, Pebble issue tracker, Connect protocol docs, pnpm's own docs/blog on default-blocked build scripts and audit exit codes); MEDIUM on graph-rendering scale thresholds (numbers vary by library/benchmark, directional not absolute); MEDIUM on npm/pnpm supply-chain framing (Shai-Hulud is real and dated, but its direct applicability to a copy-in-source component library needs to be argued, not assumed).

**Package manager note (maintainer constraint, added mid-research):** this project uses **`pnpm`**, not `npm`. Every lockfile/CI-install/audit-gate discussion below names `pnpm-lock.yaml` and `pnpm install --frozen-lockfile` specifically, and treats pnpm's own default security posture (build scripts blocked by default since pnpm v10, `pnpm audit`'s exit-code behavior) as first-class pitfalls in their own right, verified against pnpm's current docs/blog as of 2026-08-22 rather than assumed from npm behavior.

This project's own history is a primary source here: the MCP server (`internal/mcp/server.go`) already had a Critical path-confinement finding fixed in Phase 3 of the original build, and CR-01 (server-initiated notifications corrupting `pendingWriter`'s counter) is a live, carried-forward bug being folded into this milestone specifically because it is about to get a second long-lived connection-bearing surface next to it. Both are direct precedent for pitfalls below, not generic web advice.

## Critical Pitfalls

### Pitfall 1: `127.0.0.1` binding is treated as the security boundary, and DNS rebinding walks straight through it

**What goes wrong:**
The team binds `codegraph ui` to loopback and considers the surface closed — "it's not exposed to the network, only localhost can reach it." An attacker's web page then performs DNS rebinding: it's served from a domain the attacker controls, the browser resolves and caches that origin, and after the TTL expires the attacker flips the DNS answer to `127.0.0.1`. The browser's Same-Origin Policy checks the **hostname** the page believes it's on, not the IP the socket actually connects to — so JavaScript already running under the attacker's origin now talks straight to `codegraph ui` on loopback, carrying whatever Origin/Host header the attacker chose, and the local server accepts it because it never checked.

This is not hypothetical for exactly this product category. **CVE-2024-28224** (Ollama, NCC Group advisory) is DNS rebinding against a local-only AI dev-tool HTTP API: attackers used the `ADAPTER` parameter of the "Create a Model" endpoint to reference arbitrary local files and the "Push a Model" endpoint to exfiltrate them to an attacker-controlled registry — full read access to a developer's local filesystem via a tool that "only listens on localhost." NCC Group explicitly notes the rebind can happen in as little as 3 seconds. More directly on point: **CVE-2025-66414 / CVE-2025-66416**, DNS rebinding in the *official* MCP Python and TypeScript SDKs for HTTP/SSE-bound local MCP servers (stdio is unaffected) — the same protocol family this project's own MCP server speaks, just over a different transport. The fix landed as automatic DNS-rebinding protection enabled by default the moment a server binds to `127.0.0.1`/`localhost`/`::1` unless the caller explicitly opts out.

**Why it happens:**
"Bound to loopback" and "only reachable by processes on this machine" get conflated with "only reachable by content the user trusts." A browser tab open to an unrelated malicious site is a process the user did not choose to run against their local server, and DNS rebinding is specifically engineered to make the browser do exactly that.

**How to avoid:**
Loopback bind is necessary but not sufficient — it must be paired with server-side **Host header validation against an explicit allowlist**, checked on every request, not just at connection setup. NCC Group's own remediation for this exact pattern: accept only `localhost:<port>` and `127.0.0.1:<port>` (and `[::1]:<port>` if IPv6 loopback is served) as valid `Host` values; reject everything else with 4xx before any handler logic runs. Do this as HTTP middleware ahead of ConnectRPC's mux, not inside individual RPC handlers — a single omitted handler defeats the whole scheme. Origin header validation (see Pitfall 2) is complementary, not a substitute — Host and Origin are attacker-controlled independently and an attacker who controls DNS controls both, so validating against a hardcoded allowlist (not "does it look like localhost") is what actually holds.

**Warning signs:**
- Threat model or design doc says "bound to loopback, so no auth needed" without a Host-check line item
- No test exercises a request with a spoofed `Host`/`Origin` header against the running server
- The bind-address flag design treats "loopback-only" as the entire security posture rather than one of two independent controls (this milestone's own scope note — "bind address and auth kept as explicit seams" — already signals awareness; the gap is making the *current* default state (no `--host`) demonstrably safe, not just structurally extensible later)

**Phase to address:** The phase implementing `codegraph ui`'s HTTP listener and ConnectRPC mux, before any RPC handler ships — this is a gate on the transport layer, not a per-feature concern. Should ship with a red-then-green test: a request carrying `Host: evil.example.com` against the live loopback listener must be rejected, demonstrated failing against the pre-fix code first (per this repo's own standing rule that a gate is not trusted until shown red against a real mutation).

### Pitfall 2: Origin/Host validation implemented as a substring or prefix check instead of an exact allowlist match

**What goes wrong:**
A validator that checks `strings.HasPrefix(host, "localhost")` or `strings.Contains(origin, "127.0.0.1")` is bypassable — `localhost.evil.com`, `127.0.0.1.evil.com` (a real DNS-rebinding trick: some resolvers/browsers historically treated dotted-decimal-looking hostnames loosely), or an attacker-controlled subdomain satisfy a substring/prefix test while being a fully attacker-controlled origin. `brannondorsey/host-validation` and similar middleware exist specifically because hand-rolled versions of this check keep getting this wrong.

**Why it happens:**
Substring/prefix matching feels like it covers "any port" or "any localhost variant" conveniently, but that convenience is exactly the hole.

**How to avoid:**
Exact match against a small, explicit, hardcoded set: `localhost:<port>`, `127.0.0.1:<port>`, `[::1]:<port>` for the actual bound port — not a wildcard, not a regex with `.*`. Since this milestone deliberately keeps the bind port and address as seams for a future `--host`, the allowlist must be derived from the actual listen configuration at startup, not hardcoded to a single port string, or the two features drift apart the moment the port becomes configurable.

**Warning signs:** Any `strings.Contains`/`strings.HasPrefix`/regex-with-wildcard in the Host/Origin check; the check lives in one handler instead of shared middleware, so it's easy to add a second handler that skips it.

**Phase to address:** Same phase as Pitfall 1 — they are one control, not two.

### Pitfall 3: `localhost` vs `127.0.0.1` vs `[::1]` treated as interchangeable when they are not

**What goes wrong:** `localhost` is a *name*, not an address — it resolves via `/etc/hosts` or the system resolver, and on a misconfigured or attacker-influenced system that resolution is not guaranteed to be `127.0.0.1`. Dual-stack machines commonly bind IPv4 loopback and leave IPv6 loopback (`[::1]`) unbound, or vice versa — a server that only checks the IPv4 literal in Host validation can be bypassed by a client connecting on the IPv6 loopback with a Host header the IPv4-only allowlist never anticipated. Browsers also resolve `localhost` differently across platforms in edge cases (some environments map it to both `127.0.0.1` and `::1` and race between them).

**How to avoid:** Bind explicitly to both `127.0.0.1` and `[::1]` (or deliberately choose one and document the other as unsupported), and include both literal forms plus `localhost` in the Host allowlist — but never derive the allowlist by resolving `localhost` at runtime, since that reintroduces exactly the DNS-trust problem the allowlist exists to avoid. Test on a machine where IPv6 is actually enabled, not just IPv4-only CI runners.

**Phase to address:** Same phase as Pitfall 1.

### Pitfall 4: CORS configured permissively "to make local dev easier" and that config survives into the shipped binary

**What goes wrong:** During development, a wildcard CORS origin (`Access-Control-Allow-Origin: *`) or `AllowCredentials: true` paired with a reflected origin is the fastest way to stop fighting the browser while iterating on the Svelte dev server talking to the Go backend on a different port. If that configuration is not build-tag-gated or environment-gated, it ships in the release binary, and now *any* website can make cross-origin ConnectRPC calls against the user's local index (read verbatim source, query the graph) as long as the loopback listener is reachable — which, per Pitfall 1, DNS rebinding gets around even without a rebind (a wildcard CORS response doesn't even need Host spoofing, since the browser will happily let a same-origin-restricted resource load cross-origin once the server says yes).

`connectrpc.com/cors` (the project's own CORS helper) makes correct configuration easy, but it still requires the caller to pass the right `AllowedOrigins` — it is not secure-by-default in the sense of refusing wildcard.

**Why it happens:** CORS errors are the single most common "make the error go away" friction point in local full-stack dev, and `*` is the fastest fix that isn't understood as a security control by whoever reaches for it under deadline pressure.

**How to avoid:** For a read-only, single-user, localhost UI where the browser and the ConnectRPC server are served by the *same* origin in production (embedded SPA served by the same `go:embed`'d handler that serves the API), CORS should not need to allow any cross-origin caller at all in the shipped binary — same-origin requests don't trigger CORS preflight in the first place. Reserve permissive CORS strictly for a `dev` build tag / local-only dev-server proxy setup, and add a test that the release build's CORS policy (if any exists at all) rejects an arbitrary `Origin`.

**Warning signs:** `AllowedOrigins: []string{"*"}` anywhere reachable from the default build; CORS middleware registered unconditionally rather than behind a dev-only build tag; no test asserting cross-origin requests against the release binary are rejected.

**Phase to address:** SPA-embedding phase (once the SPA is served same-origin, CORS should mostly become moot for the release binary) plus the security-hardening phase — verify at the seam where dev and prod configs diverge.

### Pitfall 5: Serving verbatim source files from disk reopens the path-traversal class this project already fixed once

**What goes wrong:** "Browse & inspect — open a node to verbatim source" means the UI's backend reads arbitrary file paths off disk and returns their bytes over ConnectRPC. If the path comes from client input (even indirectly, via a node ID that encodes a file path) and isn't confined to the indexed repo root, a request can walk `../../../etc/passwd` or read files outside the project entirely. This project's Phase 3 code review during the original build already found and fixed exactly this class of bug ("MCP `path` confinement") in the stdio MCP server — the same `internal/query.Engine` this milestone explicitly reuses as its third consumer. The risk here is not that the Engine itself is unsafe (it presumably already enforces confinement for MCP/CLI callers) but that a *new* code path in the UI's ConnectRPC handlers bypasses the Engine's existing confinement by reading files directly (e.g., for syntax highlighting, raw byte serving, or a "download source" feature) instead of going through the same guarded accessor.

**How to avoid:** Any new UI-side code that touches the filesystem directly (not through `query.Engine`) must reuse the exact same path-confinement logic the MCP server already has, not reimplement it. Prefer literally routing all source-content requests through `Engine`'s existing verbatim-source method rather than adding a second, parallel filesystem-access path in the ConnectRPC handler layer. Add a regression test mirroring the original MCP path-confinement test, aimed at the new ConnectRPC endpoint specifically — proving the *new* surface is covered, not just the old one.

**Warning signs:** A ConnectRPC handler that calls `os.ReadFile`/`os.Open` directly instead of going through `query.Engine`; any UI RPC accepting a raw file path string rather than a graph-relative node/file ID resolved by the Engine.

**Phase to address:** The Browse & inspect phase, gated before it's considered complete — same-shaped threat, cheap to prevent by reuse, expensive to discover after ship.

### Pitfall 6: Predictable, fixed port makes the loopback server an easier DNS-rebinding/CSRF target than it needs to be

**What goes wrong:** A hardcoded, well-known port (e.g., always `8080` or a project-branded port like `4242`) is trivial for an attacker's page to guess and probe — DNS-rebinding and CSRF payloads targeting "local dev tools" scan a small set of common ports precisely because tools use predictable defaults. A predictable port is a much smaller problem *if* Host validation (Pitfall 1/2) is solid, since guessing the port doesn't help if the Host check still rejects the request — but it does make blind port-scanning attacks (detecting *that* codegraph-ui is running, before attempting rebinding) trivially cheap, and it removes one layer of defense-in-depth for users who never get the Host-validation phase shipped correctly.

**How to avoid:** Prevention here is secondary to Pitfall 1 (a correct Host check makes port predictability low-severity), but cheap wins exist: bind an OS-assigned ephemeral port by default (`:0`) and have `codegraph ui` print/open the actual URL, rather than a fixed default; if a stable port is wanted for bookmarking, make it explicit opt-in via flag, not the silent default. Do not treat port obscurity as a security control on its own — it is not one.

**Phase to address:** `codegraph ui` command/listener phase — cheap decision to get right at the start, expensive UX regression to change later once users bookmark a fixed URL.

### Pitfall 7: `go:embed`'s default dotfile/underscore exclusion silently drops real Vite build output

**What goes wrong:** Go's `//go:embed` directive excludes files whose names begin with `.` or `_` from a directory pattern **by default** — this is documented, deliberate behavior (`embed` package docs; tracked historically in golang/go#42328 and #43854). Vite's production output routinely includes files matching that shape: `_app`-prefixed chunk directories are a common convention in some SvelteKit/Vite setups, and hashed asset filenames occasionally collide with the underscore-prefix pattern depending on the chunking strategy. A plain `//go:embed dist` silently omits those files at compile time — no error, no warning, just missing assets served as 404s the first time a user's browser requests a chunk that never made it into the binary. This is exactly the kind of failure that looks done (the build succeeds, `go vet`/`go build` are green) but isn't (some deep-linked or lazily-loaded route 404s at runtime).

**How to avoid:** Use the `all:` prefix form — `//go:embed all:dist` — which explicitly includes files/directories beginning with `.` or `_`. Verify by diffing the embedded FS's file list (`fs.WalkDir` over the `embed.FS` in a test) against the actual `dist/` directory tree on disk at build time — a mismatch means either the embed pattern is wrong or the drift guard (Pitfall 9) has a real gap. This should be a concrete, automated assertion, not a manual spot-check, since Vite's exact output shape can change across Vite versions without anyone touching the Go embed directive.

**Warning signs:** `//go:embed dist` without the `all:` prefix; no test comparing embedded file count/list against the on-disk `dist/` tree; a 404 in the browser console for a JS chunk that "should be there."

**Phase to address:** The `go:embed` integration phase, as a unit test gate before the SPA-embedding work is considered done.

### Pitfall 8: pnpm's strict, non-hoisted `node_modules` breaks tools that implicitly assume npm-style flat hoisting

**What goes wrong:** Unlike npm/yarn classic, pnpm creates a strict, symlinked `node_modules` tree by default (`node_modules/.pnpm/<pkg>@<ver>/node_modules/<pkg>`, with only a package's own declared dependencies visible to it, not the whole flattened tree). This is pnpm's core value proposition (correctness, disk efficiency) and it is also a well-documented, still-live source of "works under npm, fails under pnpm" breakage for tooling that implicitly relies on hoisting to resolve a plugin or peer dependency it doesn't declare directly. `vitejs/vite#324` is the canonical long-running issue tracking exactly this class of pnpm/Vite resolution failure; Vite's own troubleshooting docs and community writeups (`aimadetools.com`'s "shamefully-hoist fix," pnpm's own `node-modules` settings docs) exist specifically because this keeps recurring. The failure mode is almost always the same shape: a Vite/SvelteKit plugin, or a Protobuf/ConnectRPC codegen plugin (`@bufbuild/protoc-gen-*`-family or similar `@connectrpc`/`@bufbuild` packages), resolves a peer or transitive dependency it expects to find hoisted at the root and instead gets a "module not found" error that never occurs under npm/yarn's flatter default layout — and the shadcn-svelte CLI, which itself shells out to install packages, inherits whatever hoisting behavior the project's `.npmrc`/pnpm settings establish, so a misconfigured pnpm hoisting setup can make the CLI's own installs behave inconsistently too.

**How to avoid:** Do not reach for `shamefully-hoist=true` as a blanket fix — pnpm's own guidance (and the community writeups surfaced above) recommends starting from pnpm's strict default and using a targeted `public-hoist-pattern` for the specific package(s) that need it, once a concrete resolution failure is actually observed, rather than flattening the whole tree preemptively and losing pnpm's isolation guarantees for everything else. Pin the actual Vite/SvelteKit/`@bufbuild`/`@connectrpc` package versions used, since this class of bug is frequently fixed upstream between versions; verify the full `pnpm install && pnpm build` sequence on a clean checkout (no stale `node_modules`) as part of CI, since a locally-working `node_modules` that predates a pnpm-settings change can mask the failure until a fresh clone hits it.

**Warning signs:** A `.npmrc` with `shamefully-hoist=true` added without a recorded reason; a "module not found" error for a package that *is* listed in `package.json` but isn't a direct dependency of the package trying to resolve it; CI passing locally but failing (or vice versa) due to different `node_modules` staleness between a developer machine and a fresh CI checkout.

**Phase to address:** SPA scaffolding / ConnectRPC-codegen-tooling phase — resolve any hoisting-dependent breakage before it's built around, since a `shamefully-hoist` workaround adopted early tends to calcify rather than get revisited.

### Pitfall 9: pnpm's default-blocked lifecycle/build scripts make committed `dist/` output silently depend on unrecorded local approval state — a drift trap specific to this milestone's "commit `dist/`, `go:embed` it" design

**What goes wrong:** As of pnpm v10 (a deliberate, breaking, security-first change explicitly aimed at preventing supply-chain attacks via malicious postinstall/preinstall scripts), **dependency lifecycle scripts are ignored by default** — a package's `postinstall`/`preinstall`/`install` script simply does not run unless that package is explicitly approved via `pnpm approve-builds` (which records approval in `pnpm-workspace.yaml`'s `onlyBuiltDependencies`/`allowBuilds`, config that itself was renamed again between pnpm v10 and v11 — verify the exact field name against the pinned pnpm version at implementation time, not against this document). Packages with unreviewed build scripts are silently skipped by default; pnpm's `strictDepBuilds` setting exists specifically to turn that silence into a hard CI failure instead.

This interacts directly and dangerously with this milestone's core design decision: **`dist/` is committed to git and `go:embed`'d**, and the signed release pipeline is pure Go specifically so it never needs to run the JS build. If any dependency in the SPA's toolchain relies on a build/postinstall script to produce correct output (a common pattern for tools that download or compile a platform-specific native binary at install time — esbuild is the most widely cited real-world example of exactly this pattern, and Vite depends on esbuild transitively) and that script is silently skipped because it was never approved on a given machine, the resulting `dist/` build on that machine can differ from — or outright fail to build correctly compared to — a machine where the same package was approved. Two concrete failure shapes: (1) a developer approves the build interactively once, commits a `dist/` produced with the approved script having run, and CI (running non-interactively, with no recorded approval) produces a *different* `dist/` the next time anyone regenerates it, so the drift guard (Pitfall 10) flags a diff that has nothing to do with actual source changes — a false-positive that trains people to ignore the guard; or (2) the reverse — CI has the approval baked into its image/config and a fresh developer machine does not, so the developer's local `dist/` regeneration silently differs from what CI would produce, and they commit the wrong bytes without ever seeing an error.

**How to avoid:** Pin build-script approval **as committed configuration**, not as an interactive, per-machine action — explicitly list every package whose build script must run in `pnpm-workspace.yaml`'s approval config (`onlyBuiltDependencies`/`allowBuilds`, per the pinned pnpm version), so approval state is part of the repository, identical on every developer machine and every CI run, not something `pnpm approve-builds` decides interactively and differently each time. Enable `strictDepBuilds` (or the pinned version's equivalent) in CI so an unreviewed build script causes a **hard, loud CI failure** rather than a silent skip — this converts "dist/ quietly differs because of unrecorded approval state" into "the pnpm install step itself fails," which is a far cheaper bug to find. Document explicitly, in whatever runbook governs `dist/` regeneration, that a fresh clone plus `pnpm install --frozen-lockfile` must be the only sanctioned way to build `dist/` before committing it — never a machine with an accumulated, undocumented history of interactive `pnpm approve-builds` answers.

**Warning signs:** `pnpm-workspace.yaml` has no `onlyBuiltDependencies`/`allowBuilds` section at all (meaning approval state lives only in individual developers' un-committed local config or interactive history); CI's `pnpm install` step has no `--frozen-lockfile` and no `strictDepBuilds`-equivalent enforcement; a `dist/` regeneration produces a diff with no corresponding source change, and nobody can explain why.

**Phase to address:** The phase that introduces the SPA build toolchain — approval-state pinning belongs in the same commit that adds the `pnpm-lock.yaml`/`package.json`, verified by CI failing loudly (not silently degrading) the moment an unapproved build script is encountered.

### Pitfall 10: The "non-vacuous generated-artifact drift guard" (rule `84d1gfpywd`) goes vacuous in the exact way this repo has already been burned by three times — and pnpm gives it two new, pnpm-specific ways to do so

**What goes wrong:** The milestone explicitly commits to a drift guard for two consumers — `dist/` vs SPA source, and `*.pb.go`/generated TS vs `.proto` — and explicitly cites the project's own standing rule that a guard must carry a **positive assertion** it did its work, because negative-only guards pass vacuously the moment their anchor stops matching. This project's own `PROJECT.md` records the exact three-times-burned failure mode already: `go test -run PATTERN` **exits 0** when `PATTERN` matches zero tests — three plan-declared verification commands in the v0.11.0 sweep matched zero tests while reading green, one of them the named guard for a CRITICAL threat.

Applied here, the concrete failure shapes are:
- A CI step that runs `git diff --exit-code dist/` after a build step that silently failed or was skipped (e.g., `pnpm install --frozen-lockfile` failed due to a registry hiccup, the step still exits 0 because someone piped through `|| true` for flakiness, and the diff check then compares stale-vs-stale and reports "clean")
- A `buf generate` / drift-check job with a genuine race: proto generation and the diff check run in parallel or out of dependency order, so the diff check executes against not-yet-regenerated output and reports clean by comparing old-against-old (a documented real-world failure mode of exactly this CI pattern)
- **pnpm-specific:** the build-script-approval drift trap from Pitfall 9 makes a diff check pass vacuously in a different way than "no diff was computed" — it computes a real diff, but that diff reflects unrecorded approval-state differences, not actual staleness, so the guard is technically doing its job (finding a real byte difference) while telling the team something false about *why* — and a team that's been burned by that false-positive once tends to start treating the guard's failures as noise, which is the same end state as vacuous
- **pnpm-specific:** `pnpm audit` (see Pitfall 11) exits `0` both when genuinely zero vulnerabilities exist and when the registry call itself fails (non-200 response) — a JS-side vulnerability gate wired the same "exit code 0 = pass" way as the guard above inherits the identical vacuous-on-silent-failure shape, just in the security-scanning gate rather than the drift gate
- A guard whose anchor is a specific file list or glob that stops matching after a refactor (e.g., the SPA's build output directory gets renamed, or a new `.proto` file is added to a directory the guard's glob doesn't cover) — the guard keeps running, keeps passing, and keeps meaning nothing

**How to avoid:** Every drift guard must assert something that can only be true if the guard's actual comparison ran and found a match — e.g., assert the embedded/generated file *count* is nonzero and matches an independently-computed expected count, not just "no diff." Demonstrate each guard **red** against a real, deliberately introduced staleness (edit a `.proto` field without regenerating; edit an SPA source file without rebuilding `dist/`; revoke a build-script approval and confirm the pnpm-install step itself fails loudly rather than silently producing different bytes) before trusting it green — this repo's own standing rule, and the exact discipline that would have caught all three prior `go test -run` vacuous-match incidents. For the CI ordering hazard specifically, make the diff-check job depend explicitly on the generation job completing (not just interleave in the same job with implicit ordering), and regenerate-then-diff in a single sequential step rather than two jobs that could race.

**Warning signs:** A drift-check CI job with no test proving it can fail; `||`/`continue-on-error` anywhere near a generation, install, or diff step; a guard whose passing condition is "no diff found" rather than "diff found nothing AND the generation step is independently verified to have run and produced non-trivial output"; a JS-side security/drift gate whose exit code is trusted without distinguishing "checked and clean" from "the check itself silently failed to run."

**Phase to address:** The phase that introduces each generated-artifact pair (SPA build, Protobuf codegen) — the guard ships in the same phase as the artifact it gates, per this project's own established pattern (v0.10.0: "the claims-drift guard ships in the same phase as the resources it gates").

### Pitfall 11: Introducing a JS toolchain "for development only" leaks into the signed, reproducible release build anyway

**What goes wrong:** The stated design — commit built `dist/` assets, `go:embed` them, keep the release pipeline pure Go — is the right shape specifically to avoid this pitfall, but it only holds if nothing downstream ever *invokes* `pnpm`/`node`/`vite` as part of `goreleaser release` or any step that runs during a tagged release. Concrete ways this erodes over time: a `Makefile`/`Taskfile` target that regenerates `dist/` gets wired into a `pre-hook` in `.goreleaser.yaml` "just for convenience," or a CI job order accidentally makes the release job depend on a build job that runs `pnpm install`. The moment any release-triggering workflow path executes `pnpm install`/`pnpm install --frozen-lockfile`, the release's provenance and SBOM should — but frequently in practice don't — reflect that a JS dependency tree with transitive npm packages briefly existed in the build environment, and any content in `node_modules`/pnpm's content-addressable store that ends up on disk during that step is a supply-chain surface `govulncheck` (Go-only) and Syft's default Go-module scanning do not cover unless explicitly configured for the JS ecosystem too.

Real-world severity of *why this matters*: the September–December 2025 "Shai-Hulud" npm worm compromised hundreds (later ~"640", then a "2.0" wave affecting tens of thousands of repositories) of npm packages by hijacking maintainer accounts and injecting a self-propagating worm into `pre-install`/`post-install` scripts — meaning simply installing a compromised transitive dependency, even in a throwaway CI step, can execute arbitrary attacker code with access to whatever credentials that CI job's environment holds (including, in the worst case, an OIDC token scoped for cosign signing). pnpm v10's default-blocked build scripts (Pitfall 9) genuinely reduce this specific attack surface versus npm's historical always-run-postinstall default — a real, verifiable mitigation, not just pnpm being incidentally involved — but that mitigation only helps if the release-triggering environment never runs `pnpm install` at all; it does nothing for a release job that shouldn't be running pnpm in the first place. A toolchain confined to "development only" is only actually confined if the release pipeline is provably incapable of invoking it — not merely undocumented as doing so.

**How to avoid:** Enforce via CI structure, not convention: the `release.yml` workflow (or whichever job actually runs `goreleaser release`) must have no step, pre-hook, or transitive dependency that shells out to `pnpm`/`node`/`npx`/`npm`/`yarn`. The cheapest verification is structural — grep the release workflow and `.goreleaser.yaml` for those binaries and fail CI if found, or run the release build in an environment where `node`/`pnpm` are not even installed, so any accidental invocation fails loudly instead of silently succeeding. `dist/` regeneration belongs in a separate, clearly-labeled, non-release-triggering workflow (e.g., a PR check that verifies `dist/` is committed and current — the drift guard from Pitfall 10 — run in an environment that *does* have Node/pnpm, but is never the same job that produces signed release artifacts).

**Warning signs:** `.goreleaser.yaml` or `release.yml` referencing `pnpm`/`node`/`npm` anywhere, even in a comment describing a "just in case" regeneration step; the release job's runner image has Node.js/pnpm preinstalled and nobody has verified it's unused; no CI step asserting the release job's toolchain is Node/pnpm-free.

**Phase to address:** The SPA build/embed phase, cross-checked in the release-pipeline-integration phase (or as a dedicated verification step in whichever phase touches `.goreleaser.yaml`/`release.yml`) — this is exactly the kind of cross-cutting concern this project's constraints table already flags as non-negotiable ("the signed release pipeline must stay pure Go with NO JS toolchain in it").

### Pitfall 12: `shadcn-svelte`'s copy-in-source model reduces but does not eliminate npm/pnpm supply-chain exposure

**What goes wrong:** `shadcn-svelte` components are copied into the project's own source tree via its CLI rather than installed as an opaque npm dependency — genuinely reducing risk versus a black-box UI kit, since the component *code itself* is visible, diffable, and reviewable at commit time rather than silently updated by a `pnpm update`. But the CLI-added components still declare and install real npm runtime dependencies underneath (e.g., Radix/Bits UI primitives, `tailwind-variants`, `clsx`, and similar) — `dependencies`/`registryDependencies` in each `registry-item.json` are real `package.json` entries that pnpm resolves and locks into `pnpm-lock.yaml` like any other dependency, not just copied source. Treating "shadcn-svelte" as "not a dependency" because the *button component* is copy-pasted, while ignoring the transitive packages it pulls into `pnpm-lock.yaml`, misses the actual supply-chain surface.

**How to avoid:** Audit and pin the *actual* npm dependency tree that lands in `pnpm-lock.yaml` after running the shadcn-svelte CLI, same as any other dependency — lockfile committed, versions pinned, and (per Pitfall 13) scanned. Treat "copy-in-source" as reducing exposure to *drive-by updates of UI component logic*, not as exempting the project from JS supply-chain hygiene generally.

**Phase to address:** SPA scaffolding phase, alongside general JS dependency pinning (Pitfall 13).

### Pitfall 13: JS dependencies get no vulnerability-scanning or SBOM coverage because the project's existing gates are Go-only — and `pnpm audit`'s own exit-code behavior can make a "wired" gate vacuous anyway

**What goes wrong:** `govulncheck` is Go-specific — it walks the Go call graph and flags reachable CVEs in Go dependencies, and it has zero visibility into `package.json`/`pnpm-lock.yaml`. Syft's SBOM generation via GoReleaser's default `sbom:` block, absent explicit configuration, is oriented around what GoReleaser actually builds and ships (the Go binary and its archives) — it will not automatically enumerate a JS dependency tree that only ever existed at `dist/`-build time and never ships as a runtime artifact inside the binary. The practical risk: a real CVE in a transitive npm dependency (Radix primitives, Vite plugins, build tooling) goes completely unmeasured by this project's existing "govulncheck + Syft SBOM" story, creating a blind spot in a release process whose entire differentiator is verifiable supply-chain coverage — the same "gate goes blind" failure class this project has already named as its own recurring failure mode (see the GoReleaser-Pro-vs-OSS decision in `PROJECT.md`, where the concern wasn't a vulnerability getting worse but a gate becoming unable to see it).

Adding `pnpm audit` as the JS-side gate is the right instinct, but it inherits its own vacuous-guard risk, verified directly against pnpm's current documented behavior: **`pnpm audit` exits with status `0` both when the registry genuinely reports zero vulnerabilities *and* when the registry call itself fails with a non-200 response** — the command is deliberately designed to not fail CI on a registry outage, but that means a CI step that only checks the exit code cannot distinguish "we checked, and you're clean" from "the audit check silently never actually ran." This is the exact shape of rule `84d1gfpywd` — a guard whose green result is compatible with the guard having done nothing — landing in a *second*, independently-discovered place in this same milestone (the first being the drift-guard's `go test -run`-pattern precedent already recorded in `PROJECT.md`).

**How to avoid:** Add `pnpm audit` as its own named CI gate, distinct from and clearly not conflated with `govulncheck`'s coverage claim — but do not trust bare exit-code-0 as proof the audit ran. Parse and assert on the audit's actual output (e.g., that a dependency count was scanned, or that the JSON output's summary object is present and well-formed) rather than the shell exit code alone, so a registry outage produces a loud, distinguishable CI failure instead of a silent pass indistinguishable from "genuinely clean." If `SECURITY.md` or release docs describe vulnerability-scanning coverage, they must now describe **two** separate scanners with two separate scopes (Go via govulncheck, JS via `pnpm audit`) — this project already has a recorded, open issue of `SECURITY.md` overstating govulncheck's actual coverage; adding an entirely new, currently-uncovered ecosystem without updating that document repeats the same documentation-drift mistake at a larger scale, and doing so with a gate that can itself pass vacuously compounds it.

**Phase to address:** SPA scaffolding phase for the initial scanner wiring, with the positive-assertion fix (not bare exit code) built in from the start rather than retrofitted; documentation sweep (wherever `SECURITY.md` gets touched) to state coverage accurately.

### Pitfall 14: Binary reproducibility breaks (or is never actually verified) once build-time-generated JS assets are embedded, and pnpm's install determinism does not automatically transfer to `dist/`'s build-output determinism

**What goes wrong:** This project's release pipeline includes a reproducible double-build check. Once `go:embed` pulls in `dist/`, reproducibility now depends on the committed `dist/` bytes being bit-identical build input on every build machine — which they are, since they're committed, not regenerated at Go-build time. pnpm's own install step is comparatively deterministic (content-addressable store, strict resolution driven by `pnpm-lock.yaml`), which is a genuine, verifiable improvement over npm's historically looser resolution — but **install determinism is not the same property as build-output determinism**. Vite/esbuild's actual `dist/` output is not inherently reproducible byte-for-byte across machines/versions without deliberate configuration (embedded build timestamps, non-deterministic chunk ordering when parallelism varies, absolute paths leaking into source maps) — so a fully deterministic `pnpm install` can still be followed by a non-deterministic `vite build`, and treating pnpm's install-side guarantees as covering the whole pipeline is the mistake. This matters here specifically because if anyone ever *does* let `dist/` get regenerated as part of the Go build (contradicting the "commit dist/" design), the assumption that pnpm's determinism "handles it" would reintroduce exactly the class of non-reproducibility this project's release pipeline was built to catch and reject.

**How to avoid:** Reproducibility verification must exercise the actual shipped path: build the release binary twice from a checked-out commit with `dist/` already present as static, unmodified committed files (which the design already ensures), and confirm the double-build check still covers the embedded bytes, not just the Go compiler output. Separately and explicitly test whether `pnpm install --frozen-lockfile && vite build` run twice from the same clean checkout produces byte-identical `dist/` output — this is a distinct claim from "the install step is deterministic" and should be verified, not assumed, before relying on it for anything (even just confidence that regenerating `dist/` for the drift guard produces a stable, comparable artifact run to run). If `dist/` is ever regenerated as part of CI (even the drift-guard job, not the release job), do not let that regeneration path become load-bearing for what actually ships.

**Phase to address:** Release-pipeline-integration phase — extend the existing reproducibility check's assertions to explicitly cover the embedded SPA bytes, rather than assuming Go-level reproducibility (or pnpm's install-level determinism) implies embed-level reproducibility.

### Pitfall 15: ConnectRPC server-streaming for live push looks like it "just works" over HTTP/1.1 but gets silently buffered by a reverse proxy or misconfigured server, delivering updates in bursts instead of live

**What goes wrong:** Connect's protocol is explicitly designed to support server-streaming over plain HTTP/1.1 without requiring an Envoy-style translating proxy the way classic gRPC-Web does — this is one of the stated reasons ConnectRPC was chosen for this milestone. But "works over HTTP/1.1" is a protocol-compatibility claim, not a guarantee that every layer between server and browser actually flushes chunks as they're written. If `codegraph ui` is ever run behind any intermediary that buffers response bodies (a corporate proxy, a VPN client doing TLS termination, or even Go's own `http.Server` with response buffering misconfigured), server-streamed live-push events arrive in delayed bursts rather than as they occur — a bug that is invisible in the common case (direct `curl`/browser-to-`codegraph ui` with no intermediary) and only surfaces for users running through a proxy, exactly the kind of "works on my machine" gap this project's own local-first design otherwise avoids by construction. This is a well-documented failure mode for HTTP chunked streaming generally (nginx, in particular, buffers by default unless `proxy_buffering off`/`X-Accel-Buffering: no` is set).

**How to avoid:** Since `codegraph ui` is local-only and typically has no intermediary at all, this is lower severity than for a hosted service — but still worth an explicit smoke test: verify the server-streaming RPC actually flushes each message as written (`http.Flusher` interface used correctly in the Go handler) rather than relying on Go's default buffering behavior, and document that running `codegraph ui` behind a corporate proxy/VPN that intercepts localhost traffic is unsupported/untested, rather than silently degrading to "looks connected, updates just don't arrive live."

**Phase to address:** Live-push phase — add a test that asserts message-by-message delivery latency (not just eventual delivery) against the real HTTP server.

### Pitfall 16: ConnectRPC's typed error model gets flattened by naive frontend error handling, hiding the difference between "not found," "index stale," and "server crashed"

**What goes wrong:** Connect maps its RPC error codes onto real HTTP status codes and carries structured error details, which is one of Connect's actual advantages over a hand-rolled REST surface. If the Svelte client's error handling collapses every failed RPC into a generic "something went wrong" toast, the UI loses the ability to distinguish a genuinely stale/missing index (which should route the user toward `codegraph init`/`codegraph sync`) from a transient connection drop (which should trigger an automatic reconnect) from a real bug (which should surface a report-worthy error). Given this project already treats "stale graph shown without warning" as a correctness bug (worktree-mismatch detection exists precisely to surface staleness rather than silently querying wrong data), a UI that can't distinguish "no data because stale" from "no data because broken" reintroduces the exact class of silent-staleness bug this project has already spent effort eliminating elsewhere.

**How to avoid:** Map ConnectRPC error codes to specific UI states deliberately (e.g., `NotFound` → "no such symbol," `FailedPrecondition`/a custom detail for "index not yet built" → route to onboarding, `Unavailable` → reconnect banner) rather than a single catch-all error boundary. Reuse whatever staleness/worktree-mismatch signal the CLI/MCP paths already expose from `query.Engine`, surfaced as a first-class UI state rather than an error to swallow.

**Phase to address:** Index-health / query-workbench phase, where these distinctions actually matter to the user.

### Pitfall 17: `connect-go` and `connect-es` codegen/runtime version skew breaks silently or breaks loudly at the worst time

**What goes wrong:** Connect-ES 2.0 is an explicitly non-backward-compatible major version relative to 1.x, tied to a Protobuf-ES 2.0 runtime bump with its own Node/TypeScript minimum-version requirements — a `connect-es` bump in the frontend without a matching `connect-go`/protobuf-runtime posture on the backend (or vice versa) is a real, documented breaking-change boundary, not a theoretical one. Separately, protobuf's own toolchain is moving toward "poison pill" enforcement that will hard-fail on protoc/runtime version mismatches within a major line — a distinct hazard from the connect-es major-version one.

**How to avoid:** Pin `connect-go`, `connect-es`, and the protobuf codegen toolchain (`protoc-gen-go`, `protoc-gen-es` or equivalent) versions explicitly in `go.mod`/`package.json`/`pnpm-lock.yaml`, and bump them together, deliberately, as a single reviewed change — never let Renovate/Dependabot auto-bump the JS-side codegen dependency independently of the Go side. The drift guard from Pitfall 10 should also catch a version-skew-induced regeneration diff, since regenerating from a bumped codegen tool against unbumped `.proto` files will produce output that doesn't match what's committed.

**Phase to address:** ConnectRPC/Protobuf foundation phase — establish the pinning discipline before any handler code depends on generated types.

### Pitfall 18: Force-directed layout on the whole-repo file/package rollup produces an unreadable hairball the moment the repo has real scale

**What goes wrong:** Force-directed graph layouts (the default choice for "just show me the graph" implementations) have high computational complexity and, critically, degrade into visually unreadable "hairballs" on real-world dense graphs — this is a well-documented, named failure mode in graph-visualization literature, not a tuning problem that goes away with more iterations. codegraph-go's own self-indexing numbers give a concrete scale reference: the shipped v1.0 corpus already produces hundreds of files and thousands of edges on a mid-sized repo, and real target users (Sean's daily-driver repos, work team's Java/C# codebases) will be considerably larger. A naive `d3-force`/generic force-directed rendering of the file/package rollup at that scale will not read as "a whole-repo picture" — it will read as a blob of overlapping lines, which directly undermines the stated design rationale for the rollup view ("the rollup is largely reading edges that already exist rather than computing a new projection" — a *correct* data decision undermined by an *incorrect* rendering decision if force-directed is chosen naively).

**How to avoid:** Do not default to unconstrained force-directed layout for the whole-repo view. Options with better track records at this scale: hierarchical/clustered layouts that lean on the package/directory structure already present in the rollup (a tree-like or radial layout keyed to the file/package hierarchy reads far better than physics simulation for a rollup that already has natural hierarchy); edge bundling to reduce visual clutter even if force-directed positioning is kept; or falling back to a matrix/adjacency-style view for the highest-density subgraphs, since matrix representations are documented to out-perform node-link diagrams past roughly 20 nodes for readability even though they're less immediately intuitive. Whatever is chosen, benchmark it against this project's own largest real corpus (the work team's Java/C# repos, or codegraph-go's own ~209k-line self-index) before considering the graph view done — a demo against a 50-file toy repo proves nothing about the actual target scale.

**Phase to address:** Graph-view phase — this is a design decision that needs to be made before implementation, not discovered as a UX bug after ship.

### Pitfall 19: Live-push re-renders make graph nodes visibly jump around every time the watcher fires a re-index event

**What goes wrong:** A force-directed (or any physics-based) layout that gets fed updated data on every watcher re-index event and naively re-runs the simulation from scratch will reposition every node, not just the changed ones — nodes the user was looking at jump to new positions mid-read. This is *specifically* acute for this milestone because live push is a first-class, explicitly designed feature ("views update in place rather than going quietly stale") — the very feature meant to keep the graph current is also the feature most likely to make the graph view unusable if layout stability isn't handled deliberately. This is a well-known D3-force-specific footgun with a well-known fix.

**How to avoid:** Feed new/changed nodes into the *existing* running simulation rather than restarting it — d3-force's documented pattern initializes new nodes' `x`/`y` from an already-positioned neighbor (if a linked node has a position, the new node inherits it), which keeps unrelated parts of the graph stable. Use a low `alphaTarget` (not zero, not a full re-heat) when applying incremental updates so existing nodes drift gently rather than snapping. Key data joins (Svelte's `{#each ... (id)}` keyed blocks / D3's `selection.join` with a key function) by stable node ID so unrelated nodes aren't torn down and recreated on every update, which is what actually causes the visual "jump" in most naive implementations (the DOM node is destroyed and recreated at a fresh default position, not actually smoothly moved).

**Phase to address:** Live-push phase, verified specifically against the graph view (not just the list/table views, which don't have this problem).

### Pitfall 20: Live push causes reconnect storms and update-fan-out problems the moment more than one browser tab is open

**What goes wrong:** A developer routinely has `codegraph ui` open in more than one tab (one on `symbols`, one on the graph view), or leaves a tab open across a laptop sleep/wake cycle. If the server-streaming reconnect logic on the client is naive (immediate retry on drop, no backoff), a watcher restart or a laptop sleep/wake can produce a reconnect storm — many tabs simultaneously hammering the server-streaming endpoint the instant connectivity returns, which for a Pebble-backed single-process server competing with the fsnotify watcher's own write load could produce a real, if minor, contention spike (see Pitfall 22). Separately, if the server maintains per-connection state proportional to open streams without bound, an unbounded number of tabs (or leaked, never-cleaned-up dead connections) is a resource-growth path with no cap.

**How to avoid:** Client-side exponential backoff with jitter on stream reconnect, not immediate retry. Server-side: bound the number of concurrent server-streaming connections (or at minimum, log/monitor it) and ensure the watcher's re-index broadcast to N streaming subscribers is a simple fan-out over already-computed state, not N independent re-computations of the update payload. Test explicitly with 3+ concurrent browser tabs/clients against one `codegraph ui` process, including a deliberate connection-drop-and-recover scenario.

**Phase to address:** Live-push phase.

### Pitfall 21: The UI shows confidently-stale data instead of surfacing staleness, repeating a bug class this project has already fixed once for the CLI/MCP surfaces

**What goes wrong:** This project already treats "queries silently answer against a stale or wrong-worktree index" as a correctness bug serious enough to build dedicated detection for (worktree-mismatch detection: a `status` warning plus an inline MCP notice). A UI that queries `query.Engine` through ConnectRPC but doesn't surface the same staleness/worktree-mismatch signal — or surfaces it once on page load and then lets it go stale itself as the underlying index changes without a corresponding live-push event — reintroduces the exact bug class in a third surface, having already been fixed in two.

Two concrete ways this happens: (1) the UI reads the staleness/worktree state once at page load via a normal unary RPC and never refreshes it, so a worktree switch or a watcher pause mid-session goes unreflected in a page that otherwise "looks live" because the graph view itself is receiving push updates; (2) live push updates the *data* views but not the *health/status* chrome (a banner, a badge), so the "everything is live" impression from the graph view bleeds onto index-health information that isn't actually being kept current the same way.

**How to avoid:** Staleness/worktree-mismatch state should itself be part of the live-push stream, or independently polled on a short interval, not fetched once. The index-health view and any persistent UI chrome (header badge, connection-status indicator) should have their own explicit "last confirmed at" signal, distinguishable from "actively live," so a user can tell the difference between "this is current as of right now" and "this was current as of the last successful check."

**Phase to address:** Index-health phase, cross-checked against the live-push phase for consistency (both need to agree on what "current" means and how it's communicated).

### Pitfall 22: `internal/mcp/server.go`'s `pendingWriter` bug (CR-01) is folded in as a fix, but the same "server-initiated write without a corresponding client-initiated pending count" shape can be reintroduced independently in the new ConnectRPC server-streaming path if the two surfaces don't share the underlying logic

**What goes wrong:** CR-01 is: `pendingWriter.Write()` unconditionally decrements a `pending` counter that's only ever incremented when a *client request* comes in expecting a response; a server-initiated notification (unsolicited, not a reply to any pending request) still triggers a `Write()`, still decrements the counter, and can drive it negative or below its true value — corrupting the signal `stdinLingerReader` uses to decide whether to keep waiting for legitimately-owed responses before reporting EOF. The milestone explicitly folds this fix in because "this milestone adds a second long-lived connection-bearing surface, so the existing one being correct matters more, not less" — but that reasoning cuts both ways: the *new* surface (ConnectRPC server-streaming for live push) is structurally the same shape — server-initiated pushes interleaved with client-initiated request/response — and if its connection-lifecycle bookkeeping is implemented independently (a different counter, different assumptions about what "pending" means) rather than by extracting and reusing the corrected logic, it can reintroduce an equivalent bug under a different name.

**How to avoid:** Fix CR-01 first (already scoped as its own explicit deliverable), then when designing the ConnectRPC server-streaming connection lifecycle, explicitly ask "does server-initiated (unsolicited push) traffic get correctly distinguished from request-response traffic in whatever counts pending/in-flight state here" — as a design review question, not an afterthought. If there's a reusable pattern or shared primitive that falls out of the CR-01 fix, prefer reusing it over re-deriving equivalent bookkeeping independently for the streaming server.

**Phase to address:** CR-01 fix should land early (it's explicitly listed as foundational scope); the live-push phase's design review should explicitly reference CR-01's root cause as a checklist item, not assume unrelatedness just because one is stdio/JSON-RPC and the other is ConnectRPC/HTTP.

### Pitfall 23: A second process (`codegraph ui`) opening the same Pebble store the watcher/daemon already has open fails outright, not gracefully

**What goes wrong:** Pebble enforces a single-writer lock at `Open()` — this is documented, intentional behavior (tracked explicitly in `cockroachdb/pebble` issue #1583, "Multi-process access: 1 writer, N readers," and issue #1081), and Pebble's own maintainers note `Open()` acquires an exclusive lock **regardless of read-only mode** — opening the DB read-only from a second process does not sidestep the lock. Attempting to open the same store from a second OS process while the indexing daemon/watcher already holds it fails with an OS-level "resource temporarily unavailable" (flock contention), not a friendly application error. The milestone's design already anticipates this at the architecture level — "the UI sits on `internal/query.Engine` and does not fork it" — but "does not fork it" needs to mean "runs in the same process as (or is served by) whatever already holds the store open," and if `codegraph ui` is implemented as a genuinely separate OS process from `serve --mcp`/the watcher daemon (which the milestone explicitly calls for — "Its own process; it never shares a lifecycle with `serve --mcp`"), the store-access question is not automatically resolved by process independence; it's the opposite risk.

**How to avoid:** This needs a concrete decision, not an assumption: either (a) `codegraph ui` talks to the store through the **already-running** daemon process (via an RPC/IPC hop to the daemon that already holds the Pebble handle, rather than opening Pebble directly) — consistent with this project's existing single-writer daemon-with-lockfile pattern (`codegraph daemon`, single-writer lockfile, `codegraph unlock`) — or (b) `codegraph ui` opens its own read-only handle in a mode Pebble genuinely supports for concurrent access (Pebble's `Open()` locking issue thread should be checked for the current state of any read-only-safe multi-process mode as of the actual `cockroachdb/pebble` version pinned in `go.mod`, since this is an area the library's own maintainers were, as of the cited issues, still discussing rather than shipping). Given the "process independence from `serve --mcp`" is a stated design goal (isolating a UI-side connection bug from disturbing an agent's MCP session), option (a) — UI process talks to a running daemon/query surface via IPC rather than opening Pebble a second time — is very likely the correct shape, but this has to be an explicit architectural decision made and tested, not discovered as a runtime error the first time `codegraph ui` is launched while `serve --mcp` (or the watcher) is already running, which is the *normal*, expected user scenario, not an edge case.

**Warning signs:** Any code path where `codegraph ui` calls Pebble's `Open()` directly rather than going through an existing daemon/Engine instance; no explicit test launching `codegraph ui` while a watcher/daemon process already has the store open; the error a user sees in that scenario is a raw OS lock error rather than an actionable message.

**Phase to address:** This is architecturally foundational — needs to be resolved in the same phase that stands up `codegraph ui`'s process/command scaffolding, before any query-serving feature is built on top of an assumption about how the store is reached, since retrofitting IPC-to-daemon after building direct-Pebble-access UI handlers is a rewrite, not a patch.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|-----------------|------------------|
| Wildcard CORS during local dev, left in a non-build-tag-gated code path | No CORS friction while iterating on the Svelte dev server | Ships permissive CORS in the release binary (Pitfall 4) | Never in code reachable by the release build — gate behind a `dev` build tag or dev-server-only proxy config |
| `shamefully-hoist=true` reached for as a first fix to a pnpm resolution error | Makes "module not found" errors disappear immediately | Loses pnpm's isolation guarantees project-wide instead of fixing the one package that actually needs it (Pitfall 8) | Acceptable only as a temporary diagnostic step to confirm the hoisting theory, never committed as the fix |
| Approving pnpm build scripts interactively per-machine instead of pinning approval in `pnpm-workspace.yaml` | Fastest way to unblock a local `pnpm install` | `dist/` silently differs between machines with different approval history (Pitfall 9), and the drift guard produces false positives that erode trust in it | Never acceptable once `dist/` is committed and gated by a drift guard — approval state must be committed config from day one |
| Trusting `pnpm audit`'s exit code alone as the vulnerability gate | Fast to wire up, looks identical to any other CI gate | Indistinguishable from a silently-failed registry call (Pitfall 13) — exactly the vacuous-guard shape this repo has already been burned by three times | Never acceptable as the sole check — always pair with a positive assertion that scanning actually happened |
| Opening Pebble directly from `codegraph ui` "just to get something running" instead of routing through the daemon | Faster to a working demo | Hits the single-writer lock the first time a real daemon is also running (Pitfall 23); becomes a rewrite once the IPC-to-daemon shape is decided | Acceptable only for a throwaway spike explicitly not carried into the shipped command, and only if it's clearly labeled as such |
| Naive force-directed layout with default settings for the graph view | Fastest path to "something renders" | Hairball at real scale (Pitfall 18), have to redo the whole layout strategy later once real-repo testing happens | Acceptable for an internal prototype/spike used to validate the ConnectRPC data plumbing, never as the shipped default |
| Restarting the D3 simulation from scratch on every live-push update | Simplest possible "data changed → re-render" code | Visible node-jumping on every re-index event (Pitfall 19), directly undermines the "views update in place" design goal | Never acceptable once live push is wired to the graph view — this is core to the feature working as designed, not a nice-to-have polish item |
| A single generic error boundary/toast for all ConnectRPC failures | Less frontend error-handling code to write initially | Can't distinguish stale-index from broken-connection from real-bug (Pitfall 16), reintroduces the silent-staleness bug class | Acceptable only for the earliest internal spike; must be replaced before the index-health/staleness surfacing work is considered done |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|-------------------|
| `internal/query.Engine` reuse | Adding a second, parallel filesystem-access path in ConnectRPC handlers instead of routing all source-content requests through the Engine's existing guarded accessor | Every UI RPC that touches file content or graph state calls into `query.Engine`, never `os.ReadFile`/direct Pebble access from the handler layer |
| fsnotify watcher → live push | Treating the watcher's existing debounced re-index event as directly streamable without adapting it to per-connection fan-out, causing either missed events (single-subscriber assumption) or redundant recomputation per tab | A single re-index event is computed once and fanned out to N streaming subscribers; the watcher's existing debounce logic is unchanged, only its downstream consumers multiply |
| Pebble store access from a second process | Assuming "own process" (a stated design goal, isolating UI from MCP lifecycle) also means "own store handle" | UI talks to the store through the already-running daemon/Engine via IPC, or explicitly documents/tests the concurrent-open failure mode if a direct handle is genuinely required |
| ConnectRPC codegen (`connect-go` + `connect-es`) | Letting Dependabot/Renovate bump the Go-side and JS-side codegen tools independently | Pin both together, bump as one reviewed change, verify via the drift guard that regeneration still matches committed output after any bump |
| `go:embed` + Vite build output | Plain `//go:embed dist` silently dropping underscore/dot-prefixed Vite chunks | `//go:embed all:dist`, verified by a test comparing embedded file list to on-disk `dist/` |
| Release pipeline + JS toolchain | A "just for regeneration convenience" pre-hook or step in `.goreleaser.yaml`/`release.yml` that shells out to `pnpm`/`node`/`npm` | Structural CI check that the release-triggering workflow path never invokes Node/pnpm; `dist/` regeneration lives in a separate, non-release workflow |
| pnpm build-script approval + committed `dist/` | Approval state living only in a developer's interactive `pnpm approve-builds` history, never committed | Approval pinned as committed config (`pnpm-workspace.yaml`), `strictDepBuilds`-equivalent enforced in CI so an unreviewed script fails loudly |
| Vite/SvelteKit/`@bufbuild` codegen plugins under pnpm's strict hoisting | Reaching for `shamefully-hoist=true` at the first "module not found" error | Targeted `public-hoist-pattern` for the specific package once a concrete failure is observed; verify on a clean checkout, not a pre-existing local `node_modules` |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| Unconstrained force-directed layout on the whole-repo rollup | Graph view "works" on small demo repos, becomes an unreadable static-looking blob on real repos | Hierarchical/clustered layout leaning on directory/package structure; benchmark against the project's own largest real corpus before shipping | Directionally, SVG rendering degrades noticeably in the low thousands of nodes/edges, Canvas somewhat higher, WebGL considerably higher (exact crossover varies by library — verify against the chosen renderer, not these numbers alone) |
| SVG-based rendering of the graph view for large repos | Smooth on small graphs, frame-rate collapse (dragging/panning becomes laggy) as node/edge count grows | Canvas or WebGL rendering for the graph view specifically (table/list views can stay DOM-based); pick based on actual measured target-repo scale, not the toy demo | Roughly low-thousands of SVG elements is where degradation typically starts becoming noticeable — treat as a signal to benchmark, not a hard number |
| Restarting a D3 simulation fully on every live-push tick | Visible jank/jump on every watcher re-index event, worse the more frequently files change | Incremental simulation updates (low `alphaTarget`, position-inherit for new nodes) rather than full restart | Becomes visible the moment live push is wired to a layout that re-simulates from scratch — not a scale threshold, a correctness-of-approach issue |
| Verbatim source served over ConnectRPC without size awareness | Large files (generated code, vendored dependencies, minified bundles inadvertently indexed) blow up message size, slow to transfer/render | Cap or paginate verbatim-source responses for outlier-sized files; consider the same size limits the MCP/CLI paths presumably already apply (verify what `query.Engine`'s existing consumers do here, reuse rather than reinvent) | Depends entirely on what large files the target repos actually contain — verify against real corpora, not assumptions |
| Reconnect storms across multiple open tabs after sleep/wake | Momentary server-side contention (Pebble reads competing with watcher writes) the instant many clients reconnect simultaneously | Client-side exponential backoff with jitter; bounded concurrent-stream handling server-side | Scales with number of open tabs/windows — a single-tab workflow may never surface this, multi-tab habitual users will |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Treating loopback bind as sufficient security | DNS rebinding lets any malicious web page talk to `codegraph ui` as if it were same-origin (CVE-2024-28224 precedent, CVE-2025-66414/66416 precedent in the MCP ecosystem specifically) | Host header allowlist validation on every request, independent of bind address |
| Substring/prefix Host or Origin matching | Bypassable via `localhost.evil.com`-shaped hostnames or attacker-controlled subdomains | Exact match against a small hardcoded allowlist derived from the real bind config |
| Wildcard/permissive CORS surviving into the release build | Any website can drive cross-origin ConnectRPC calls against a user's local index | Same-origin-only in the release build (SPA served same-origin); CORS permissiveness confined to a dev-only build tag |
| Direct filesystem access in new ConnectRPC handlers, bypassing `query.Engine`'s existing path confinement | Reopens the exact path-traversal class already fixed once in the MCP server (Phase 3 of the original build) | Route all file-content access through `query.Engine`, never a second parallel `os.ReadFile` path |
| No JS-ecosystem vulnerability scanning, or one trusted by exit code alone | Real CVEs in npm/pnpm transitive dependencies go completely unmeasured by the Go-only `govulncheck`/Syft coverage this project already relies on; `pnpm audit` itself exits 0 on both "clean" and "registry call failed," so a naive wiring is silently vacuous | Explicit, separately-named JS dependency scanner (`pnpm audit` or an OSV-style scanner) as its own CI gate, asserting on parsed output rather than bare exit code |
| A JS toolchain step reachable from the release-triggering workflow | The Shai-Hulud-class npm worm (real, dated, self-propagating via install scripts) executing with access to whatever the release job's credentials touch, including cosign OIDC | Structurally prevent `pnpm`/`node`/`npx`/`npm` from being invokable anywhere in the release-triggering workflow path; verify by absence, not by policy |
| Build-script approval state left as undocumented, per-machine interactive history | `dist/` produced with silently different bytes depending on which machine built it, undermining both the drift guard and reproducibility claims | Pin approval as committed `pnpm-workspace.yaml` config; enforce `strictDepBuilds`-equivalent in CI so an unreviewed script is a loud failure, not a silent skip |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-------------------|
| Graph view defaults to force-directed layout at real scale | User opens the flagship "whole-repo picture" feature and sees an unreadable hairball, the opposite of the stated value proposition | Hierarchical/clustered default layout, tested against real large repos before ship |
| Live push restarts the layout simulation on every update | Nodes the user is actively looking at jump around mid-read, actively worse than not having live updates at all | Incremental, position-stable updates keyed by node ID |
| Staleness/worktree-mismatch surfaced once at load, not kept current | User trusts a "live-feeling" page that's actually showing outdated health status, reintroducing a bug class this project has already fixed for CLI/MCP | Staleness state included in the live-push stream or independently polled, with an explicit "last confirmed" indicator |
| Reconnect storms after laptop sleep/wake or watcher restart, with multiple tabs open | Momentary server contention or a hung reconnect leaves tabs showing "connecting..." indefinitely | Exponential backoff with jitter on the client; bounded concurrent-stream handling on the server |
| Generic "something went wrong" error for every ConnectRPC failure | User can't tell "your index is stale, run sync" from "the server crashed" from "you have no network" | Map ConnectRPC error codes/details to specific, actionable UI states |

## "Looks Done But Isn't" Checklist

- [ ] **Loopback bind:** Often missing Host header validation entirely — verify a request with a spoofed `Host` header against the running listener is rejected, not just that the bind address is `127.0.0.1`
- [ ] **`go:embed` of `dist/`:** Often missing the `all:` prefix, silently dropping underscore/dot-prefixed Vite output — verify by diffing the embedded FS's file list against the actual `dist/` tree, not by "the build succeeded"
- [ ] **Generated-artifact drift guard:** Often passes vacuously because the anchor stopped matching, a `||`/`continue-on-error` swallowed a real generation failure, or (pnpm-specific) unrecorded build-script approval state produces a "real" diff for the wrong reason — verify by demonstrating it fails against a deliberately introduced staleness, per this project's own standing rule
- [ ] **pnpm build-script approval:** Often left as undocumented per-machine interactive state — verify `pnpm-workspace.yaml` pins approval explicitly and CI fails loudly (not silently) on an unreviewed script
- [ ] **`pnpm audit` as a security gate:** Often trusted by exit code alone — verify the gate distinguishes "scanned and clean" from "the registry call itself failed," since pnpm's own documented behavior makes those two cases produce the same exit code
- [ ] **Release pipeline purity:** Often assumed pure-Go by design intent alone — verify by structural CI check (grep/env check) that no `pnpm`/`node`/`npx`/`npm` is invokable anywhere in the release-triggering workflow path, not just by the design doc saying so
- [ ] **Graph view at scale:** Often demoed against a small toy repo — verify against the project's own real largest corpus (its own ~209k-line self-index, or a representative Java/C# repo) before calling the graph view done
- [ ] **Live push + staleness:** Often ships live-updating data views while the staleness/worktree-mismatch chrome stays stale itself — verify the health/status surface is updated by the same live mechanism, not just the data tables
- [ ] **Multi-process Pebble access:** Often untested because the common dev workflow is "run `codegraph ui` alone" — verify explicitly with `serve --mcp`/the watcher daemon already running when `codegraph ui` starts, since that's the normal user scenario, not an edge case
- [ ] **JS supply-chain scanning:** Often assumed covered because `govulncheck` exists — verify there is a separate, explicitly named scanner covering `pnpm-lock.yaml`, and that `SECURITY.md` accurately states both scanners' actual scope

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|----------------|------------------|
| DNS rebinding / missing Host validation shipped in a release | MEDIUM | Ship a patch release adding Host validation middleware; no data format changes needed since it's purely a request-admission control, but any users who ran an exposed version briefly should be notified per normal security-advisory practice |
| Force-directed hairball graph view shipped as default | HIGH | Requires redesigning the layout algorithm and likely the rendering approach (SVG→Canvas/WebGL) together; hard to patch incrementally since layout choice affects interaction code (drag, zoom, click targets) throughout |
| Naive full-simulation-restart on live push shipped | MEDIUM | Contained to the graph view's update-handling code; swap in incremental-update logic without touching the data layer or ConnectRPC schema |
| Drift guard discovered to have been vacuous after a real drift incident | LOW-MEDIUM | Fix the guard's assertion, regenerate/rebuild the actually-stale artifact, demonstrate the fixed guard red-then-green against the real historical drift as its own test case |
| pnpm build-script approval state discovered to have caused a real `dist/` drift after ship | MEDIUM | Pin approval as committed config, regenerate `dist/` from a clean checkout with the pinned approval applied, verify byte-for-byte against what should have shipped, re-cut a release if the shipped `dist/` is confirmed wrong |
| `pnpm audit` discovered to have been silently non-functional (registry failures masked as "clean") | LOW-MEDIUM | Fix the gate to assert on parsed output; retroactively run a real scan against the current lockfile to close the gap the vacuous period left open |
| Pebble multi-process lock conflict discovered post-ship (`codegraph ui` fails to launch while daemon runs) | HIGH if direct-Pebble-access was baked into UI handlers throughout; LOW if the Engine/daemon-IPC seam was kept clean | If the seam was kept clean (UI never opens Pebble directly), route through the daemon instead — a targeted change. If direct access is scattered across handlers, this is close to a rewrite of the data-access layer |
| JS toolchain found reachable from the release workflow after a release already shipped | MEDIUM-HIGH | Audit exactly what that release's build environment had installed/executed; treat any credentials that environment held (cosign OIDC token, `GITHUB_TOKEN`) as potentially exposed per standard incident response; fix the workflow structurally, not just remove the offending line |
