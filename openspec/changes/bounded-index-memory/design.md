# Design

## Context

See proposal.md for the motivation. After #272, a full index runs these steps in `internal/indexer`:

1. `discover.DiscoverAll` lists the files in path order.
2. `Extract` runs W persistent workers and returns one `goextract.FileResult` per file, in one slice.
3. `detectRoutes` reads every result and parses the files of the languages whose route detector fired. Its route nodes and edges join the results as one result without a path.
4. `resolveRefs` builds the `symbols.Builder` from all results and freezes it into a `symbols.View`.
5. `resolve.Types` runs for each result, on one thread. It also sets `InterfaceMethods` on each node of the result.
6. `symbols.NewHierarchy` reads the type edges of every file and declares the overload sets.
7. `resolve.Calls` runs for each result, on one thread.
8. `resolve.Link` assembles all edges in the order of split-indexer-layers D6. It then runs the global passes: `synthesizeGoImplements`, `synthesizeOverrides`, `retryConformanceCalls` and `rewireSetEdges`.
9. `writeGraph` runs `resolve.CollapseEdges` over all edges, then stages the whole graph through `stage` and one `graphstore.Writer`, and commits once.

The resolver has two barriers, not one. Types must see the whole frozen view, and Calls must see the hierarchy that the type edges of every file build. Both are pure functions of one result and the shared read-only state (split-indexer-layers D2).

The hierarchy and the global passes read only four edge kinds: `contains`, `embeds`, `extends` and `implements`. This document calls them the structural edges. A sync already keeps the same subset of the stored graph in memory (`View.StoredEdges`).

Two kinds of node have no file. Every part of a C# partial type emits one shared node id with the sentinel `FilePath` "" (`csharpextract`). An overload set whose members span files also has `FilePath` "" (`symbols/hierarchy.go`, `setOf`). Today each part of a partial type emits its own copy of the shared node, with its own visibility. `csharpextract` sets no `InterfaceMethods`. Only `goextract` sets them, and a Go interface is declared in one file. `stage` sorts nodes with `sort.Slice`, which is not stable, so the store keeps an arbitrary copy.

Every open of the Pebble store takes its exclusive `LOCK` file. That includes the reads of a query, because `query.OpenAt` opens the store for each tool call. `graphstore.Open` retries a held lock for a short time, then returns `ErrStoreLocked`. The daemon, the startup reconcile of `codegraph serve` and the CLI already handle that error. `graphstore.Open` creates a store that does not exist.

`codegraph index` deletes the store directory before the run (`internal/cli/index.go`), and `wtindex.Build.build` does the same before its full rebuild. `internal/wtindex/seeddir.go` already builds an index in a locked, random-suffixed sibling directory and sweeps the leftovers. `internal/fsatomic` holds the crash-safe file operations of the repository.

## Goals / Non-Goals

**Goals:**

- Memory that does not depend on the per-file extraction state of the whole repository.
- The same records, byte for byte, as the current pipeline writes, for every worker count and claim order. The one exception is the merged node of an id that several files emit (D11).
- A full index that replaces the store in one atomic step and leaves no partial graph after a failure.
- A full index that is the only writer of its store while it runs, and that leaves the previous graph readable until the exchange.
- `graphstore.Import` within the same batch cap. #271 names it, and an import of a large export holds the whole graph in one batch today, which is the same growth.

**Non-Goals:**

- A smaller symbol index. The `symbols.View` keeps every node, as today.
- Faster indexing. The 10% throughput budget of the bench gate must still pass, but this change does not try to improve it.
- A sync that waits for a full index to end. A sync during a full index fails with `ErrStoreLocked`, as it does today while `run` holds the store.

## Decisions

### D1. Three parallel passes with two barriers

The full index runs these steps. Each pass uses the same W workers and the shared claim loop of D8.

1. Pass 1, extract. A worker runs `extractOne` on one file, then writes the result to the spill file (D2). It builds the `Declarations` of the result with `symbols.DeclarationsOf`. It keeps the offset of the record and the declarations of the result in slices of file order.
2. Route detection. The detectors run over the files of the languages whose detector fired, on `forEachFile`. A worker reads one record from the spill, runs `detectRoutesInFile` on it and keeps only its route nodes and edges. `detectRoutesInFile` takes its parser from the worker's parser cache, the same `setup` cache as pass 1, instead of a new parser for each file. The worker then stores the returned nodes and edges in the route result of the run, in file order. It releases its token after that store. The handler index comes from the declarations, not from the full results. The route result goes into the spill and the declarations like any other result, so it counts as one more record of the run.
3. Barrier 1. The declarations go into the builder in file order, as `AddResults` adds them today. The order matters, because the builder keeps candidates in the order it gets them. The builder merges the copies of a shared id (D11). It then freezes into the view.
4. Pass 2, structure. A worker reads one result from the spill and runs `resolve.Types`. It keeps only the structural edges of that file, in a slice of file order, and drops the rest.
5. Barrier 2. The hierarchy builds from the structural edges in file order, as `NewHierarchy` does today. The global synthesis runs once here (D3).
6. Pass 3, resolve and stage. A worker reads one result from the spill again. It runs `resolve.Types` and `resolve.Calls`, then the per-file assembly of D3. It sends the unit of its file to the writer (D4).
7. The writer stages the global records, the no-file unit of D3, the excluded-file records and, last, the metadata record.

`extractOne` is the per-file body that pass 1 and `Extract` share. It reads the file, takes the parser of its language from the worker's cache, calls `extract.File` and stamps the stat data. `extract.File` sets `InterfaceMethods` on each node from `FileResult.InterfaceMethods`, as `Types` does today, and `schemaMethodSpecs` moves from `resolve` to `extract` with it. `extract.File` is the one function that `extractOne` and the test helper `extractTree` of `resolve` both call, so the stamp has one place. `resolve_test.go` holds 16 calls of `goextract.Extract` today. Those tests move onto a helper that calls `extract.File`, so they get the stamp too.

`symbols.Declarations` is a new type that holds what the builder reads from a result: `ImportPath`, `RelPath`, `Language`, `Err`, the nodes, `MethodArity` and the `contains` edges of `IntraEdges`. It also holds `DefaultVisibility` (D11). `Language` is there for the handler index of route detection, which skips the results of other languages and the results with an error. `symbols.DeclarationsOf(r, defaultVisibility)` builds it from one `FileResult`, and it is the only place that lists these fields. Pass 1, the route result, `Sync` and the test helpers of `resolve` and `symbols` all call it. `symbols` imports `goextract` today, so the import set of task 3.1 does not change. `Builder.AddResults` takes a slice of `Declarations`, so the compiler enforces the projection. `Freeze` builds `View.InterfaceMethods` from the `InterfaceMethods` of the merged nodes. `Builder.AddInterfaceMethods` and the loop in `loadStoreView` that calls it go away, because the stored nodes reach `Freeze` through `AddNode` and carry their methods. So a full index and a sync feed the `implements` synthesis from one source.

`resolve.Types` takes each node of the result from the view (`View.Node`), so it uses the merged node. It no longer sets `InterfaceMethods`. It then changes no shared data, which pass 3 needs, because W workers read the view at once.

Pass 3 runs `Types` a second time, because pass 2 keeps only the structural edges. `Types` is pure and resolves without a parse, so the second run costs much less than a parse. Task 8.2 measures it.

Alternative: one barrier, with types and calls resolved in one pass. That does not work, because `Calls` needs the hierarchy that the type edges of every file build.

Alternative: pass 2 spills its full output for pass 3. That saves the second `Types` run, but it adds a second codec. If task 8.2 shows that the second run breaks the throughput budget, this decision changes to the spill. Task 8.2 showed that it does not: with the record form of D2, the index is within 3% of `main` on the 120,000-file corpus, so the decision stays.

### D2. The spill file holds the extraction results

Pass 1 writes each `FileResult` as one record to the spill file in the scratch directory of D6. The run keeps one offset per file. W workers append at once, so the spill writer is safe for concurrent appends. One mutex covers the offset counter and the write of a record. A worker takes the mutex, writes its frame at the current offset, advances the offset by the frame length and releases the mutex. So each record is contiguous at the offset that the writer returns, and no two records share an offset. Passes 2 and 3 read a record with `os.File.ReadAt`, which is safe from many goroutines.

The spill codec uses `encoding/gob` for the Go structs of `goextract`. It carries each `*schema.Node` and `*schema.Edge` as deterministic proto bytes, because gob does not handle the internal fields of a proto message. `FileResult.Err` travels as its text, with a flag for `goextract.ErrInternal`. Pass 1 still fails the run on an internal error before it writes the record.

A record does not hold the gob type descriptions. A gob stream sends the description of each type once, before the first value. A stream of its own for each record repeats the descriptions in every record and compiles a new decoder for every read. The first bench of task 8.2 measured that form: it made the index 16% slower than `main`, with 29% more peak RSS. So each record is one value message of a stream whose descriptions are known in advance. The first `Encode` of an encoder sends the descriptions of every type that the record type can reach, in an order that depends only on that type. So every encoder agrees on them, and a decoder that read them once reads the records of all encoders, in any order. The codecs come from a `sync.Pool`. A codec that returned an error does not go back. A test checks that several encoders write the same descriptions and that one decoder reads the records of all of them. The frame reader of `recordio` reads a frame of up to 4 KiB with one `ReadAt` call, and a longer frame with two.

The deterministic proto marshal (`deterministicMarshal` in `graphstore/batch.go`) and the uvarint length framing of `writeExportRecord` and `Import` move to a new package, `internal/recordio`. It exports a frame writer and a frame reader. The export, the import and the spill all use them. The reader takes a ceiling on the frame length. `Import` passes its 64 MiB ceiling, which guards against a hostile stream. The spill passes no ceiling, because the run wrote the spill itself in the same process. The spill adds a read of one frame at an offset. A `rapid` property in `recordio` round-trips frames of every length class of the uvarint prefix, the empty frame included. The kind tags of the export frames become exported constants of `graphstore`, because the export comparisons of package `indexer` read them. `internal/indexer/determinism_test.go` decodes and encodes export frames with its own copy today, because the framing was unexported. The failure tests of task 5.6 and the golden test of task 3.3 live in the same package and decode exports through `recordio`. One package must not hold two decoders of one format, so that copy moves onto the reader and the writer of `recordio`. `internal/indexer/mainstream/phpextract/resolution_test.go` holds one more copy of the frame decoder, the frame encoder and the kind tags. Its comment says that it mirrors the unexported copy of `determinism_test.go`. It is an external test package that already imports `graphstore`. So it moves onto `recordio` and the exported tags in the same task, and the comment goes. `resolve/link_test.go` keeps its deterministic marshal. That is one call of the proto library, not a codec.

The danger of a codec is a field that it drops. Gob also drops zero values, so an empty slice comes back as nil. Two tests guard the codec (task 2.2). `TestSpillRoundTrip` round-trips every fixture and part of the synthetic corpus. Its positive assertion is that the corpus sets every field, checked by reflection. `TestSpillRoundTripProperty` draws `FileResult` values with `rapid`, empty and zero values included. Both compare with `cmp.Diff`, `protocmp.Transform()`, `cmpopts.EquateEmpty()` and a `cmp.Comparer` for `error` that compares nil-ness and the `Error()` text. The comparer is needed because the decoded error is a new value, and `go-cmp` refuses to compare two error values on its own. A probe of the plan review showed that. The property also draws an error that wraps `goextract.ErrInternal`, and asserts `errors.Is` on the decoded error. So the flag of the codec has a test. The resolver treats an empty slice and a nil slice the same, so the equality that matters ignores the difference.

The generator of the synthetic corpus is `Generate` in `tools/bench/gencorpus`, which is `package main` and cannot be imported. `gen.go` and `gen_test.go` move into a new package, `internal/gencorpus`, under `internal/`. That follows `internal/corpora`, which `tools/corpora` and an `internal/indexer` test both import. A test under `internal/` never imports a package under `tools/`. The `gencorpus` command and `TestSpillRoundTrip` import it. The bench runner keeps its subprocess build of the command, so that the runner and the `task` targets generate the corpus through one command. Its constant `regressionFileCount` is a copy of `ProductionFileCount`. Its comment says that the copy exists because the generator is `package main`. The move makes that sentence false, so the runner imports `gencorpus.ProductionFileCount` in its place and the comment goes. A test in `tools/bench/runner/main_test.go` compares the default count with `regressionFileCount`, so it reads the imported constant too. `tools/bench/BASELINE.md` names `tools/bench/gencorpus.ProductionFileCount` in two places, and both change to the new path.

Alternative: parse each file again in passes 2 and 3. That needs no codec, but the parse is most of the cost of a full index, so throughput falls to about one third.

Alternative: a protobuf message that mirrors `FileResult`. Each new extraction field then needs a schema change as well. The gob codec follows the Go struct.

### D3. The global passes run once, and each edge has one unit

Today `Link` runs the global passes over every edge, but they read only the structural edges. At barrier 2, a new function in `resolve` takes the structural edges, the view and the hierarchy, and returns:

- The synthesized `implements` edges, then the synthesized override edges, as today.
- The overload set edges of `rewireSetEdges`, and the member pairs whose `contains` edge a set replaces. On the sync path, `rewireSetEdges` also returns `contains` edges from an owner to the members of a stored set that no result declares any more. They stay among these outputs. Each one belongs to the unit of its member's file, because `EdgeOwnerID` names the target of a `contains` edge. A full index has no stored set, so it gets none.
- A conformance index for the retry of pending calls.

The barrier 2 function reads the structural edges once into two tables. The member index maps a type and a member name to every member id, in edge order. It also maps each member id to its owner, the source of the last `contains` edge that targets it, as `methodOwner` does today. The supertype table maps a type to its supertypes and keeps the kind of each edge. The hierarchy of `symbols` builds a supertype map from the same edges, without the kinds. The table stays apart from it, because the table carries the overlay below. The hierarchy that `Calls` reads holds no synthesized edge today, and that does not change. The three global passes of today each build their own maps from the same edges: `retryConformanceCalls` builds two member maps and a supertype map, `synthesizeOverrides` builds a member map, and `synthesizeGoImplements` builds a struct-method map and an interface-embeds map. All of them read the two tables instead. The retry takes the last id for a name and the owner from the member index, as today. `Hierarchy.OwnerOf` does not serve for the owner, because it keeps only a source of type kind, and today's rule takes any source. `synthesizeOverrides` takes every id of kind method, as today. `synthesizeGoImplements` takes the members whose type is a struct and whose member is a method, with the arity from the view. It takes the interface embeds from the `embeds` entries of the supertype table between two interfaces. `View.Members` does not serve here, because it holds only the `contains` edges inside one file. A Go method in another file than its struct reaches the retry only through a `contains` edge that `Types` makes. An overlay adds the synthesized `implements` edges to the supertype table, because the structural edges do not hold them. Two passes read them. `Link` appends them today before it calls `synthesizeOverrides`, which takes `implements` as a supertype edge, and the retry reads them too. So the barrier 2 function keeps that order. It runs `synthesizeGoImplements` first and adds the overlay. Then `synthesizeOverrides` and the conformance index read the table with the overlay. The claim that the results stay as today is an equivalence over every list of structural edges. `TestConformanceIndexMatchesHelpers` (task 3.4) draws such lists with `rapid`. It compares the retried calls and the overrides with a reference model of the four rules of today, which task 3.4 lists. Without one index, pass 3 builds the retry maps for each file, and the cost grows with the square of the repository.

Each edge belongs to one unit, chosen by the owner path: the `FilePath` of the node that `EdgeOwnerID` names. The owner lookup covers the nodes of the view and the overload set nodes of the hierarchy. The map that `resolve.go` builds from `g.Nodes` covers the same two sets today. The package nodes add nothing, because their `FilePath` is empty either way. An overload set inside one file has that file as its path, so the type-to-set `contains` edge belongs to that file's unit.

- A file unit holds the edges whose owner path is that file.
- The route unit holds the edges of the route result. Each of them has a route node as its source, so no other unit makes the same triple. `Assemble` checks both sides: it refuses an edge of the route unit whose source is not a route, and an edge of a file unit whose source is one. The owner path of such an edge is the file that registers the route. But pass 3 handles the route result as its own record, so its edges form their own unit.
- The no-file unit holds the edges whose owner path is "". These are the base edges of a C# partial type, which several parts emit for one source. They are also the edges whose owner is an overload set that spans files.

Pass 3 sends the edges of the no-file unit to a run-wide list instead of the writer. It keeps them by file index and by the categories of split-indexer-layers D6. After pass 3, the writer collapses that list in the same order that `Link` uses today. The no-file unit is small, because only partial types and cross-file sets have edges in it.

All candidates of one (source, kind, target) triple are in one unit. The reason is that the owner of an edge follows from its source or its target. So a collapse of each unit gives the result of one global collapse. The per-file assembly enforces the units with `goextract.ErrInternal`. In a file unit, each edge must have the file or "" as its owner path. In the route unit, each edge must have a source node of kind `route`.

Pass 3 assembles the edges of a file in the order of split-indexer-layers D6, restricted to that file. The order is type edges, calls without a deferred type and deferred calls. Then come synthesized `implements`, synthesized overrides, retried calls and the set edges. A unit holds every candidate of a triple, in the same relative order as the global list of today. `CollapseEdges` sorts each group with `sort.Slice`, which is not stable but is deterministic for one input order. So the group gets the same pick in both paths.

`Link` becomes a loop over the per-file assembly plus the collapse of the no-file unit, so the order has one implementation. `Sync` still calls `Link`, with only the results of its reparse set. `Link` returns the owner-path function of its `Global` with the graph, and `Sync` uses it for the file-index entry of each edge and for its check of a kept edge. So the unit of an edge and its file-index entry have one source in a sync, as in a full index. `Link` collapses the edges in each unit, so `Sync` does not collapse them again, and `CollapseEdges` takes only the edges. Its file-path parameter had no effect: the candidates of one triple share their source, and so its file. The barrier 2 function takes the structural edges of those results plus the stored structural edges of the view (`View.StoredEdges`). The global passes take them the same way today, through `withStoredEdges`. So it can return a synthesized `implements` or override edge whose unit is an unchanged file. One example is a changed file that adds an interface which an unchanged struct satisfies. After the loop over the results, `Link` collapses the global edges of each unit that has no result in the call, and emits them too. The sync then keeps or deletes stored synthesized edges against that output, as it does today. In a full index every unit has a result, so this step emits nothing. A full index does not take that on trust: after barrier 2 it asks the `Global` for the edges of the units with no record, and fails with `goextract.ErrInternal` if there is one. Task 3.3 adds `TestLinkUnitsMatchGolden` before `Link` changes. It runs a full index over the fixtures and compares the stored edge, file and file-index records with a golden file. Under the flag `-update-link-goldens`, it writes the golden file instead, in the pattern of `-update-plain-goldens`. So one test holds the projection. One run with the flag, at the commit before `Link` changes, records what a full index stores today. The file-index records (`x/`) prove the owner lookup, because the owner path of each edge decides its `x/` entry. The goldens live in package `indexer`, because only that package runs route detection, and the route unit is part of what they prove. After `Link` changes, the same test runs the new pipeline over the same fixtures against those files. Node records stay out of the goldens, because the merged node of D11 changes them on purpose. Two tests in `resolve` cover what the goldens cannot. `TestAssemblyRejectsForeignEdge` gives the assembly an edge that breaks each unit rule. `TestCollapseByUnitProperty` draws random edge lists with `rapid` and checks that the union of the collapse of each unit equals one global collapse.

### D4. One writer, a token bound and a size cap checked on the batch length

W tokens bound the working state. The tokens are a `semaphore.Weighted` of size W from `golang.org/x/sync/semaphore`. A worker takes a token with `Acquire(ctx, 1)` before it claims a file, and gives it back at the release point of its pass (D8). In pass 3, the release point is after the writer stages the unit of that file. So at most W files hold working state at once, whether a worker holds the file or the unit waits for the writer. The channel to the writer holds min(W, n) units, where n is the number of spill records, the route result included. So a send never waits once the worker has its token. A worker waits for a token, and the writer sets the pace.

The writer goroutine stages each unit through `stage`, with the bounded batch writer as its `Sink`. So the layer keeps one staging step. The body of the writer goroutine is one unexported function that takes the store as a `graphstore.GraphStore`. So a test can call it with the stub store of `resolve_test.go`. `writeGraph`, `Resolve` and the `resolveFunc` parameter of `run` go away, because they have no caller left. `indexer.resolveRefs` goes away with `Resolve`, its only caller. `resolveGraph` stays, because `Sync` calls it. The tests that inject a failure through `resolveFunc` use the `onCommit` hook of D8 instead.

The bounded batch writer lives in `graphstore`, because it owns the `*pebble.Batch`. `NewBoundedWriter(cap, onCommit)` is a method of the `GraphStore` interface, in the place of `NewWriterSized`. It returns a `graphstore.Writer`, so the `Sink` of `stage` and `importRecord` take it as they take any writer. The two last verbs of that interface keep their meaning. `Commit()` applies the open batch, and `Close()` releases an open batch without a commit. The one difference from `NewWriter` is that an add can commit a full batch first. `onCommit` is a `func(graphstore.Commit) error` that the writer calls for each commit. A `Commit` holds four values. `Len` is the length of the batch. `BeforeLast` is the length that the writer read before it added the last record. `Records` is the record count. `Sync` says whether the commit used `pebble.Sync`. `BeforeLast` costs nothing, because the writer reads `Batch.Len()` before each add for the cap check. So a test sees the cap rule and the commit mode with no access to the batch. So a test stub of the interface can serve it, as the stubs serve `NewWriter` today. `graphstore.DefaultBatchCap` is the one default. Before it adds a record, the writer reads `Batch.Len()`, the length of the batch buffer. If that length is already above the cap and the batch holds a record, it commits the batch and starts a new one. Then it adds the record. So the writer computes no record size, and a batch exceeds the cap by at most its last record. In terms of a `Commit`, a batch with more than one record has `BeforeLast` at or below the cap. A batch with one record has no part to bound. Its `BeforeLast` is the 12-byte header. The cap is a memory budget, and a record is at most a few megabytes, so that slack does not matter. If the open batch holds a record, `Commit()` applies it. The mode of that last commit follows the store. A store from `OpenStaging` has the WAL off, so the writer uses `pebble.NoSync` there. On every other store it uses `pebble.Sync`. Each earlier commit uses `pebble.NoSync`. The writer goroutine of `run` and `importWith` each defer `Close()`, so a failed run releases its open batch. `TestWriterClosesBatchOnStageError` (task 5.3) holds that rule with a stub writer that fails on `PutEdge`. It takes the place of the close-on-staging-error test of `writeGraph`. Both commit sites check `Batch.Count() > 0`. The length alone cannot tell an empty batch, because `Batch.Len()` counts the 12-byte batch header, so an empty batch has length 12. Without the guard, a test with a cap below 12 commits an empty batch before its first record. A writer that got no record commits one on `Commit`. Pebble accepts both without an error, so the guard is the one enforcement point of the rule that no batch is empty. With the guard, the batch that `Commit` applies holds the last record. So the last record of a run is always in the last batch, and that batch is the one `Sync` commit of `Import`. `run` stages the metadata record last (D1 step 7). `Import` holds it back until the end of the stream (D9). So in both, the metadata record is in the last batch. A check before the add can keep every batch under the cap. But it needs the size of each record before the add, which means a second model of the key shapes of `keys.go`. The plan review found a gap in that model for the metadata record, so the plan dropped it. `batchsize.go` goes away with it: `BatchSize`, its methods, `Bytes`, `fixedAllowance`, `maxSizeHint` and `setOverhead`. The same rule serves `run` and `Import`. `NewWriterSized` goes away with `writeGraph`, its last caller. `Writer.DeleteGraph` goes away for the same reason. The exchange of D6 replaces the graph, and `ReplaceStore` is then the one way to do that. `DeleteAllExcludedFiles` stays, because tests of `internal/indexer` and `internal/uiserver` build a store without coverage records through it. Its doc comment drops the sentences about `writeGraph`.

Every batch of the staging store commits with `pebble.NoSync`. The staging store has the WAL off (D6, `OpenStaging`), and Pebble refuses a `Sync` commit on such a store with "pebble: WAL disabled". A probe of the plan review showed this. Durability comes from the flush and close of D6. `Import` writes into a store with the WAL on, so its last batch, the metadata, commits with `pebble.Sync`.

`DefaultBatchCap` starts at 16 MiB. Task 8.2 measures peak RSS with the cap at 4, 16 and 64 MiB. The change keeps the value with the lowest peak RSS inside the throughput budget. Task 8.2 measured 4 MiB at 21% below the throughput of `main`, which is outside the budget. It measured 16 MiB at 3% below with the peak RSS of `main`, and 64 MiB at 1% below with 23% more peak RSS. So the value stays 16 MiB. The value does not change the specs. `run` passes the `batchCap` variable of D8, and `Import` passes `DefaultBatchCap` through the unexported `importWith`, which its test calls with a lower cap. `Import` commits no batch for a stream with no records. For a stream with no metadata record, it commits the other records in batches like any other.

The final records do not depend on the batch grouping, because each key gets one value. Node ids that several files emit get the merged node of D11, the same bytes from every unit. Each file has one record. Each edge triple is collapsed in its unit. So a store built with any W and any claim order holds the same records.

The node count in the metadata is the number of distinct node ids. The writer computes it as the number of nodes in the view, plus the package nodes and the overload set nodes. Their ids come from distinct kinds, so the three sets do not overlap. `stage` stops returning its own count. A count per unit counts a shared id once per unit, so it is wrong after D3. Its doc comment drops the sentence about two nodes with one id, because D11 merges them before `stage` sees them.

Alternative: several writers that commit at once. Each writer then holds its own open batch of up to the cap, so the memory of the write step grows with W. One writer keeps it at one batch.

Alternative: sorted SSTables through `DB.Ingest`, one per bounded batch. Pebble checks overlap only among the tables of one call, so this needs no global sort. But each ingested table that overlaps the others lands in L0. A graph write of thousands of overlapping tables gives a read amplification that a compaction must pay down. Each table also costs one file write and `fsync`. Batches through the memtable avoid both.

### D5. Run-wide state

These parts of the run stay in memory until the run ends. Each one grows with the repository.

- The `symbols.View`: every node and the candidate maps, as today.
- One spill offset per file for the whole run, and one `Declarations` value per file until barrier 1. Their nodes are the nodes that the view holds, not copies. ### D6. Scratch directory, writer lock and atomic exchange

`internal/wtindex/seeddir.go` already has the mechanism that this change needs: a random-suffixed sibling directory, an `flock` on a lock file inside it, and a sweep of the directories whose lock it can take. That code moves to a new package, `internal/scratchdir`. The prefix is a parameter. A second parameter asks for the `.gitignore` that `wtindex` writes, because its directory sits in the worktree root. A store scratch directory under `.codegraph` does not ask for it. The `flock` helper of `wtindex` moves to its own small package, `internal/flock`, with a shared or exclusive mode. `scratchdir` uses it for the directory lock, and `graphstore` uses it for the swap lock and the writer lock below. So `graphstore` does not depend on `scratchdir`.

The move also closes two gaps in the current code. Today the directory exists for a moment before its lock does, and a sweep in that moment removes a live build. Also, `lockFile` creates the lock file and then calls `flock`, in two system calls. A sweep between them can lock the new file and remove the directory. A probe of the plan review showed this.

`scratchdir.New` creates the directory under a pending prefix. A prefix must have a name and end in "-". The pending prefix replaces that dash, so a pending name never starts with the final prefix. `New` returns an error for any other prefix, and `Sweep` removes nothing for it. If the caller asks for it, it writes the `.gitignore`. It then creates a lock file under a temporary name with `O_EXCL`, locks it, and renames it to the lock name. So the lock file has its lock from the first moment it has its name. Last, it renames the directory to its final name with `fsatomic.RenameDir`. `wtindex.place`, which moves a finished seed directory into the worktree, keeps its `os.Rename`, because no requirement of this change touches it. The sweep looks at both prefixes. It removes each directory whose lock file it can lock. A final-name directory without a lock file is a run that a kill stopped during its own removal. A final name always gets its lock before the name, so no live run looks like this. The sweep removes it. A pending directory without a lock file is a live run in its first instants, or a run that a kill stopped then. If its modification time is older than `scratchdir.PendingMaxAge`, one minute, the sweep removes it. Otherwise it stays. The sweep never creates a lock file. For a store, the writer lock also keeps the sweep and the create apart. The reason is that `run` does both while it holds that lock.

A full index uses one scratch directory, `<store>.scratch-<random>`, beside the live store. It holds the lock file, the spill file and a `store/` directory, the staging store. Only `store/` takes part in the exchange. The lock file and the spill never enter the live store.

The full index cannot keep the live store open during the build. Every open takes the exclusive Pebble lock, so every query then fails. A new writer lock keeps other writers out instead. It is an exclusive `flock` on `<store>.write`, which `graphstore.LockWriter` takes through the retry helper below. `Sync` and the full index each hold it for their whole run, and a query does not take it. `Sync` takes it after its backfill check, because the backfill calls `run`, which takes it itself. So no sync commits to the live store during a build, and a query reads the previous graph until the exchange. A sync that cannot take the lock returns `ErrStoreLocked`, which its callers already handle.

The writer lock file, the swap lock file and the scratch directory all live in the parent of the store, `.codegraph`. Today `codegraph init` creates that directory and the store directory. If `.codegraph` is missing, `codegraph index` refuses with `ErrNotInitialized`. Otherwise it deletes the store directory and recreates only that directory. For every other caller of `Run`, `graphstore.Open` creates the parent through `pebble.Open`. `run` now creates the parent itself, after `DiscoverAll` and before step 1, because the lock files need it before any store opens. So discovery walks the tree as it does today, `codegraph index` keeps its check, and a tree with no `.codegraph` directory still indexes through `Run`. The daemon has its own lock, the pid file `.codegraph/daemon.lock`. It keeps one daemon process per repository, and the writer lock keeps one writer per store at a time. The daemon's package comment says today that its lock guards the single-writer invariant, and that sentence changes to name the daemon process instead.

`run` takes these steps.

1. It takes the writer lock. If the retries run out, it returns `ErrStoreLocked`.
2. It reads the prior coverage generation through `OpenExisting`, then closes the store. There are three outcomes, the same three that `codegraph index` classifies today. `ErrStoreLocked` fails the run. `ErrNotFound`, from `OpenExisting` or from `GetMeta`, means a store that was never indexed. It gives generation 0 and leaves `Stats.PriorGenerationErr` nil, so a first index prints nothing. Any other error also gives generation 0, and the run goes on with that error in `Stats.PriorGenerationErr`. Today `run` aborts on that third outcome, and only the CLI tolerates it. The tolerant rule moves into `run`, because `run` now owns the read, and `--force` is the recovery path that the CLI already documents.
3. It sweeps the leftover scratch directories of the live store, then creates its own.
4. It opens the staging store at `<scratch>/store` with `graphstore.OpenStaging`. That function opens with the Pebble WAL off, because a crash discards the store anyway. It goes through the shared open and retry helper below.
5. After the last commit, which holds the metadata with the prior generation plus one, it closes the staging store. The `Close` of a staging store flushes the memtables first, because with the WAL off the unflushed data is otherwise lost.
6. It takes the swap lock exclusive. Only then does it look for the live store, with `os.Lstat` on the live path. So no open of this release can create the live store between the look and step 7. A live path that exists takes the exchange branch, whatever it holds. `codegraph init` creates the store directory empty. A probe of the plan review showed that a rename onto an empty directory fails on macOS with "file exists".
7. If the live path exists, it takes the Pebble lock of the live store with `pebble.LockDirectory`. It then exchanges `<scratch>/store` and the live store with `fsatomic.ExchangeDirs`. If the live path does not exist, it moves the staging store into place with `fsatomic.RenameDir`. Then it releases the locks of steps 6 and 7. It releases them on every return path, a failed exchange included. Pebble keeps its directory locks in a registry of the process. A lock that leaks there blocks every later open of the store in a daemon until the process ends.
8. It removes the scratch directory, which now holds the old store or nothing. `graphstore.ReplaceStore` runs steps 6 and 7, so the locks stay in `graphstore`. Then it releases the scratch lock and the writer lock.

`fsatomic.ExchangeDirs` and `fsatomic.RenameDir` are new. `ExchangeDirs` swaps two directories in one system call: `renameat2(RENAME_EXCHANGE)` on Linux, `renamex_np(RENAME_SWAP)` on macOS. Both are in `golang.org/x/sys/unix`. `RenameDir` calls `os.Rename`. Each call changes an entry in the parent of each of its two paths. In step 7 those parents differ: they are the scratch directory and `.codegraph`. So both functions then call one unexported helper. It runs `fsync` on the parent of each path. If the two paths share a parent, it runs `fsync` once. Then the change is durable in both directories. The helper calls `fsync` through an unexported variable of `fsatomic`, and a test wraps that variable to record the directories. The system call of `ExchangeDirs` goes through a second unexported variable, which `TestExchangeDirsUnsupported` replaces. `ReplaceStore` calls the exchange through an unexported variable of `graphstore`, `exchangeDirs`, whose value is `fsatomic.ExchangeDirs`. A test of `graphstore` replaces that variable, so `fsatomic` exports no seam. The seam lives in the package whose test sets it, as `sameDevice` of `wtindex` and `openLockRetrySleep` do. The package comment of `fsatomic` changes, because it says today that the package holds one file-write primitive. A probe of the plan review showed why step 6 comes first: `graphstore.Open` creates a missing store, and an `os.Rename` onto that store then fails with "file exists". `fsatomic` knows nothing of Pebble, and the locks stay in `graphstore`, the one package that knows Pebble.

`run` removes its scratch directory on every return path, after the errgroup ends and the staging store closes. A killed run leaves its directory unlocked, and the sweep of the next full index removes it. Before the exchange, that directory holds a partial new store. After the exchange, it holds the old store. A store open does not sweep, because an open runs for each query, and a sweep can delete a whole copy of the store.

A process that has the store open during the exchange keeps the old directory, and Pebble creates new files by path. So it then writes into the new store. Two locks prevent this. `Open`, `OpenExisting`, `OpenStaging` and `Checkpoint` all call the unexported `open` in `graphstore`. It takes a shared `flock` on `<store>.swap` for the life of the handle. It takes that lock before `pebble.Open` and before it creates any directory, because step 6 depends on that order. The lock file sits in the parent of the store. If the parent is missing, `open` creates it, as `pebble.Open` did before. The exchange takes the same lock exclusive. A process of an earlier release does not take the swap lock, so the exchange also takes the Pebble lock of the live store. The retry loop around `pebble.Open` moves into a helper that `open`, `LockWriter` and the exchange all call, with `openLockRetrySleep` as the test seam. The helper takes two functions: the attempt, and a classifier that turns a lock-held error of that attempt into `ErrStoreLocked`. It retries while the classifier returns `ErrStoreLocked`, and it returns every other error at once. `graphstore` has one rule for the classification: `classifyOpenError` and `isLockHeldOS` match the error shapes of Pebble's lock, so they run only on an error from `pebble.Open`. `pebble.LockDirectory` takes the same lock with the same shapes, so the exchange passes `classifyOpenError` too. An `flock` failure has another shape, `EWOULDBLOCK` from a `LOCK_NB` call. So `LockWriter` and the swap lock pass a classifier of `internal/flock`, which matches only that errno. The rule that each classifier runs only on the errors of its own call does not change. Three comments state the old rule, and each one changes. The `Callers` line of `isLockHeldOS` gives `pebble.Open` as the only source of its errors, and it now names `pebble.LockDirectory` too. The comment of `classifyOpenError` names `Open` as its only permitted caller. It now names the retry helper, with an attempt of `pebble.Open` or of `pebble.LockDirectory`. The comment of `ErrStoreLocked` says that classification happens exactly once, inside the retry loop of `Open`. It now says that each classifier runs inside the retry helper, on the errors of its own attempt. When the retries run out, the run fails with `ErrStoreLocked`, removes its scratch directory, and the live store does not change.

A filesystem without the exchange returns `EINVAL` on Linux or `ENOTSUP` on macOS. The run then fails with an error that names the cause, and the live store does not change. There is no fallback to two renames, because a crash between them leaves no store.

`graphstore.OpenExisting` opens a store that exists and creates no store. Pebble's `ErrorIfNotExists` does not serve alone. A probe of the plan review showed that it creates the directory and its `LOCK` file before it fails. So the unexported `openExisting` first looks for the directory and for Pebble's manifest marker in it. If either is missing, it returns `ErrNotFound` and creates nothing. One unexported helper of `internal/indexer` calls it. The helper opens the store with `OpenExisting` and returns its metadata or `ErrNotFound`. Step 2 calls the helper, and `needsFileIndexBackfill` calls it in place of its `graphstore.Open`. Both read the metadata of the live store, and a backfill check then creates no empty store. For the backfill check, `ErrNotFound` from the helper means a backfill, as `ErrNotFound` from `GetMeta` does today. `Checkpoint` keeps its `os.Stat` check and its call to `open`, so it gains the swap lock and nothing else. During a first full index, the live path is the empty directory that `codegraph init` made. In that case `wtindex` must still get a pending build from `Checkpoint`, as it does today.

`Stats.PriorGenerationErr` carries the third outcome of step 2, and `codegraph index` prints the warning that it prints today. The two existing CLI tests on a never-indexed store and on an unreadable store keep passing. `Options.CoverageGenerationFloor` goes away, because no caller wipes the store before the run any more. `codegraph index` drops its own lock check before the run, because step 1 and step 2 return `ErrStoreLocked`. It wraps that error from `indexer.Run` with the remedy text that it prints today. A test in `internal/cli` holds the writer lock with `graphstore.LockWriter` and runs `codegraph index`, which then prints that text.

`wtindex.Build.build` stops calling `os.RemoveAll` on its store before `indexer.Run`, because `run` now replaces the store atomically. Its seed directory stays, because it places a whole `.codegraph` directory into the worktree, not only a store.

Alternative: the full index keeps the live store open for the whole run, as `run` does today from resolution to the commit. That keeps syncs out with no new lock, but every query fails for the whole build.

Alternative: no writer lock, and a second read of the generation under the swap lock. That keeps the generations unique, but the exchange then discards the commits of each sync during the build.

Alternative: write in place with the metadata last, as the commit marker. With it, each reader must refuse a store without metadata, and a failed run leaves no graph.

### D7. Cancellation and goroutine lifetime

`run` takes a `context.Context` as its first parameter, and the errgroup of the run derives from it. `Run` and the backfill of `Sync` pass `context.Background()`, so the exported API does not change. The tests of the package call `run` with a context that they cancel.

Pass 1, route detection and pass 2 run one after the other, each in the `errgroup.WithContext` of its own `forEachFile` call. No writer runs yet, so each of them has only its workers to stop. Pass 3 and the writer share one more `errgroup.WithContext`, because an error of either must stop the other. In each group, the first error cancels the context. The token wait, a send to the writer and the writer's receive each stop on `ctx.Done()`. Only the sender closes a channel. When the workers of the last pass are done, that pass closes the channel to the writer.

`goleak.VerifyTestMain` runs once, after the last test of the package. It cannot tell which test leaked. The tests of the first-error requirement therefore check at the moment `run` returns: `goleak.VerifyNone(t, goleak.IgnoreCurrent())` outside a bubble, and `synctest.Wait` inside a `testing/synctest` bubble. The backpressure and cancel tests run in a bubble, so they need no sleeps.

### D8. One claim loop and its test hooks

`forEachFile(ctx, n, workers, setup, body)` owns the claim loop of all three passes and of route detection: the semaphore, the shared counter and the hooks. It starts min(W, n) workers, as `extractWithFactory` caps its workers at the file count today. So a large `--workers` value allocates nothing per unused worker. `setup` runs once per worker, for the parser cache of pass 1 and of `Extract`. `body` runs once per file, and it gets a `release` function for the token of that file. `release` gives the token back and calls `onRelease`. The body calls it at the release point of its pass. In pass 3 the body puts `release` into the unit that it sends to the writer. The writer goroutine calls it after it stages the unit. `release` acts once. When a body returns an error, the loop calls it, so a failed file leaks no token. The loop that is inline in `extractWithFactory` today moves into it, and its body becomes `extractOne` (D1).

Each pass names the release point of its token. In pass 1, it is the return of the spill write. In route detection, it is the store of the file's route nodes and edges in the route result of the run. In pass 2, it is the append of the structural edges of the file. In pass 3, it is the moment the writer stages the unit of the file.

Unexported package variables of `internal/indexer` give tests control, in the style of `gitExecLookPath`. Production code never sets them.

- `claimOrder` maps the counter value to a file index. A test sets a permutation.
- `onClaim(step, file) error` and `onRelease(step, file, state)` see a token being taken and given back. `step` names the pass or route detection, and `file` is the file index. If `onClaim` returns an error, the body of that file does not run, and the loop fails with that error. A test injects a worker failure in this way. A test counts the files that hold working state at once in each step. `state` is the unexported struct that holds the run-wide state of D5. A test reads four parts of it. Three are the artifacts of the steps: the spill file with its offsets, the route result and the structural edge slice. The fourth is the channel to the writer, and a test reads only its length. So the hook can read the artifact of the step for its file. Each of the three artifacts is a slice of file order, and the worker wrote the slot of its file before the release. The hook reads only that slot, and it reads the spill with `ReadAt`, so it shares no memory with a worker that still writes. In pass 3 the writer goroutine calls `onRelease` after it stages the unit. The store is not readable until the exchange, so a test notes the file there and reads the store after the run.
- `batchCap` sets the cap that `run` passes to `graphstore.NewBoundedWriter`. A test lowers it.
- `onCommit` is the commit callback that `run` passes to the bounded writer. It gets the `graphstore.Commit` of D4 for each committed batch: the length, the length before the last record, the record count and the commit mode. A record count is the number of `Writer` calls, not of Pebble entries, because one `PutNode` can put two entries. If the callback returns an error, the commit fails with that error. A test injects a commit failure in this way.
- `onPass(step, state)` runs at the start of each pass and of route detection, with the run state. A test runs a sync or a read of the store from it. `TestSinkBackpressure` keeps the state of pass 3, and reads the length of the channel to the writer from it.
- `onExchange` runs after step 7 of D6 returns and before step 8. A test kills the process from it.

`graphstore` gets no hook variable for the cap or the callback. Its tests pass them to `NewBoundedWriter` or `importWith` themselves. Its three seam variables are `openLockRetrySleep`, `exchangeDirs` (D6) and `checkpointHook`. `Checkpoint` calls `checkpointHook` while it holds the handle of its source open. `TestReplaceStoreWaitsForCheckpoint` uses it to hold that handle, and so its shared swap lock, while a `ReplaceStore` waits.

Because the hooks are unexported, the tests that use them live in package `indexer` and call `run`. `internal/cli` cannot set them, and `indexer` cannot import `internal/cli`. A test that kills a process starts the test binary again as a child. The child gets a `-test.run` value that names a helper test, and an environment variable that selects the hook. The child sets `onCommit` or `onExchange` to send `SIGKILL` to itself. Their export comparisons use `exportNormalized`, the helper that `sync_determinism_test.go` already holds. It moves beside `indexAndExportWith` in `determinism_test.go` and takes a flag that says whether to clear `CoverageGeneration`. It decodes and re-encodes the frames through `recordio`. `indexAndExportWith` calls it in place of its own inline copy. No new export helper is added. `indexAndExport` in `internal/indexer/mainstream/phpextract/resolution_test.go` holds a third copy of the same normalization. It stays. A test file cannot be imported from another package, and a production helper whose only callers are tests has no place in `graphstore`.

### D9. `graphstore.Import` uses the bounded writer

`Import` reads the export stream and writes through the bounded batch writer. An export holds the metadata frame first, and `Import` puts the records in stream order. So `Import` keeps the decoded metadata frame aside while it reads. After the end of the stream, it puts that record through the writer as the last record. It writes into the store that the caller passes, with no scratch directory, because it has no production caller. Its doc comment states that the store is not complete until `Import` returns nil. For a value of 0 or below, `run`, `Sync` and `forEachFile` all call it. ### D11. A node id that several files emit becomes one merged node

`symbols.Builder` merges the copies of one id that it gets from several declarations, in file order. The merged node takes the first visibility that differs from the default visibility of its language. If any copy is exported, the merged node is exported. Its other fields come from the first copy, and within one file from the first copy that the file emits. No rule merges `InterfaceMethods`, because no shared id carries them (Context). The merge also covers a route that one file registers twice. The route id depends only on the file, the method and the path, so the copies share an id. But each copy has the start line, end line and start column of its own registration. The merged node takes those of the first registration.

The default comes in through `Declarations.DefaultVisibility`, which `internal/indexer` sets from a new field, `extract.LanguageSpec.DefaultVisibility`. So `symbols` keeps the import set of the split-indexer-layers table: `goextract`, `nodeid` and `schema`. For C#, the value is a new constant of `csharpextract`, `DefaultTypeVisibility`. The extractor passes the same constant to `csharpVisibility` for a type, so the default lives in one place.

C# applies an access modifier on any part to the whole type. So the first visibility that a part states is the visibility of the type. Today the store keeps an arbitrary copy, so a `public partial class` can be stored as `internal` and fail to resolve from other files. This is the one change to the graph, and the `graph-index` delta states it.

A sync must merge the same way. The sync first finds the shared ids of its cycle, from two sources. The first is the ids with `FilePath` "" that the results of an `Extract` emit. The sync reads them from the results of every reparse wave, not only the first, and repeats the waves until no new shared id and no new file appear. A file that a later wave reparses can hold a part of a second partial type. Without the repeat, the other parts of that type stay out of the reparse, and the sync counts their edges twice. The second is the stored nodes with `FilePath` "" that a stored `contains` edge of a modified or deleted file targets. The sync reads those edges with `IterateEdges` on the file node id of each such file, kept to an exact source match. A modified file counts, because a part can leave its type. It drops `partial`, takes another name or moves to another namespace. Its results then emit the id no more, and only the store names it. It finds every other file that emits one of those ids through the stored `contains` edges, with the reverse adjacency below. It reparses those files in its later wave. The initial `dependentPaths` set cannot see them. It comes from the stored edges of the files that changed, and an added part is not in the store yet. `loadStoreView` runs after the waves. It skips a stored node whose id is a shared id of the cycle, so the merged node of the reparse replaces the stored one. It also skips every stored edge whose owner id (`EdgeOwnerID`) is such an id. Those are the two groups of the delete step below: the base edges from the shared id and the `contains` edges into it. Otherwise a stale base edge of a deleted part reaches the hierarchy through `View.StoredEdges`. It also reaches the overrides and the conformance retry of `Link` through `withStoredEdges`. The sync then stores an edge that a full index does not have. Sync finds the other files that emit a shared id through the stored `contains` edges that target it. It reads them from its own `buildReverseAdjacency`, which takes the set of edge kinds to keep, here calls and `contains`. Today only the `dependentPaths` step builds that adjacency, and only after the prune removed a node. A sync that only adds a file removes nothing, so it builds none. The added-part scenario of the `graph-index` delta is such a sync. So the sync now builds the adjacency once, at the first of two moments that need it. The first moment is the `dependentPaths` step of a sync with a non-empty `goneIDs`. The second is the shared-id step of a cycle with a shared id. A sync with neither builds none. Each reader of the map filters by kind. The `dependentPaths` loop reads only the calls entries, as today, so a `contains` edge into a pruned method adds no dependent. The shared-id step reads only the `contains` entries. Today that function is a copy of `query.BuildReverseAdjacency` with a fixed filter to calls, and its comment says so. The comment changes: the function is now a variant that takes edge kinds, and `query` keeps its own. A shared function in `graphstore` can remove the copy, but no requirement of this change needs it. Issue #274 tracks that collapse, together with `query.BuildImplementsIndex` and `query.buildContainsIndex`, two more full-scan edge indexes. The same kind parameter can serve the first. The second indexes by source and folds overload sets, so it needs a parameter for the key as well. The comment in `sync.go` cites the issue. The sync sorts its declarations by `RelPath` before `AddResults`, because a later reparse wave appends files out of order. When no file emits a shared id any more, the sync deletes its node, as it does for an overload set today. The delete step below removes its edges first, so no edge from it dangles. An unchanged file can hold an edge into that node, for example a class that extends it. For an ordinary node, `filesResolvingToChangedSets` finds such a file. It reparses each file that owns an edge into a candidate set that the sync changes, whatever the edge kind. Today it skips a stored node with `FilePath` "", because it reads the module key and the changed state from the file path. It now treats a shared id of the cycle through the files that emit it. It takes those files from the `contains` entries of the reverse adjacency. It records the id under the module key of each of those files. If one of them is in the changed set, the name counts as touched. If none of them is unchanged, the stored id leaves the set of after. So a shared node that loses its last part changes its candidate set. Each file that owns an edge into it then joins the later wave. The reverse adjacency then has a third reader, and a cycle with a shared id builds it before that call.

The edges of the no-file unit have no `x/` entry, because `PutEdge` writes none for the owner path "". So the prune of a file through the `x/` index does not remove them. There are two groups. The first group is the base edges whose source is a shared id. The second group is the `contains` edges from the file node of a part to a shared id. Before it stages the reparse, the sync deletes them for each shared id of the cycle. That includes the ids of a deleted part and of a part that left its type. It finds the first group with `IterateEdges` on the shared id, kept to an exact source match. It takes the second group from the `contains` entries of the reverse adjacency for the shared id. The adjacency above is built once per sync, so the stored edges are read once. It then stages the edges of the merged reparse. So the edges of a deleted part go away, and the edges of the other parts come back.

Alternative: keep the copy of the last file in path order. That needs no merge, but a partial type then takes the visibility of whichever part sorts last.

Alternative: if two copies differ, fail the run. A valid C# tree with one public part then fails to index.

## Risks / Trade-offs

- [The second `Types` run in pass 3 slows the index] → Task 8.2 runs the bench on the 120,000-file corpus. If throughput falls by more than the budget, pass 2 spills its output (D1 alternative).
- [The spill codec drops a field or an empty value] → The two codec tests of D2.
- [A triple gets candidates from two units] → `TestLinkUnitsMatchGolden` and the `ErrInternal` checks of D3. Task 8.1 compares the stores of three real trees with `main`.
- [The merge of D11 changes the stored node of a partial type] → The `graph-index` delta states the rule. Task 8.1 lists each node that differs from `main` and makes sure that each one is a merged node.
- [The scratch directory needs as much disk space again as the live store] → A full disk fails the run. The live store does not change.
- [A filesystem has no atomic exchange, for example some network filesystems] → The run fails with an error that names the cause. It does not change the store (D6).
- [A reader holds the shared swap lock for a long time] → The exchange waits for the timeout of the open lock, then fails. Today the same reader blocks `codegraph index` through the Pebble lock.
- [A sync during a long full index fails] → The daemon queues the flush again on `ErrStoreLocked`. It does so at most 5 times (`maxFlushLockRequeues`), at its 2-second debounce. A full index that runs longer than about 12 seconds exhausts the chain. The `.sync-pending` sidecar then stays set, and the next watcher event or session reconcile syncs the change. The file records of the new store come from the files that pass 1 read, so that later sync still finds the change.
- [A killed run leaves a copy of the old store until the next full index] → Only disk space. The next full index removes it.

## Migration Plan

Nothing to migrate. The store format does not change, and an existing store opens as before. A store with a partial type gets the merged node at its next full index. A sync that reparses a part of that type also writes it. A process of an earlier release takes no writer lock, so it can still sync during a full index of the new release. The exchange then discards that sync, and the next sync reparses its files. Rollback is a revert of the change. The earlier release ignores the files that this change adds beside the store. The two lock files, `.codegraph/store.write` and `.codegraph/store.swap`, are empty. A scratch directory, `.codegraph/store.scratch-*`, stays only after a killed run, and it holds at most one copy of the store. The earlier release has no sweep for it. So after a rollback, make sure that no `codegraph index` runs, then remove it with `rm -rf .codegraph/store.scratch-*`.
